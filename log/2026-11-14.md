### 1.2 引擎实现要点

1. **状态机**：版本 `DRAFT→PUBLISHED→RETIRED`（已发布不可回草稿）；实例
   `RUNNING⇄SUSPENDED→COMPLETED/TERMINATED/CANCELLED`（终态不可再迁移）；节点 `PENDING→ACTIVE→COMPLETED/SKIPPED/CANCELLED`；
   任务 `PENDING→COMPLETED/CANCELLED/TRANSFERRED`。
2. **幂等**：启动键 = `document_type:document_id:version_id`，冲突**返回既有实例**（`replayed:true`），不是 409。
3. **任务完成**：事务内「重读实例状态 → 重读任务状态 + 乐观锁 → SOD 判定 → 任务与节点迁移 →
   执行节点动作（同一事务）→ 计算后继并物化 → 审计与事件」；动作失败整体回滚，任务保持 `PENDING`，副作用为零。
4. **条件求值**：八个运算符白名单 + 字段路径白名单；**禁止原型链**（`__proto__` / `constructor` / `prototype`），
   变量缺失一律 false。**不执行任何脚本**。
5. **动作契约**：注册式 handler（`FORM_WRITE` / `PUSH` / `CALLBACK` / `NOTIFY`），在业务事务内执行；
   未注册或抛错 → `PLATFORM_WORKFLOW_ACTION_FAILED`，事务整体回滚。
6. **路由前缀** `/api/platform/workflow-*`，共 16 条；**未占用** `/api/approvals/**`（6 族 canonical）
   与 `/api/workflows/**`（退役中的旧 CRUD）。

### 1.3 实现期发现并修正的四项真实缺陷

| # | 缺陷 | 处置 |
|---|---|---|

| 2 | **节点实例被重复插入**（启动时全量物化 + 进入节点时再插入）→ UNIQUE 冲突 | `materializeNode` 改为**激活**既有节点实例（仅重复进入的节点才新建） |

### 1.4 实现期发现并收敛的两项合同表述

1. **`INITIATOR_MANAGER` 参与人类型不可用** —— 本仓库 `users` 表没有部门归属，

   白名单收窄为 `ROLE` / `USER` / `INITIATOR` / `FIELD_USER`。

## 5. Attachment 子系统（PL-10，Design §32.6）

**授权来源**：业务所有者 2026-11-14 裁定「按序把四个子系统全部建完」。

- **模块** `server/modules/platform-attachments.js` —— 附件能力的唯一 owner。
- **内容不入库**：数据库只存元数据与内容寻址的存储键；文件落附件目录。
  同一内容可挂多个单据而只存一份文件。
- **上传**：`multipart/form-data`（新增 `readMultipart`，独立上限默认 10 MB）+ base64 JSON 两条路径；
  `readJson` 行为一字未改。
- **下载**走鉴权后的 API，附件目录不在静态服务范围内；固定 `Content-Disposition` 下载，不内联执行。
- **类型安全**：content type 与扩展名**双重**白名单；文件名净化；落盘键由服务端按内容摘要生成。
- **权限**：`ATTACHMENTS_UPLOAD` / `ATTACHMENTS_DELETE` 为平台级；**读取权限继承归属对象**
  （`ATTACHMENTS_VIEW` 是平台级查看权）。这是本单元的**设计修正** —— 若沿用"下载必须有
  `ATTACHMENTS_VIEW`"，新权限码只在 ADMIN 手上，附件能力对普通用户等于不可用。
- **挂载点** 7 个，按各自的**既有查看权限**判定。
- **派生计数**：`accounting_vouchers.attachment_count`（既有孤儿列）成为派生值。
- **测试** `server/platform-attachments.test.js`（13 例，已登记 FAST/FULL）。

### 实现期踩到的三个坑

1. `Content-Disposition` 里的**中文文件名**会让 Node 抛 `ERR_INVALID_CHAR`（HTTP 头只允许 latin1），
   表现为 500。改为 ASCII 回退名 + RFC 5987 的 `filename*=UTF-8''` 百分号编码。
2. 类型白名单若在 `readMultipart` 与附件模块里各判一次，拒绝码会来自两个地方 —— 判定必须唯一。
3. 派生计数的测试若断言"初始为 0"，会被前面用例的上传污染 —— 改为相对断言（+1 / 回到原值）。

## 6. Notification 子系统（PL-11，Design §32.7）

**授权来源**：业务所有者 2026-11-14 裁定「按序把四个子系统全部建完」。

  `unreadCount` 恒为 0。现在六类生产者全部接线：通用工作流引擎 3 类、既有 6 审批族的待办与结果、
  信用特批待决与裁定、库存月结阻塞项。
- **路由** 5 条；**接收人** `USER` / `ROLE` / `SUBSCRIBERS`；**去重**按 `user_id` + `dedupe_key`。
- **读取一致性**：列表与未读计数同源同条件（此前列表 `LIMIT 50` 而计数取全表，二者可互相矛盾）。
- **权限**：读接口改用 `NOTIFICATION_VIEW`（不再用 `DASHBOARD_VIEW`），前端路由登记表同步。
- **测试** `server/platform-notifications.test.js`（11 例，已登记 FAST/FULL）。

### 实现期踩到的四个坑

1. **`notifications` 缺 `event_type` 列** —— 消费侧无法区分「待办 / 结果 / 阻塞 / 知会」，
   只能靠解析标题（标题含单号会变）。已补列。
2. **通知自带事务会击穿既有域的断言** —— 销售订单提交的既有契约按 `BEGIN` 次数断言
   "第二次外层尝试只在重新发现之后开启"；通知在业务事务之后多开一次 BEGIN 就让它红了
   （3 !== 2）。改为**自提交**：通知本就是尽力而为的副作用，多接收人之间不具备原子性是可接受的。
3. **事务内的局部变量在事务外不可见** —— `check` / `row` / `approvalId` 都在事务回调内声明，
   事务外引用会抛 `ReferenceError`（表现为 500）。必须在事务外**重新读取**。
4. **行尾不一致会让补丁失配** —— `sales-orders.js` / `planning-documents.js` 是 CRLF，
   其余是 LF；补丁脚本必须按文件的主导行尾转换模式，并在写回后归一。

### 阶段 III 单元 2：`PL-RI-02` SQLite migration fail-closed（`PL_RI_02_IMPLEMENTED`）

#### scope

- 新增 `server/migrations/migration-runner.js`：schema inspection 原语 + fail-closed 步骤执行器。
- 改 `server/db.js`：加列块、`production_orders` CHECK、`accounting_vouchers` 工作流、`inventory_transfers` CHECK、`migrateWarehouseLogistics`、`lateProcurementColumns`、`migrateProductionDocuments` 全部迁入 runner；初始化失败释放句柄。

#### changes

1. **预期幂等改由 schema inspection 判定**：`tableExists` / `tableColumns` / `columnExists` / `indexExists` / `tableSql` / `rowCount` / `addColumnIfMissing`；不再用「catch 住重复列错误」表达幂等。
2. **fail-closed 执行器 `runMigrationStep({ id, inspect, apply, verify })`**：`inspect` 判定目标形态已满足才记 replay 成功；`apply` 在事务 / savepoint 内执行，失败整体回滚；`verify` 在提交前证明列、约束、索引与行数不变量，失败与 DDL 失败等价；未知错误带 migration 标识与脱敏诊断向上传播。
3. **表重建原子化**：临时表名每次唯一（不再复用固定 `_new` 名）；create → copy → drop → rename 在同一事务内；失败不留 `_new` 残留表或半复制数据。
4. **外键处理**：按 SQLite 官方「create → copy → drop → rename」流程，在事务外临时 `PRAGMA foreign_keys = OFF`、结束后恢复；重建前后比较指向该表的外键违规数，确保重建没有引入新的悬空引用。**实测证据**：开着外键时 `DROP TABLE` 会被子表引用拒绝（`defer_foreign_keys` 与 `legacy_alter_table` 都无法绕过），这正是旧实现静默跳过重建的根因。
5. **初始化失败释放句柄**：失败后数据库文件不再被锁死，「修复根因后重启重试」成立。
6. **`inspect` 谓词覆盖本段实际写入的每一列与每一个 CHECK**（首版遗漏 `return_orders.delivery_id` 等列，被 `v13-phase2` 的索引创建当场暴露并修正）。
