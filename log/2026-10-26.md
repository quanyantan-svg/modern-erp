## 追加：Gate B OQC Fixture —— Design（同一连续授权 §4.0）

### 2. Design 决策

**选定 A**：经 canonical 质量控制点写入器 `createQcp()` 安装一个真实、有效、可审计、测试域内的 `SALES_DELIVERY` + `PRODUCT` 作用域豁免控制点（`inspection_required=false`，带 test-only 理由），随后完全依赖既有 canonical 冻结路径 `configureTrackedDraftLines()` → `freezeQualityPolicy()` → `resolveQualityPolicy()`，生产代码零改动。

**驳回 B**：交付后再次调用 `freezeQualityPolicy()` 无效——该函数对 `UNIQUE(source_type, source_item_id)` 幂等，命中既有快照即原样返回而不重新解析（`traceability-quality.js:437-438`）；建单时已冻结 fail-safe 快照 `inspection_required=1`。要让 B 生效必须先删除已冻结快照，即 R03 明令禁止的手工构造策略证据。

**驳回 C**：真实 OQC 检验会使 Credit/Finance 验收套件内嵌第二张验收面（检验单 + 逐行匹配 + PASS 完成），并改变 M-R03/M-R09 实际检验的对象；门禁接受 `PASS` 与 `WAIVED` 两种放行态，有真实控制点与真实理由的豁免无需任何检验即达 `WAIVED`。仅当业务要求这些用例必须真正执行出货检验时 C 才正确，而当前要求不是。

**驳回 D**：Batch A 手工快照行 `qcp_id=NULL`、`qcp_version=NULL`、`waiver_reason='CONCURRENCY_FIXTURE'`，不对应任何控制点、不记录任何解析结果，违反 R02/R03；且因完全绕过策略解析合同，Wave 10 套件将无法发现 `resolveQualityPolicy()` 的回归。

### 3. Design 关键点

- **fixture 落点**：`server/test-utils/wave10-mysql-acceptance-fixture.js` 新增导出 `seedWave10QualityPolicy(db, options)`，与既有 `seedWave10SalesParameters()`（同一 writer 模式）并列；`seedWave10AcceptanceBase()` 增加 `qualityPolicy` 选项（默认 `true`），在 product 与 user 行之后、任何业务单据之前调用。

中间没有任何陈述说明决定该分类的前置条件，导致任何审阅者都无法在不重推整条容量链的前提下
核对期望值与用例意图。新增行把推导**就地显式化**，且是**加性证据**：
若将来已提交敞口变化导致 `available >= 20000`，前置断言会显式失败，而不是静默误分类。
该行**不引入新常量、不引入种子派生真相**：`capacity.available` 仍由
`readAuthoritativeCapacity()` 从有效 Profile 与实际持久化敞口计算，`20000` 是同块中已用两次的 delta 字面量。
断言消息文本保持原文不变。

### 4. 失败根因（只读分析，未改任何代码、夹具、测试、migration 或 schema）

- **现象**：MySQL 侧 `information_schema.CHECK_CONSTRAINTS.CHECK_CLAUSE` 返回的文本把字符串字面量的单引号
  以反斜杠转义，例如 `(decision in (\'pass\',\'warning\',\'block\',\'special_approval_required\'))`；
  SQLite 源侧同一约束为普通引号形式。
- **机制**：`normalizeCheckClause()`（`server/test-utils/wave10-mysql-schema-fixture.js:270-287`）
  在解析失败时降级为 `raw: <原文小写>`。其分词器/解析器无法处理反斜杠转义引号，
  因此**凡含字符串字面量的 CHECK 在 MySQL 侧全部降级为 `raw:`**，而 SQLite 源侧正常归一化，
  两侧文本形态不可比 → `check-constraint parity` 断言失败。
- **纯函数复算证据**（只读，未连接数据库）：
  - `(decision in ('pass','warning',...))` → **PARSED**；
  - `(decision in (\'pass\',\'warning\',...))` → **FALLBACK（`raw:`）**；
  - `(sales_order_id is not null or sales_delivery_id is not null)`（无字面量）→ **PARSED**。
    与观察完全一致：三个失败约束均含字面量，唯一未失败的那条不含字面量。
  - 对 MySQL 渲染结果做去转义后，SQLite 侧与 MySQL 侧归一化结果**逐字相等**
    → 底层约束语义相同，**物理一致性成立，失败出在夹具的文本比对机制**。
- **影响面**：六张 Wave 9 表（`credit_lock_anchors`、`credit_parameters`、`credit_check_rules`、
  `credit_profile`、`credit_policy_snapshots`、`credit_profile_ratings`）与两张 Wave 10 表

### 5. Design（`solution.md` 新增 §37.48）

**选定 A**：在 tokenizer 的字符串字面量分支内加入**受限的、以来源为界定的**转义识别；
新增显式的字面量方言参数（`sql_standard` / `mysql_catalog`），由调用点的 provenance 决定；
新增保留失败原因的可诊断通道；未闭合字面量改为 fail-closed。

**驳回 B**（进入 tokenizer 前的语法感知转义规范化）：要安全地反转义，必须先自行定位字面量区间，
即在第一个分词器前再造一个分词器；两个分词器会漂移，且预处理器无法区分"已转义"与"字面反斜杠"，
无法满足"未知转义必须 fail-closed"，且形态上接近被禁止的"无条件全局反斜杠删除"。

**驳回 C**（解析器层的统一语义模型）：需改动 token 形态、解析器与渲染器，改动面最大，
且把转义规则放进决定**结构**的层而非决定**字面量边界**的层；但其**意图被采纳**——
选定方案对两种表示产出**同一个语义字面量模型**，且方言是显式参数而非隐式猜测。

**Design 关键点**：

- `sql_standard` 方言：仅 `''` 表示字面引号；字面量内的反斜杠**不支持**并 fail-closed
  （两方言对该字节本就分歧，不得默选其一）。
- `mysql_catalog` 方言：字面量的**定界符本身被反斜杠转义**（与 A2 捕获形态一致）；
  内容逐字取用；内容内出现反斜杠即 fail-closed（内容转义约定未观测，猜测会把两个不同字面量合并）。
- 归一化入口保持现有返回类型，新增 `describeCheckClauseNormalization(value, options)` 返回
  `{ form, dialect, canonical, reason }`。
- 比较本身仍是安全网：误解码会产生**不同**的规范形态，`assert.deepEqual` 因此拒绝判定等价。
- `sql_mode` 与来源的关系：`sql_mode` 治理服务端**解析输入 DDL**（规范 DDL 用普通引号 → 与模式无关）；
  未观测的是服务端**重新打印**已存表达式的**渲染约定**；选定方案按 provenance 选方言，
  观测并记录 `@@session.sql_mode` 与 `VERSION()`；若观测到禁用反斜杠转义的模式则以具名诊断 fail-closed。

### 6. Fail-closed 与负向证据

纯函数复算（无数据库）实测：

- `unsupported escape inside string literal`：两方言下字面量内容含反斜杠 → `form=raw`；
- `unterminated string literal`：两方言下未闭合字面量 → `form=raw`；
- `unescaped quote inside string literal`：`mysql_catalog` 内容内出现未转义引号 → `form=raw`；
- `expected )` / `trailing tokens` / `missing operand`：不支持语法、尾随 token、截断表达式 → `form=raw`；
- 空子句 → `form=empty`、`canonical=''`、`reason='empty clause'`。
- 每一种情形都**保留非空原因**，且其规范形态**永不等于**任何已解析形态。
- `raw:` fallback **保留**，未被关闭；`describeCheckClauseNormalization()` 的返回键固定为
  `['canonical','dialect','form','reason']`，原因长度有界（≤120）。

### 5. `M-BIZ-19` `no-rule` 变体必须表达的业务语义

- 引擎语义（`credit-check.js:508-511`/`:666-675`）：规则是**带版本、带日期、带状态**的业务对象，
  引擎在**生效规则**（阶段匹配 + `status='ACTIVE'` + `effective_from<=businessDate` +
  `effective_to` 有效）上选取，再按确认模式过滤；**没有适用的生效规则**时，该阶段**不承载任何信用控制**：
  不强制、判定 `PASS`、原因码 `NO_APPLICABLE_EFFECTIVE_RULE`、**不产生任何证据**。
- 因此 `no-rule` 变体必须表达的**业务事实**是：**"在这个阶段、在这个业务日，没有适用的生效信用规则"**，
  且必须通过**规则集的状态**来表达，而不是通过"规则行不存在"来表达。
- 现行做法的两个独立问题：(a) 它**在数据库层就不成立**——被 Profile 引用的规则行不可删除；
  (b) 即使可以，删除规则行表达的是"此规则从未存在"，而不是"此阶段当前没有生效规则"——
  两者是不同的业务事实。
- Requirement 因此要求：保留引用完整性（不得删除/孤立/改指被引用的行）、保留规则事实的真实性与可审计性、
  保留三条互不相同的"未强制"路径（**开关关闭** / **无适用生效规则** / **规则生效但不匹配确认模式**）
  在 fixture 状态与用例命名上可区分，并保留该用例的可观测合同（不强制、`PASS`、持久化投影逐字不变）。
