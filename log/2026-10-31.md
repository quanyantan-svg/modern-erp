- **矛盾**：R1 的单式恒等式把**物理消耗**、**物权转移**、**商业释放**压进同一个词，导致两类**重复扣减**：`ownerChanged` 被当作物理流出（`closing_qty` 少扣一次）、`commercialReleased` 被当作物理流出（再少扣一次）。

- **数值例子**：共同场景 VMI 收货 100（全部 SUPPLIER 所有）。D-1（先转移后消耗）100/50 → supplierOnHand 0、enterpriseOnHand 50、ownerChanged 100、closing 50；D-2a（消耗直接扣 SUPPLIER，单腿）30 → supplierOnHand 70、supplierConsumedDirect 30、released 30、closing 70；**D-2b（先 Owner Change 再实际消耗）必须显式第二条真实物理 OUT**：同一 `movement_group_id` 内三腿 SUPPLIER OUT 30 → ENTERPRISE IN 30 → **ENTERPRISE OUT 30**，同事务、无可见中间态，只写两腿会使物理总量凭空 +30 破坏 VMI-P；D-3（消耗与结算分离）30 消耗 + 20 转移 → closing 70，released 50 中 30 为**无实物转移**的释放，须由 `released_qty` 承载。四例逐例满足 VMI-P/S/E/C。
- **D-P01 仍未批准**：不得自动选择 D-2（含 D-2a/D-2b）；设计给出推荐 D-2a 及理由。
- 落地：§26.33.4.4、§26.33.7（M-09）、§26.33.10.1（INV-4）、§26.33.10.5。

### C-04 GL 防绕过（`M1-D-30`）

- **独立核对 `commercial-golive.js::postSupplierBill` 三个分支**：
  - **DIRECT**（`finance-recognition.js:258-267`）：只链接既有 FINAL open item，**不创建凭证**；`postSupplierBill` 的 `:315` 条件跳过 `createSystemVoucher`。更严重的是 `commercialReconciliation` 的 WHERE（`:650`）`COALESCE(recognition_mode,'INVOICE_DRIVEN_OPEN_ITEM') <> 'DIRECT_BUSINESS_OPEN_ITEM'` 会把 DIRECT 行**整行排除** → 该账单对 `SUPPLIER_BILL_TO_SUBLEDGER_GL` 的 BLOCKING 检查**不可见** = 静默 GL 绕过。
  - **INVOICE_DRIVEN**（`:270-275`）与 **PROVISIONAL**（`:277-292`）：都到达 `:315`，用**普通采购角色集** `GRNI` / `INPUT_TAX_RECEIVABLE` / `PURCHASE_PRICE_VARIANCE` / `ACCOUNTS_PAYABLE`（`:316-319`）生成分录 → 违反 M1-D-16 与 C-REQ-03。
- **模式解析**：`resolveRecognitionPolicy`（`finance-recognition-policy.js:23-63`）的遗留单据分支只覆盖 `SALES_DELIVERY` / `PURCHASE_RECEIPT`，委外来源落到**兜底 DIRECT**（`:61-62`）；而 `ensureSubledger`（`settlement-core.js:74-93`）不写 `item_kind`，该列默认 `'FINAL'`（`v22-finance-wave-a-foundation.js:206-207`）→ DIRECT 分支的现实可达性成立。
- **裁定**：**不得**把"新会计科目角色不存在"当作唯一保护；建立 **source-aware 委外加工费会计政策门禁** `assertOutsourcingAccountingPolicy`，在**任何** Finance 写入之前拦截；委外过账**不得**复用 `postSupplierBill`。允许：来源校验、期间/业务日门禁、账单创建、预留量、容量锁、输入校验、幂等、审计。禁止：复用 `postSupplierBill` 任一分支、选择任何确认模式、生成任何凭证/分录、用普通采购角色集、让 `recognition_mode` 取 DIRECT。新增 `outsourcing_accounting_policies` 登记表（**默认无行**，天然 fail-closed；只由 C-P01..C-P04 获批后的受控授权写入）。
- **诚实表述**：裁定前**委外加工费账单只能创建（DRAFT）并占用预留量，不能过账**；过账显式失败 409 `OUTSOURCING_GL_POLICY_NOT_APPROVED`，账单保持 DRAFT，零 AP open item / 零凭证 / 零分录。`closureState` 补第三态 `NOT_POSTED`。

- 落地：§26.33.4.3、§26.33.6.3、§26.33.7（M-16）、§26.33.10.4（GL-3..GL-5）、§26.33.11。

### C-05 幂等键与重复合法业务（`M1-D-31`）

- **矛盾**：物理腿 Mutation Key `<ACTION>:<orderId>:<materialListId>:<legSeq>` **不含独立业务事件 ID** → 同一订单同一物料行的第二次合法发料算出**同一个** Key → 命中 `inventory_mutation_log` 后因非 Consignment 路径**不比对请求内容**（`inventory-mutation.js:256-261`）→ **第二次发料被静默丢弃**。
- **裁定**：建立业务事件 ID 体系 —— 服务端生成稳定的 `business_event_id`；`source_id` = 业务事件 ID（非订单 ID）、`source_item_id` = 业务行 ID、`movement_group_id` 每事件一个、物理腿 Mutation Key = `<SOURCE_TYPE>:<business_event_id>:<legSeq>`（MOVE 为 `OUT`/`IN`，单腿为 `0`）。同键异请求 → canonical `idempotencyReplay` 的 fingerprint 不匹配 → 409；不同键的合法新事件 → 不同业务事件 ID → 不复用旧 Mutation；重放时整条业务动作为 no-op。
- 落地：§26.33.4.7.2、§26.33.8、§26.33.1（`M1-D-31`）。

### C-06 严格估值与防重（`M1-D-32`）

- **严格估值**：`issueValue` 在可估值余额行不存在且产品未激活时**静默**返回 `writeLegacyMovement`（`financial-inventory.js:95,:110`，`status='LEGACY_UNVALUED'`、金额 0）。委外路径必须断言返回 Movement `status='POSTED'` 且 `inventory_transactions.valuation_status='VALUED'`，否则 **409 并整体回滚**；`receiveValue` 同理不得传 `valuationBasis='LEGACY_UNVALUED'`。新增 `VAL-10` / `VAL-11`。
- **防重等价性**：`uq_tracked_post`（`v13-phase6b-traceability-quality.js:112`）在**两端不等价** —— SQLite 的 UNIQUE 索引中任一索引列为 NULL 即互异，而 `lot_id`/`serial_id` 恒有一列为 NULL → SQLite 上**实际不提供任何去重**；MySQL 走 `generatedPartialIndex`（`mysql-schema.js:138-160`，`useDigest` 判定 `:445-447`）把 NULL `COALESCE` 成 `CHAR(30)` 取 SHA2 → 重复被拒绝。故 R1 "双端严格身份占用" 的结论不成立。
- **裁定**：新增 `tracked_inventory_movements.identity_key TEXT NOT NULL DEFAULT ''`（`LOT:<id>` / `SERIAL:<id>` / `NONE`，**仅委外写者填充**）+ 部分 UNIQUE 索引（限六个委外来源，`reversed=0`）—— 5 列全 NOT NULL，SQLite 部分索引与 MySQL 摘要生成列**语义等价**；历史行按 `lot_id`/`serial_id` 确定性回填，不改写其他列。旧 `uq_tracked_post` 保留不动。**有效唯一性** = (source_type, source_id, source_item_id, identity_key, direction)，`source_id` 为业务事件 ID。Mutation Key（防重放）与身份唯一性（防重复过账）是**两层不同保障**。
- 落地：§26.33.4.6.1、§26.33.7（M-15）、§26.33.10.2（VAL-10..VAL-12）。

### C-07 加工费预留量定义（`M1-D-33`）

- **矛盾**：R1 的 `AP-1` 写"账单行的 base_quantity 之和 ≤ 该收货行的可计费量（eligible = 行数量 − 已归属退货 − 已预留）"，把 **GrossEligible** 与 **RemainingEligible** 混为一谈 → 同一笔预留被扣两次。
- **裁定**：三段式 —— `GrossEligible = 收货行数量 − 有效退货量`；`ReservedOthers = 其他有效账单（DRAFT/WAITING_MATCH/POSTED）的 base_quantity`；`RemainingEligible = GrossEligible − ReservedOthers`；新行必须 `newQuantity <= RemainingEligible`。累计口径与 `GrossEligible` 比较，**两者不得交叉使用**。预留键统一到 canonical `commercial_source_type='OUTSOURCING_RECEIPT_ITEM' + commercial_source_item_id`（现状用 `source_outsourcing_receipt_item_id` 键，经 canonical 路径创建的账单不被计入预留）。
- 落地：§26.33.10.3（AP-1..AP-8）、§26.33.12（`M1-GC01`）。

### C-08 历史 CONFIRMED 收货兼容（`M1-D-34`）

- **矛盾**：R1 的"既有 `'CONFIRMED'` 行在读取时被映射为 `'EFFECTED'`"不成立 —— `createOutsourcingReceipt`（`outsourcing.js:344-359`）在**创建**时即写 `'CONFIRMED'`，只有 `confirmOutsourcingReceipt`（`outsourcing-finance.js:76-150`）才改为 `'EFFECTED'` 并写库存与成本；历史库中**同时存在**两类 `'CONFIRMED'` 行。
- **裁定**：**不得**无条件映射。判定依据四类可核查证据 —— `inventory_transactions`（`source_type='OUTSOURCING_RECEIPT'`）、`inventory_valuation_movements`、canonical 质量判定 `deriveQualityState(db,'IQC',receiptId,'OUTSOURCING_RECEIPT')` ∈ {PASS, WAIVED}、`outsourcing_receipt_items`（来源明细）；`outsourcing_cost_evidences` 仅作旁证。分类为 `EFFECTED_CONFIRMED` 或 `LEGACY_UNVERIFIED`（附 `unverifiedReason`）。`LEGACY_UNVERIFIED` **不开放**新的账单与退货能力（先判后写，409 `OUTSOURCING_RECEIPT_NOT_EFFECTED`），**不改写**历史记录；历史修复属**独立授权**，不在 M1 范围。
- 落地：§26.33.5.1、§26.33.7（读时派生说明）、§26.33.11。

### C-09 RBAC 与职责分离（`M1-D-35`）
