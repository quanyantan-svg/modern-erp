### 5. 本轮新发现（4 项，均为**既有**产品行为，非本轮修复引入）

#### F-01（BLOCKING）应付清单把已转销的暂估项仍显示为未付

暂估应付（`PURCHASE_RECEIPT` / `PROVISIONAL`）结转成供应商账单（`SUPPLIER_BILL` / `FINAL`）后，
`conversion_state` 置 `CONVERTED`（`server/modules/finance-provisional-conversion.js:16`），
**但不把该行 `open_amount_cents` 清零**。而 `listPayables`
（`server/modules/settlement.js:99-112`）不区分 `item_kind` / `conversion_state`，
逐行与汇总都按 `open_amount_cents` 暴露。

实测（干净库、本轮真实数据）：

- 已结清的最终应付行：`status=SETTLED`、`outstandingCents=0`（正确）；
- 已转销的暂估行：`status=OPEN`、**`outstandingCents=450000`**；
- 清单汇总 `summary.balanceCents=550000`，权威口径（`AP_TO_GL` 校验与付款核销守卫只认
  `FINAL + OPEN`）为 **0** → **汇总高估 550000 分（5,500 元）**；
- 对该行发起付款：**付款单创建成功 201**，**确认被 409 拒绝**「待核销项目已结清、非最终项目或非权威来源」
  → 客户侧留下一张挂着的 DRAFT 付款单。

权威口径（`AP_TO_GL`）与读模型口径不一致，是这个缺陷的根因表述。

#### F-02（BLOCKING）期初库存单没有成本字段 → 永久阻断权威结账，并连带阻断委外发料

期初单 API（`server/modules/inventory-opening.js:56-97`）与 UI（`src/pages/inventory-work.jsx:2133`
`InventoryOpeningEditor`，只收 货品 / 仓库 / 数量）**都没有成本字段**；期初确认只调
`applyInventoryMutation`，不写估值。于是期初库存恒为 `LEGACY_UNVALUED`
（`inventory_transactions.valuation_status` 默认值），触发两项 BLOCKING 检查：

- `LEGACY_UNVALUED_MOVEMENTS` = **17**（FAIL）
- `INVENTORY_QUANTITY_VS_VALUATION` = **1691**（FAIL）

**连带效应（制造场景更致命）**：跟踪物料的期初批次**没有身份级估值池**，
委外发料被估值闸门 409 拒绝（`OUTSOURCING_VALUATION_UNVERIFIED`「委外物料缺少权威估值余额」），
委外收货 / 完工 / 加工费过账随之级联失败。**即：批次料一旦从期初进来就走不通委外。**

UI 侧还有一个独立缺口：期初单编辑器**没有批次 / 序列号字段**（API 层 `item.lotId` / `item.serialId`
是支持的，`server/modules/inventory-opening.js:92`），所以从**界面**导入跟踪物料期初必然产生无身份仓位
→ `TRACKED_DIMENSION_VS_CANONICAL` BLOCKING FAIL（本轮用**带身份的 API 期初单**后该检查 **PASS**，
证明 canonical 期初路径本身在跟踪维度上是正确的）。

#### F-03（BLOCKING）委外加工界面无法完成跟踪物料的收货

服务端要求跟踪身份，但界面不提供，三个位置同时缺失：

| 界面位置 | 实际请求 | 服务端要求 |
|---|---|---|
| 委外发料 `src/pages/outsourcing.jsx:519-530` | body 只有 `materialListId` / `quantity` / `idempotencyKey` | LOT 物料必须带 `lotId`（`server/modules/outsourcing-inventory.js:22`） |
| 委外收货「生效」`src/pages/outsourcing.jsx:1021-1023` | `body: {}` | 必须带 `materialIdentities`（`server/modules/outsourcing-finance.js:240`，`:341` 用它做倒冲身份） |
| 委外收货单创建 `src/pages/outsourcing.jsx:998-1005` | item 无 `serialId` / `lotId` | 服务端**允许**（`server/modules/outsourcing.js:1199`） |

客户侧表现：批次物料点「发料」→ 409「LOT 物料必须提供唯一批次身份」；
点「收货生效」→ 同一 409；序列号成品连收货单都建不出带身份的明细。
**API 层是通的**（本轮用 `materialIdentities` + `serialId` 一次跑通 28/28），
**断的是界面**。

#### F-04（BLOCKING）批次身份列表的「当前数量」被移动笔数放大

`GET /api/tracking/identities`（`server/modules/traceability-quality.js:606-613`）把
`inventory_lot_balances` 与 `tracked_inventory_movements` **同时 JOIN 到同一批次且二者无任何关联**，
形成笛卡尔积，`SUM(b.quantity)` 被放大为「真实数量 × 该批次移动笔数」。

实测对照（同一批次的真实数量 vs 端点返回值）：

| 批次 | 真实数量 | 移动笔数 | 端点 `currentQuantity` |
|---|---|---|---|
| `AC2-TE2E-1794965288244` | 20 | 1 | 20（仅因只移动过一次才正确） |
| `AC2-TE2E-1794965309662` | 20 | 3 | **60** |
| `AC2-TE2E-1794965520804` | 17 | 4 | **68** |

库内 canonical 仓位与跟踪投影**逐批次完全一致**（17+3、20、500），所以错的是**读模型**，不是数据。
同源的批次主档列表（`listLots`，同文件 `:646`，Requirement §32.14 `IW-TRACE-01/06`）**是正确的**，
两个列表页因此互相矛盾。引入时间 `b85a445`（2026-09-27）—— **既有缺陷，与上一轮的 D4 改动无关**。
