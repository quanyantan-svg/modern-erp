### 2. 续轮实测发现并修复的真实缺陷

#### 2.1 M2 的 Profile key 硬编码了一个随日历漂移的日期（真实缺陷，本轮修复）

`server/mysql-sales-customer-wave11-a-credit-query.integration.js` 的 M2 以字面量
`cus-w11-self:sp-self:2026-08-28` 选择 Sub-Limit scope。但共享 Fixture 的 `PROFILE_FROM` 是
**相对当前日历日推导**的（`HISTORICAL = TODAY-30d`，`PROFILE_FROM = HISTORICAL-30d`），Fixture
自身注释也明确要求"每个 fixture 日期都从服务器当前日历日推导，永不静默过期"。因此该字面量只在
Design 撰写当天（2026-10-28）成立：2026-10-29 的真实 key 为 `cus-w11-self:sp-self:2026-08-29`，
M2 的 `find()` 返回 `undefined`，断言以 `Cannot read properties of undefined (reading 'usedCents')`
失败。该缺陷自上一轮 M2 修正引入后从未被任何执行验证过。

修正：改为从 Fixture 自身导出的 `PROFILE_FROM` 常量派生精确完整 key
（`SELF_SUB_LIMIT_PROFILE_KEY` / `OTHER_SUB_LIMIT_PROFILE_KEY`），并对两个 scope 各加一条
"必须存在"断言。选择语义仍是精确匹配，不回退为"第一条 SALESPERSON_SUB_LIMIT"。

#### 2.2 M9 的稳定投影维度少于批准 Design（真实偏差，本轮补齐）

批准 Design `solution.md §37.54.20.19.8` 要求跨引擎内容比较使用"至少 sourceOrderId +
scopeType + stage + businessDate + **stable Profile key** + **proposedDelta** + **decision**"的稳定
投影。上一轮实现只用了前四维，且把"sourceOrderId:scopeType"式的压缩键同时用于跨引擎比较与唯一性
断言。

修正：`normalizeHistory()` 的投影键补齐到七维，Profile key 取自
`credit_profile` 的稳定业务键 `customer_id:salesperson_scope_key:effective_from`（per-engine UUID
不可跨引擎识别），proposedDelta 由持久化 `recordedBreakdown` 的
`proposedTotalCents - exposureCents` 推导。`Set` 仍只用于显式唯一性断言，未用于产出去重后的
比较数据；单引擎页间重叠仍直接比较真实 `checkResultId`。M2 collector 的 amount evidence 亦补齐
`profileKey`（`zero` 与 `historical` 两个投影此前丢失该字段）。

#### 2.3 T5 冻结指纹链对行尾不稳定，且历史摘要自证（真实脆弱性，本轮修复）

- 上一轮 T5 的三条历史摘要断言是 `assert.equal(CONST, '字面量')`，即常量与自身比较，不构成证据。
  已改为断言六个冻结链节点**两两不同**，即"历史证明与新版证明不得混为同一个 SHA"。
- `core.autocrlf=true` 会在 checkout 时把工作树改写为 CRLF，而 Git 以 LF 存储 blob；原 T5 直接
  对工作树字节取摘要，一次 checkout 即可让冻结断言失效。已改为对 **LF 归一化**字节取摘要，使冻结
  常量等于将要提交的 Git blob 摘要，证据链可对仓库对象复核而不只对某一次 checkout 复核。

#### 2.4 新增 T10：M4 跨引擎修复的无 MySQL 可执行证明

新增 `T10 the V2 identity chain is independent of the physical JSON rendering the engine stores`：
同一 Writer 输出在 SQLite 为紧凑 JSON TEXT、在 MySQL native JSON 为带空格规范渲染。断言 V1 rule
hash 与 V1 CSP1 **必须不同**（复现 M4 分叉），而 V2 rule hash、CSP2 fingerprint 与 CCHK2 group
identity **必须完全相同**。该用例在无 MySQL 连接的条件下证明 M4 修复成立。

### 2. 复核结论：矛盾成立，且根因是一处双键缺陷

已确认的矛盾：**同一 Credit Check Group 的连续两次 exact replay 均返回 `PASS` 且 `consumedSpecialApprovalId`
相同，而 `audit_logs` 中 CONSUME 行数始终为 0。**

根因不在"是否走了 replay 路径"，而在**同一段代码使用了两个互不相干的键**：

```text
findConsumableApproval()  键 = 该审批是否已有 CONSUME 审计行  → 决定"这张审批还能不能用"
消费段 if (!isReplay)     键 = 该 Check Group 是否是 replay     → 决定"要不要写 CONSUME 审计行"
决定翻转为 PASS                                        → 与 isReplay 无关，始终发生
```

当"审批尚无 CONSUME 审计行"与"本次是 replay"同时成立，就产生 **PASS + 审批 ID + 0 条消费证据**。
由于"已消费"的唯一判据就是那张不存在的审计行，该审批**永远**被判为未消费。

本轮在既有 Wave 10 Golden 中找到该行为的**机器可复核证据**：
`server/sales-customer-wave10-credit-check.test.js` 的
`"V2 approval isolation — CSP1 approval releases only exact V1 replay and never a changed CCHK2"`
断言 `replay.decision === 'PASS'` 与 `replay.consumedSpecialApprovalId === approval.id`，
**且从不断言 CONSUME 审计行数**——该用例在当前基线下通过。这同时构成验收缺口证明：
**没有任何既有断言覆盖"replay 路径的消费证据"**。

### 3. 本轮新增的两项认定（上一条记录未覆盖）

- **C-3（反向矛盾）**：当首次消费落在**非 replay**（新建 Group）路径时，落盘 Result 行为 `PASS`；
  此后同一 Group 的合法幂等 replay 会重新执行"已消费"判定并把决定退回 `SPECIAL_APPROVAL_REQUIRED`
  （CCHK2 路径），或在 CCHK1 路径因落盘决定与重算决定不等而直接 409
  `CREDIT_CHECK_LEGACY_REPLAY_AMBIGUOUS`。**同一根因同时产生"放行两次"与"合法重放被拒"两个方向的错误。**
- **C-4（落盘明细串值）**：`consumedSpecialApprovalId` 是 Scope 循环外的单一变量；范围 A 被释放而范围 B
  未被释放时，B 的落盘明细残留 A 的审批 ID，使"哪张审批释放了本范围"成为假命题。

### 4. 关键结构事实（实测，非推测）

- `credit_special_approval` **无任何消费状态列**；`credit_check_results` **无 `special_approval_id` 列**；
  释放关联只存在于 `component_breakdown_json.consumedSpecialApprovalId`。
- `audit_logs` **无** `(entity_type, entity_id, action)` 唯一约束，只有 `idx_audit_entity` 普通索引。
- 消费身份在既有 CONSUME 审计 detail 中**已经**是 `(check_group_id, scope_type)`；本轮只是把它提升为
  一等被持久化、被唯一约束保护的事实。
- 审批查找**不按 Check Group 绑定**；`source_sales_order_id IS NULL`（出库范围审批）时对任意同范围同快照
  的检查都成立——这是"跨动作重复消费"的最强路径。
- MySQL 事务在 `transaction()` 起始处即取全局事务闸门 `mysql_transaction_gates ... FOR UPDATE` 并持有至
  COMMIT/ROLLBACK；SQLite 使用 `BEGIN IMMEDIATE`。因此当前部署形态下事务不会交错；但设计**不依赖**该全局
  串行化，另设局部保证（审批行 `FOR UPDATE` + 账本 UNIQUE 约束）。
- MySQL 默认 REPEATABLE READ 下，普通 `SELECT` 读事务快照，可能看不见并发已提交的消费行；因此消费结论的
  读回必须是当前读（锁定读）。

### 2. 精确根因（隔离 SQLite 复现，非推测）

E3 套件把**两个各自正确、互相独立**的 Fixture 世界放进**同一个** MySQL 数据库，而两个生产解析器把
这些事实当作**全局**事实。四个缺陷（后两个是被第一个遮蔽的潜伏缺陷）：

| # | 缺陷 | 证据 |
|---|---|---|
| C-1 | 两个 ACTIVE 的 `CREDIT_MANAGEMENT_ENABLED` 版本窗口重叠：`param-CREDIT_MANAGEMENT_ENABLED`（自 PROFILE_FROM）与 `w10-race-enabled`（自 2026-01-01），均 `effective_to=NULL` | `readEffectiveParameter`（`credit-check.js:90-95`）在业务日期上遇到 >1 个有效 ACTIVE 版本即抛 `CREDIT_EFFECTIVE_VERSION_AMBIGUOUS`；隔离复现实测 `effective CREDIT_MANAGEMENT_ENABLED versions at 2026-10-29: 2` |
| C-2 | 阶段 SO_APPROVE 上同时存在共享世界的 `W11_A_SO_APPROVE`（BLOCK/BLOCK）与 T-17 的 `W10_RACE_RULE`（OVERRIDE_REQUEST/WARNING） | `effectiveRuleRows` 收集阶段全部有效规则、`strongestOutcome` 取最强 → 结论为 **BLOCK**；隔离复现实测 `decision=BLOCK`。**修复 C-1 后 T-17 仍会失败** |
| C-3 | T-17 用 `WHERE decision='SPECIAL_APPROVAL_REQUIRED' ORDER BY id LIMIT 1` 取来源行，而共享世界**本身就有 8 条**该结论的结果 → 会取到共享世界的行，审批绑错快照 | `seedWorld` 的 `runCheck`（limit 100000 / delta 200000）必然超限 |
| C-4 | T-17 用同一个 actor（`ADMIN`）申请并审批特别审批 | 生产 SOD（§36.6.6，`credit-special-approval.js:255-261`）抛 `CREDIT_SPECIAL_APPROVAL_SOD`；隔离复现实测 |
