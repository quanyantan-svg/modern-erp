**Goal**

**Root Cause**

复现路径(临时脚本 `scripts/_test_trial_balance.mjs`,已删除):会计 → 新建 SMOKE-E01 / SMOKE-E02 → 提交 → admin 审核 → 过账 → 查询 `/api/reports/trial-balance?period=2026-09` → 返回 `trialBalance: []`(完全空)。同期 Income Statement 返回 `revenue=1000000 / expense=400000 / profit=600000`,Balance Sheet 返回 `equationValid=true`。两个独立的 bug 在 trial balance 内叠加:

1. **Subject filter 排除了所有 seed 科目**。`server/app.js:1817` 的 `getTrialBalance` 用 `SELECT … FROM accounting_subjects WHERE active = 1 AND parent_id IS NOT NULL`,而 `server/db.js:1139-1148` 的 seed 把 7 个科目(`1001 / 1002 / 1122 / 1405 / 2202 / 6001 / 6401`)全部不设置 `parent_id`(`parent_id = NULL`)。`parent_id IS NOT NULL` 把所有种子行都过滤掉,subjects 数组为空,整个 trial balance 当然空。同期 Income Statement / Balance Sheet **不**过滤 `parent_id`,所以它们显示正确。
2. **`endDate` 在 UTC+8 off-by-one**。原代码 `endDate = new Date(y, m, 0).toISOString().slice(0, 10)` —— 在本地时区构造上月最后一天 00:00,然后 `.toISOString()` 转为 UTC。生产 Tencent Cloud 是 UTC+8,`2026-09-30 00:00 +08:00` = `2026-09-29T16:00Z`,`.slice(0,10) = '2026-09-29'`。月底(30 / 31 / 28 / 29)的凭证静默被排除。同期 Income Statement / Balance Sheet 的日期算术用 `new Date(year, month, 0).getDate()` 在本地时区直接取出 `lastDay` 数值再字符串拼接,**不**经过 `.toISOString()`,所以它们正确。

## Phase E — Hotfix: Trial Balance Closing-Balance Direction Aggregation (v0.9.8 → v0.9.9 candidate)

**Goal**

修复 `8ae1d8f` 之后用户在腾讯云生产环境确认的最后一个 trial balance blocker:期间 `2026-09` 各 subject 行数据已正确(1001 ¥6,000 debit、6001 ¥10,000 credit、6401 ¥4,000 debit;本期发生额借 ¥14,000 / 贷 ¥14,000 balanced),但页脚 `期末余额` 显示 `借 ¥20,000.00 / 贷 ¥0.00`,正确应为 `借 ¥10,000.00 / 贷 ¥10,000.00`。严格 scope:不动 schema、不改 reporting 公式、不改 voucher state machine、不改其他报表、不改 period closing。

**Root Cause**

复合缺陷 —— `getTrialBalance` 后端返回的 `closingBalance` 是「按 subject type 的 normal direction 签名」(`ASSET/EXPENSE: 期初 + 借方 - 贷方`;`其他: 期初 + 贷方 - 借方`),**符号约定与 subject normal side 绑定**,不是统一的 debit/credit 签名。前端用 sign-based heuristic 把 `Math.max(closingBalance, 0)` 归入借方合计、`Math.max(-closingBalance, 0)` 归入贷方合计 —— 这个启发式**假设正数永远等于借方**,对 credit-normal 科目(LIABILITY/EQUITY/REVENUE)而言其正 closing 余额其实是 CREDIT 侧,被前端错误归入借方。

具体生产数据:
- 1001 ASSET/DEBIT-normal:closing = +¥6,000 → DEBIT ✓(启发式碰巧正确)
- 6001 REVENUE/CREDIT-normal:closing = +¥10,000 → CREDIT,但前端归入 DEBIT ✗
- 6401 EXPENSE/DEBIT-normal:closing = +¥4,000 → DEBIT ✓(启发式碰巧正确)
- 前端 totalClosingDebit = 6000 + 10000 + 4000 = ¥20,000(错的,把 6001 也算进来)
- 前端 totalClosingCredit = ¥0(错的,6001 应在此)

Opening balance 也有同样的潜在缺陷:`opening SQL = SUM(DEBIT) - SUM(CREDIT)` 统一签名,正数对应 net debit 活动,负数对应 net credit 活动 —— 当前生产 `opening` 全 0,启发式碰巧工作,但对有前期余额的科目会同样错。

**Fix**

1. **后端增加 canonical balance-direction helper**(`server/modules/extended.js`):
   - 新增 `classifyBalanceDirection(balance, subjectType, opening)` —— 纯函数:
     - `opening=true`:opening 符号直接代表借贷方向(`balance > 0 → DEBIT`、`balance < 0 → CREDIT`),与 subject type 无关。
     - `opening=false`:按科目 normal direction 解读 —— `ASSET/EXPENSE` 正 → DEBIT,负 → CREDIT(contra);`LIABILITY/EQUITY/REVENUE` 正 → CREDIT,负 → DEBIT(contra)。
     - `balance === 0` 返回 `null`(不计入任一侧合计,避免污染 footer)。
   - `getTrialBalance` 每行响应增加 `openingDirection` / `closingDirection` 字段,从 `classifyBalanceDirection` 派生,response shape `+2 / -0` 字段。
   - 现有 `openingBalance` / `closingBalance` 数值字段保留(向后兼容 + UI 行内渲染用绝对值 + 方向 prefix)。
2. **前端 direction-aware 聚合**(`src/pages/accounting.jsx`):
   - 删除 `Math.max(Number(r.openingBalance || 0), 0)` / `Math.max(-Number(r.openingBalance || 0), 0)` / `Math.max(Number(r.closingBalance || 0), 0)` / `Math.max(-Number(r.closingBalance || 0), 0)` 四处 sign-heuristic。
   - 新增 `sumByDirection(balanceField, directionField, side)` helper —— 按后端 direction 字段归类,使用 `Math.abs(balance)`(避免重复显示负号)。
   - 行内 opening/closing 单元格:用 `r.openingDirection` / `r.closingDirection` 渲染 `借 ` / `贷 ` prefix + `Math.abs(value)`,className 用 `'positive' / 'negative'`(替代 sign-based `'positive' / 'negative'`)。
   - Period debit / credit 合计不变(本来就是 gross movement,无需 direction)。
3. **未变更**(严格 scope 保护):
   - Income Statement / Balance Sheet / Financial Summary 公式;
   - voucher amount unit logic(`d9079f0`);
   - manual voucher UI + VoucherModal + VoucherDetail(`314a11d`);
   - VOUCHER_SUBMIT / VOUCHER_APPROVE / voucher state machine / period closing;
   - schema(`period` 列已存在;不动);
   - `resolvePeriodRange()` / `parent_id IS NULL` 修复 / `period = NULL` 兼容 / POSTED-only 过滤(`8ae1d8f`);
   - `legacyGetTrialBalance`(`extended.js:384`,unused by routes);
   - styles.css / Nginx / systemd / backup 配置;
   - 其它 page / module / API。

## Post-v1.0.0 Production Audit Fix — Inventory Transfer 500 + Warehouse Product Permission

**Goal**

修复 v1.0.0 production journal 在 GET /api/inventory-transfers 反复记录的 `Error: no such column: it.reviewer_id`(server/app.js:1338 主查询引用 `it.reviewer_id`,但 `inventory_transfers` 老 schema 不声明该列);补齐 warehouse 角色对 `/api/products` 的访问(`master-data.jsx:329` 库存 tab 加载 `/api/warehouses` + `/api/products`,role-warehouse 此前缺 `PRODUCTS_VIEW`)。严格 scope:不发明新 permission,不重写 business logic,不修改 styles/Nginx/systemd/backup。

**Audit 摘要**

1. **`inventory_transfers` 既有 CREATE TABLE(`migrations/extended-schema.js:577-588`) 缺少运行时需要的列**:
   - `remark` —— createInventoryTransfer 在 INSERT / listInventoryTransfers SELECT 都引用
   - `updated_at` —— 同上
   - `reviewer_id` —— listInventoryTransfers / getInventoryTransfer / changeInventoryTransferState(action=transfer|cancel) 都引用
   - 老 CHECK 约束只允许 `('DRAFT','SUBMITTED','APPROVED')`,但 runtime `transfer` action 写 `TRANSFERRED`,`cancel` action 写 `CANCELLED`,违反 CHECK(后续 UPDATE 也会 500)
2. **`inventory_transfers` 既无 ADD COLUMN migration 也无 CHECK rebuild(`server/db.js`)**:对比 production 实战 joint migration pattern (`migrateProductionOrdersCheck` / `migrateVoucherWorkflow`),该表 schema 缺口没有相应 reconciliation 路径
3. **`server/app.js` 三处引用 `INVENTORY_TRANSFER_STATUS` 常量但全仓库未定义**(`grep -rln` 仅命中 `server/app.js`):listInventoryTransfers / getInventoryTransfer / listInventoryTransfers(.map())都会触发 ReferenceError;**这是一个独立运行时缺陷**,与 column 缺失叠加导致 500
4. **role-warehouse 权限缺口**:`server/db.js:1132` 的 rolePermissions['role-warehouse'] 之前没有 `PRODUCTS_VIEW`;`/api/products` 是 `allowAny(['PRODUCTS_VIEW','PRODUCTS_MANAGE'])`,所以 warehouse 该端点 403(影响 `master-data.jsx:325 Inventory` tab)
5. **Frontend audit**:App.jsx navGroups 把 用户与角色 / 项目 / CRM 等入口 gated 在 `USERS_MANAGE` / `ROLES_MANAGE` / `PROJECT_*` 等 — warehouse user 都不会触达,`master-data.jsx UsersRoles` 的 `.catch` 处理 403 也 OK;warehouse 真正需要解决的运行依赖只有 `/api/inventory-transfers`(500) 和 `/api/products`(403),与已审计产物一致

**Fix**

1. **`server/db.js` — 幂等 schema reconciliation** (在 `migrateVoucherWorkflow()` 之后追加 `migrateInventoryTransfers()`):
   - 步骤 1:`ALTER TABLE inventory_transfers ADD COLUMN remark TEXT NOT NULL DEFAULT ''`(try/catch,列存在时吞错) —— 与 `addColumn` 同模式
   - 步骤 2:`ALTER TABLE inventory_transfers ADD COLUMN updated_at TEXT`
   - 步骤 3:`ALTER TABLE inventory_transfers ADD COLUMN reviewer_id TEXT`
   - 步骤 4:`UPDATE inventory_transfers SET updated_at = created_at WHERE updated_at IS NULL OR updated_at = ''`(legacy 行 backfill)
   - 步骤 5:`SELECT sql FROM sqlite_master WHERE type='table' AND name='inventory_transfers'` 探测 CHECK;若 `'TRANSFERRED'` 与 `'CANCELLED'` 都在,跳过;否则 `CREATE TABLE inventory_transfers_new` (含扩展 CHECK + 全部列)→ `INSERT ... SELECT ... COALESCE(...)` 保留所有现有行(包括 reviewer_id 在新增列后正确写入)→ `DROP TABLE` + `ALTER TABLE ... RENAME TO` + `CREATE INDEX`。整段被 try/catch 包裹并 `console.error` 报告失败,不影响后续 startup
   - 三条 ALTER + 一次 backfill + 一次 rebuild,每一步都 idempotent:
     - 列已存在 → ALTER 抛错吞掉
     - updated_at 已有值 → backfill 跳过
     - CHECK 已有扩展 → SELECT 检测已包含 `'TRANSFERRED'`,跳过 rebuild
     - 已有 rows → COALESCE 保留所有字段(包括 reviewer_id NULL)
2. **`server/db.js` — `rolePermissions['role-warehouse']` 增加 `PRODUCTS_VIEW`**(`server/db.js:1132`):
   - 不增 `PRODUCTS_MANAGE`(warehouse 不应创建 / 编辑 product master)
   - 不增 `USERS_MANAGE` / `ROLES_MANAGE` / `ACCOUNTING_VIEW`(separation of duties)
   - 利用既有 `INSERT OR IGNORE INTO role_permissions(role_id, permission_code)` PK 幂等路径(`server/db.js:1134`),production DB 启动一次自动 reconcile,无需 ALTER,无需手工 SQL
3. **`server/app.js` — 新增 `INVENTORY_TRANSFER_STATUS` 常量**:
   - 修复了独立运行时 ReferenceError,在 listInventoryTransfers / getInventoryTransfer 真正返回 200 之前必须先修好;否则即使 column 修复,`.map()` 行仍 ReferenceError
   - 包含 5 个 status(DRAFT / SUBMITTED / APPROVED / TRANSFERRED / CANCELLED),覆盖既有 + 扩展 CHECK 接受的全部状态
4. **未变更 / 严格 scope 保护**:
   - 不发明任何新 permission code,不动 `PERMISSIONS` registry
   - 不修改 `inventory_transfer_items` schema(无运行时缺失列)

   - 不替换 projects-workflow.jsx 各 `api('/api/users')` 调用方,因为 warehouse 不触达该模块(由 App.jsx navGroups gating 保证)
