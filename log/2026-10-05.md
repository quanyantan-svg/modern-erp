### 评审识别的设计问题

1. 路由表字段过度 — route 表先前承载 `permissions` / `transactionPolicy` / `auditPolicy` 元数据，与既有 `allow / allowAny` 运行时校验、`transaction(db, work)` 事务边界、`audit(db, ...)` 同事务审计易漂移。
2. 强制统一 handler 签名 — 先前要求所有 handler 立即统一到 `(db, req, res, actor, params)`，与"不强求统一签名 / 适配层渐进"原则冲突。
4. 推测性目录 taxonomy — 先前预先创建 14 个领域目录（`shared/` / `master-data/` / `orders/` / `procurement/` / `inventory/` / `tracking/` / `quality/` / `production/` / `planning/` / `accounting/` / `settlement/` / `reports/` / `lifecycle/` / `finance-extensions/`），无 call chain 推导。

5. dead-code 规则 — 先前基于 Stage 0 静态快照声称"已具备删除条件"；要求新建"行为等价"测试。
6. API deprecation 政策 — 先前引入强制 30 天 deprecation 周期与 `Deprecated:` HTTP 头要求。
7. `MIGRATING` 状态 — 先前把 `MIGRATING` 加为 `applicationRegistry.responsiveMode` 第三 production 值，引入"新 primary + 旧 fallback"双活屏幕设计。
8. 兼容 shim 移除条件 — 先前引入 elapsed-time 条件（`30 天` / `Wave N+2`）。
9. frontend decomposition 绑定 `master-data` — Wave 7/8 预先把 `master-data.jsx` 11 个 surface 映射为单一 `master-data` 业务域。

### 修正后的 route policy

route 表最小信息集：`method` / `path` / `handler` / `owner`。Authorization 仍由 handler 入口第一行 `allow / allowAny` 承担；事务仍由领域内 `transaction(db, work)`；审计仍由领域内 `audit(db, ...)`。不复制任何已有的运行时权威。

### 移除的推测性 taxonomy

移除 14 个预创建的领域目录；以"领域目录在某个迁移 wave 证明该业务确有 coherent owner 后才创建；ownership 跟随当前业务责任与 call chain；不创建 kitchen-sink"取代。举例仅作示例，非最终仓库 taxonomy。

### 移除的 `MIGRATING` 双活屏幕设计

`applicationRegistry.responsiveMode` 保持现有 `LEGACY_ADAPTER` / `NATIVE_RESPONSIVE` 两值；不新增运行时 production 状态。迁移模型：A. before（既有 loader 权威；新 surface 不挂载为该 route 的 live screen）；B. cutover（一次 bounded change 替换 loader；唯一 active screen）；C. responsive completion（满足 §19.5.D 后设 `NATIVE_RESPONSIVE`）。同一 route key 不允许两套 live executable business screen。
