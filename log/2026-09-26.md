## UAT R2 — 技术设计记录（仅设计）

### 调用链审计结论

- 用户管理：`POST /api/users` 严格白名单 `[username, displayName, password, roleId]`，`PATCH /api/users/:id` 白名单 `[displayName, password, roleId, active]`。`active` 是 update-only；CREATE 时由后端 hard-code `active=1`。前端 `src/pages/master-data.jsx` 的 `UserModal.save` 用 `{ ...form }` 整对象盲发，导致 CREATE 触发 `请求包含不支持的字段: active`。
- setup-admin：`scripts/admin/setup-admin.mjs:127` 解析 `ERP_DB_PATH || data/erp.db` 字符串并 `:92` 调 `createDatabase(dbPath)`，在 `ERP_DB_BACKEND=mysql` 的生产环境误入 `server/db.js` 的字符串-SQLite 分支；脚本不读 `ERP_DB_BACKEND`，不感知 MySQL。
- 系统健康：`src/pages/system-health.jsx` 是单一默认导出组件，唯一消费者是 `src/App.jsx`；桌面导航（`navGroups` `system-health`）、应用启动卡（`'health'` 图标名）、移动应用（`MOBILE_APPLICATION_GROUPS`）、路由表项（`pages['system-health']`）构成本次清理面。

- 需求：来源型 PO 必须保留不可变来源身份（来源请购单/行、来源产品、当前合同定义的不可变来源数量），同时允许运营方编辑当前后端合同支持的商业/单据字段，至少包括付款条款与付款条件天数；后端 immutability 校验必须保持严格。

- 提交要求：PO 在补全当前合同要求的商业字段后必须能保存并随后提交审批。手工创建的 PO 不得因此变更发生回归。

## UAT R4-R2A — 设计澄清（仅 solution.md / log）

### PO UPDATE 设计术语修正

- R4-R2 在 solution.md §20.7 写作 “采用 Option A：前端保留 source 标识”，但前文选项定义中 Option A 语义为 “Do not send immutable source lines at all on header-only update”，与实际修复不一致。

### PR required_date 聚合规则

- 源日期模型：`purchase_instructions` header 仅含 `planned_date`，行级保留 `need_by_date`（可为 null），无 header 级 “要求到货日”。`purchase_requisitions` header 强制单一 `required_date`，PR items 不带自己的 `need_by_date`。`createPurchaseRequisition` 校验（`planning-documents.js:704`）要求 PR header `required_date` 与每条 PUI item 的 `need_by_date` 严格相等（当后者非空时）。
- PR 自动衔接的 `required_date` 默认值确定性聚合规则：从 PUI items 中筛选 `need_by_date` 非空值，取**最早日期**（按 `YYYY-MM-DD` 字典序 / 时间序等价）；若全部为空，回退 `planned_date`。规则按集合而非顺序计算，避免依赖首条 item 的偶然顺序。
- 不引入 schema 变更。`required_date` 与某条 PUI item 的 `need_by_date` 不一致时由后端拒绝，操作员可调整 `required_date` 或来源。
