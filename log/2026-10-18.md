### C. SERIAL provenance lock proof

- Confirm-time precheck (`server/modules/sales-return-canonical-writer.js:197-201`, added in the prior gate):
  ```sql
  SELECT 1 FROM sales_return_valuation_provenance
    WHERE original_outbound_valuation_movement_id=? AND serial_id IS NOT NULL
    ${db.dialect === 'mysql' ? ' FOR UPDATE' : ''} LIMIT 1
  ```
- Supporting index (`server/migrations/sales-customer-wave6-returns.js:41`, `:507`): `idx_provenance_original_outbound(original_outbound_valuation_movement_id, id)`.
- Authoritative lock anchor: `mysql_transaction_gates.gate_id=1` (`server/db.js:1886`); every `transaction()` acquires it `FOR UPDATE` before any business row is touched. SQLite uses `BEGIN IMMEDIATE` (`server/db.js:1880`) which serializes the entire transaction.
- Transaction boundaries: one `transaction(db, () => { … })` per `confirmOptionAReturn` / `reverseOptionCReturn`. All Gates, physical writes, valuation writes, voucher, optional Credit, success audit and idempotency record commit atomically inside that one transaction.
- MySQL isolation level: default `REPEATABLE READ`. No explicit `SET TRANSACTION ISOLATION LEVEL` is issued in `server/database/mysql-adapter.js` or `server/database/mysql-schema.js`. InnoDB next-key locks under REPEATABLE READ plus the `(original_outbound_valuation_movement_id, id)` index mean the FOR UPDATE predicate acquires either a row lock (when a matching provenance row exists) or a gap lock on the outbound_id range (when no row yet exists). A competing INSERT of another provenance row with the same `original_outbound_valuation_movement_id` from another transaction will block until the first transaction commits; at that point the second transaction's FOR UPDATE re-read finds the row and the application rejects with HTTP 409.
- SQLite equivalent: `BEGIN IMMEDIATE` provides whole-transaction serialization; the `FOR UPDATE` clause is a no-op hint in SQLite. The precheck is therefore sufficient under the SQLite write transaction model.
- Two concurrent Returns attempting to consume the same original outbound before a provenance row exists:
  - **Proven DB-enforced safety**: `UNIQUE(return_valuation_movement_id)` does NOT block this race because each Return has its own valuation_movement_id. There is NO DB-level UNIQUE on `original_outbound_valuation_movement_id` (the migration does not add one for SERIAL — verified in `server/migrations/sales-customer-wave6-returns.js:383-509`). Therefore the protection comes from the index-based gap lock and from the application-level FOR UPDATE precheck, not from a DB-enforced uniqueness constraint.
  - **Application-level protection**: FOR UPDATE-locked precheck at Confirm time (line 197-201) and at Reverse time (`serialGuard` line 121-129) plus `mysql_transaction_gates` gate-row serialization.
  - **Safety requiring independent-session verification**: the InnoDB next-key lock semantics for `SELECT … FOR UPDATE` against an index range with no matching row depend on the index, the isolation level, and the InnoDB lock manager. This is dialect-dependent and has not been verified against a real MySQL independent-session harness in this session (TEST_EVIDENCE_PENDING for real MySQL execution). ### E. Three-Stage Business Gate Integration (P1)

A new helper `assertSalesPrepaymentGateAtStage(db, salesOrderId, stage,
{ businessDate, currentActorId })` lives in
`server/modules/sales-prepayment-gate.js`. It enforces:

```
NO requirement         → NOT_REQUIRED (no-op)
requirement exists,
  no gate result row   → HttpError(409, SALES_PREPAYMENT_GATE_NOT_EVALUATED)
  decision == BLOCK    → HttpError(409, SALES_PREPAYMENT_GATE_BLOCKED)
  decision == WARN     → return WARN (does not block)
  decision == OVERRIDE_REQUIRED,
    empty override_reason → HttpError(409, SALES_PREPAYMENT_GATE_OVERRIDE_MISSING_REASON)
  decision == OVERRIDE_REQUIRED,
    non-empty reason  → return OVERRIDE_REQUIRED (allows)
  decision == PASS     → return PASS
```

Hooked into three real business entry points:
  * `salesOrderAction('submit')` in `server/modules/sales-orders.js`
    → PLANNING_RELEASE stage gate
  * `requestReservationIntent` in `server/modules/sales-reservation-intent.js`
    → RESERVATION stage gate (inside the same transaction)
  * `confirmSalesDelivery('confirm')` in `server/app.js`
    → DELIVERY stage gate

This means a Sales Order cannot enter PLANNING_RELEASE, RESERVATION, or
DELIVERY without an explicit gate evaluation result. Persisted rows honor
`effective_from` / `effective_to` so an out-of-range requirement does not
block the gate. The gate row is locked FOR UPDATE inside the caller's
transaction so concurrent re-evaluations cannot bypass the carry-forward
OVERRIDE_REQUIRED decision.

### F. SO / Reservation Lifecycle Events (P1)

Real business event integration is exercised via the react-to-event helpers
in `server/modules/sales-reservation-intent.js`:

  * `adjustReservationIntentOnChange({ salesOrderId, salesOrderItemId,
    mode, newQty, consumerEvent })` — SO Change releases the existing
    intent and allows re-request at a new quantity.
  * `releaseReservationIntentsForOrder({ salesOrderId, consumerEvent })` —
    SO Cancel / Close / Delivery Confirm / Return bulk-release the
    active intents on this order; Replacement uses the same helper to
    reset before the new source-linked intent is created.

The intent state machine proceeds NONE → REQUESTED → GRANTED → CONSUMED
or back to RELEASED. Delivery Confirm transitions an active intent to
CONSUMED via the `consume` API; it does NOT auto-create a new intent, so

## MySQL Schema Bootstrap Index DDL Fix (2026-10-18)

- Scope: bounded fix to `server/database/mysql-schema.js` for the `ER_KEY_COLUMN_DOES_NOT_EXITS: Key column 'null' doesn't exist in table` failure observed during the Wave 7 real-MySQL acceptance gate.
- Boundary preserved: no Git write, no push/tag/release/deploy, no production / non-`modern_erp_domain_test` database, no `pnpm test:mysql*` / `pnpm test:fast` / `pnpm test` / `pnpm test:heavy` / `pnpm build`, no `APPLY_GUIDE.md` / `document.md` / `package.json` modification. Pre-existing dirty worktree (641 entries) and all database/WAL/SHM artifacts preserved verbatim.
- Root cause confirmed: SQLite `PRAGMA index_info(<index>)` returns `{ seqno, cid: -2, name: null }` for expression columns (Wave 7 `uq_sales_reservation_intent_order_line_mode` carries a `COALESCE(sales_order_item_id,'')` expression). `captureSqliteSnapshot` therefore stores `columns = ['sales_order_id', null, 'reservation_mode']`. The bootstrap loop's `useDigest = unique && (where || columns.length > 4)` evaluated to `false` for that 3-column expression UNIQUE index and emitted `` CREATE UNIQUE INDEX `...` ON `...` (`sales_order_id`,`null`,`reservation_mode`) ``, which MySQL rejected with errno 1072.
- Fix applied to `server/database/mysql-schema.js`:
  - Added `hasExpressionColumns(index)` (detects non-string column or expression-column mismatch at any position).
  - Tightened `mysqlIndexColumnList` to throw with `table.index` + `position N` reference when any column is not a non-empty string; never silently emits `` `null` ``.
  - Tightened `generatedPartialIndex` to throw with `table.index` + `position N` when both column and expression are missing at a position; defaults `where` to `1=1` only when missing.
  - Bootstrap loop (fresh path) now uses `useDigest = hasExpressionColumns(index) || (index.unique && (Boolean(index.where) || index.columns.length > 4))`.
  - `planMySqlIndexReconciliation` rejects expression-column indexes with a clear error rather than silently producing malformed DDL or hiding the issue.
  - `tableDefinition` refuses inline UNIQUE constraints with expression columns (MySQL has no inline expression UNIQUE; such indexes must be declared by their canonical migration).
- Compatibility preserved: SQLite migration path, `captureSqliteSnapshot`, `MYSQL_INDEX_PREFIX_LENGTHS` (Wave 6 LOT frontier), and all 3 migrations that import `mysqlIndexColumnList` (`r4-purchase-source-cardinality`, `sales-customer-wave6-returns`, `sales-customer-wave7-prepayment-reservation`) remain unchanged in behavior — they only ever pass plain string column arrays.
