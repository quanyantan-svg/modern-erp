### R4-01 C-05 Mutation Key 唯一性（已闭合）

- **发现**：`M1-D-31` 与 §26.33.4.7.2 的 R3 公式 `<SOURCE_TYPE>:<business_event_id>:<legSeq>` **不区分同一业务事件内的多个业务项**。已核对源码：`confirmOutsourcingReceipt`（`outsourcing-finance.js:100-124`）的倒冲按 `for (const m of materials)` **逐个物料行**产生物理 OUT 腿（N 个物料行 ⇒ N 条腿，`source_item_id` 各为 `m.id`）；SERIAL 产品一次发料必须拆成 `q` 次 `applyInventoryMutation`（`postCanonicalTrackedLeg` 强制 `qty===1`，`traceability-quality.js:247-275`）。⇒ N 条腿与 q 条拆分腿在 R3 公式下算出**同一个** Mutation Key；非 Consignment 路径命中 `inventory_mutation_log` 后**不比对请求内容**直接返回 `replayed:true`（`inventory-mutation.js:258-261`）⇒ 第 2…N 条腿被**静默丢弃**、物理库存少扣。
- **裁定**：Mutation Key 扩为 **`<SOURCE_TYPE>:<business_event_id>:<business_event_item_id>:<leg_seq>:<identity_key>`**，四个维度分别区分业务事件 / 业务事件项 / 物理腿 / 身份子腿；`identity_key` 复用 §26.33.4.6.1 的既有定义（`LOT:<id>` / `SERIAL:<id>` / `NONE`），**不得**用序号（重试会漂移）。另加**第二道防线**：① 每条腿断言 `mutation.replayed === false`（仅当整条业务事件命中 canonical `idempotencyReplay` 时才允许 true），否则 409 `INVENTORY_MUTATION_UNEXPECTED_REPLAY`；② 断言**实际腿数 == 预期腿数**，否则 409 `INVENTORY_MUTATION_LEG_COUNT_MISMATCH`；两者均**整笔回滚**。请求级 canonical 幂等与整笔回滚保持不变。
- **落地**：§26.33.1 的 `M1-D-31`、§26.33.4.6.1（幂等要件第 4 条、证据块的等价性措辞）、§26.33.4.7.2（一一对应规则 + 四段区分表 + 确定性要求 + 第二道防线）、§26.33.5.2（物理腿断言）、§26.33.8（幂等表 + C-05 补充）、§26.33.11（错误码）、§26.33.12（`M1-GB01`）。

### R4-02 INV-WIP-3 自指不等式（已闭合）

- **发现**：§26.33.4.2 的 `INV-WIP-3` 写作 `transferred_out_i ≤ (… − transferred_out_i + transferred_in_i)` —— **左端含 `transferred_out_i`、右端也含该项**，是**自指**不等式（展开为 `2·transferred_out_i ≤ A + transferred_in_i`），既不等价于"转移量 ≤ 当时可用 WIP"，也无法在运行时直接求值。**且** §26.33.10.1 的同一不变量另写作 `transferred_out_i ≤ supplier_wip_i` —— 两个登记点**互相不一致**。
- **裁定**：改为四量定义 —— `WIP_before(i)`（**加锁并重读源行后**的当前值，含该行此前已转入部分）、`q_requested`、`cum_transferred_out(i)`、`WIP_after(i)`；断言 `q_requested ≤ WIP_before(i)` 且 `WIP_after(i) ≥ 0`。并新增 **INV-WIP-1b：逐物料行** `supplier_wip_i ≥ 0`（R3 只有**订单级**聚合非负，单行透支可被同订单另一行的正数掩盖）。
- **落地**：§26.33.4.2 与 §26.33.10.1 的 INV-WIP 块（两处**现已一致**）、§26.33.11、§26.33.12（`M1-GB03`）、§26.33.15（T 项）。

### R4-03 历史 WIP 身份隔离（已闭合）

- **发现**：R3 的 M-07a/M-07b 只声明"历史行 `identity_json` 保持 `'[]'`、不得编造"，但**没有**回答"这些归属不可证的历史量如何不再变成新的可转出 / 可倒冲 WIP"；且 `INV-WIP-4`（配对）与 `INV-WIP-6`（身份）对历史行**字面不成立**却无处置。
- **关键源码事实（新增）**：现状 `createWipTransfer`（`outsourcing-finance.js:401-402`）对转移执行 `UPDATE outsourcing_material_list SET issued_quantity = issued_quantity - q`（源行）/ `+ q`（目标行）⇒ **历史转移量已被净值计入 `issued_quantity` 本身**。因此 M-07b **若**把历史转移量回填进 `transferred_out/in` 会与 `issued_quantity` **双计**、使 `supplier_wip` 被低估、跨订单守恒被破坏（R3 未回填，但**也未说明原因**）。
- **裁定**：① **不回填** `transferred_out/in`（历史量留在 `issued_quantity` 内）；新增**声明式**列 `outsourcing_wip_transfers.quantity_accounting`（`'NETTED_IN_ISSUED'` / `'COUNTER_ONLY'`）、`identity_state`（`'UNVERIFIED'` / `'VERIFIED'`）、`source_resolution_state`（`'RESOLVED'` / `'UNRESOLVED'`）；② 新增**持久化隔离**列 `outsourcing_material_list.legacy_unverified_wip_quantity` 与 `identity_evidence_state`（`'NONE'` / `'UNVERIFIED'` / `'VERIFIED'`），并定义 **INV-WIP-3b**：`q_requested ≤ supplier_wip_available = supplier_wip − legacy_unverified_wip_quantity`；③ **INV-WIP-4 / INV-WIP-6 明确只对"新写入行"成立**，历史行由 `identity_state='UNVERIFIED'` 显式登记，其后果由隔离规则承担（"源行可确定但无身份证据" ⇒ 身份不变式**不成立**）；④ 新增迁移 **M-07c** 承载 `legacy_unverified_wip_quantity` / `identity_evidence_state` 的回填。
- **落地**：§26.33.1（`M1-D-12`/`M1-D-28`）、§26.33.4.2（DDL、R4-03 说明段、INV-WIP 块、隔离口径）、§26.33.5.2、§26.33.7（M-06/M-07a/M-07b/M-07c、PA-4）、§26.33.10.1、§26.33.11、§26.33.15（T-09）。

### R4-04 WIP 转移相容性（已闭合）

- **发现**：现状 `createWipTransfer`（`outsourcing-finance.js:383-406`）**只**按 `product_id` 在目标订单取**第一行**（`:388`），**不**校验供应商、UOM、仓库、身份；而本 Design 把 WIP 转移定义为**归属再分配**（物料始终在**同一个**供应商 WIP 仓、同一 LOT/SERIAL 身份上、企业所有，**不产生任何物理移动**）—— 该定义只在相容时成立。

- **落地**：§26.33.1（`M1-D-12`）、§26.33.4.2（五项门禁表 + SERIAL 规则 + M-07b 收紧）、§26.33.6.2（请求体破坏性变更）、§26.33.7（M-07b）、§26.33.8（L2e 锁序）、§26.33.11、§26.33.12（`M1-GB03`）。

### R4-05 VMI 公式更正（已闭合）

- **发现（互斥性证明）**：R3 的 VMI-P / VMI-S / VMI-E 把 `adjusted_*` 放在等式**右端**（消耗侧），而 VMI-R 的 closing 公式把同一量放在**左端**（`+ adjusted`）。展开后两者右端相差 `2 × (adjusted_S + adjusted_E)` ⇒ **VMI-P/S/E 与 VMI-R 互斥，不可能同时成立**。另 §26.33.4.4 的"可复现"段落里 `closing_enterprise_qty` **遗漏 `+ adjusted_enterprise_qty`**，与 §26.33.10.5 不一致。
- **裁定**：调整量是**有符号量**（正 = 池增加），`adjusted_*` 与 `unallocated_adjusted_qty` 一律置于**左端（来源侧）**；此时 VMI-P ≡ (VMI-S + VMI-E) ≡ VMI-R 的 closing 之和（差恰为 `unallocated_adjusted_qty`）。关期判据改为 `|unallocated_adjusted_qty| > VMI_ADJUSTMENT_TOLERANCE_QTY` ⇒ 拒绝关期（**正负同等阻断**；R3 只写 `> 0`，负值会被漏过），默认容差 **0（严格）**。§26.33.4.4 的过期 closing 公式已补齐。两处 VMI 恒等式现**逐字一致**。
- **数值例子（新增五个，逐例验证 VMI-P 与两个所有权池方程同时对账）**：① 正的供应商调整（+10）② 负的供应商调整（−10）③ 正的企业调整（+5，物权转移 40）④ 负的企业调整（−5，物权转移 40）⑤ 非零未归属调整（+7，物权转移 40 ⇒ 两个池的恒等式**不可能同时成立**，差额恰为 7 ⇒ 拒绝关期）。
- **顺带固定**：`returned_qty` 的口径 = **供应商池退货**（企业池不设退货项），VMI-P 的 `returnedOrCancelled` = `returned_qty`；本轮**不**臆造第二列。
- **落地**：§26.33.1（`M1-D-29`）、§26.33.4.4（符号约定、恒等式、互斥性证明、五个数值例子、容差规则、returned 口径）、§26.33.4.4（"可复现"段补齐）、§26.33.10.5（权威版 + 对账条款 + R4 复核要点表）、§26.33.11、§26.33.12（`M1-GD01`）、§26.33.14.2（**新增 `M1-P-04`**）、§26.33.15。

### R4-07 M-12 迁移完整性（已闭合）

- **发现**：R3 的 M-12a / M-12b 只写了"1:1 回填"，**未**逐列给出取值来源；更严重的是，M-12a 把遗留行的 `converted_quantity` 隐含为 `0` —— 而遗留 `purchase_receipt_items` **没有** `source_notice_item_source_id`（M-03 才新增），历史收货与历史通知之间**没有任何可证明的归属关系**（且"无通知直接 PO→入库"是合法既有路径）⇒ 写 `0` 等于断言"已证明未转换"，属于**编造事实**。
- **裁定**：① `receipt_notice_item_sources.converted_quantity` 由 `REAL NOT NULL DEFAULT 0` 改为 **可空**：`NULL` = **未证明**，非 `NULL` = 已证明的累计转换量（已证明为零写 `0`）；M-12a 对遗留行写 **`NULL`**，运行期一律以 `COALESCE(…, 0)` 参与容量计算（**保守方向**：宁可多预留、不得少预留）。② M-12a / M-12b **逐列**给出取值来源：`id` = 确定性派生（`'M12A-'/'M12B-' || notice_item_id`，**不用** `randomUUID`，保证迁移可重放且幂等）；`business_date` = `receipt_notices.notice_date`（权威历史业务日期，**不得**用迁移执行时间或今天替代）；`created_at` / `updated_at` = `receipt_notices.created_at` / `updated_at`；`delivery_schedule_id` = **NULL**（遗留行无交期绑定证据，不得推定）；`resolution_state` = 常量 `'UNRESOLVED'`；`resolved_at` = **NULL**；`detected_at` = **迁移执行时刻**（"检测到未解析"的事实时刻，不是业务日期）。③ **幂等与防重**：M-12a 按**唯一键** `(notice_item_id, purchase_order_item_id)` 判重（`WHERE NOT EXISTS`），M-12b 按 `notice_item_id` 判重（该列同时是 `UNIQUE(notice_item_id)` 的键）；**禁止** `INSERT OR REPLACE`（会覆盖）；MySQL 侧子查询须**包一层派生表**以规避"目标表出现在 FROM"的限制。④ **`detected_at` 明确排除出 parity 断言**（它是运行时刻，两端必然不同）；PA-3 改为**逐列**比对。

### R4-08 M-15 执行顺序（已闭合）

- **发现**：R3 的 M-15 把 **PRE-A / PRE-B / PRE-C 一律排在"加列"之前**，而 **PRE-B 的定义是"回填后自洽"** —— 在 `identity_key` 列尚不存在时**无法运行** ⇒ 顺序不成立。
- **裁定**：改为**五步且顺序不可调换** —— **STEP-1 PRE-A**（可在加列前运行；只读现有列）→ **STEP-2 加列** `identity_key TEXT NOT NULL DEFAULT ''` → **STEP-3 回填**（只填空、不覆盖，且**限定在六个委外来源**，不触碰其它写者的行）→ **STEP-4 PRE-B / PRE-C**（必须在加列 + 回填**之后**）→ **STEP-5 建索引**（只在 STEP-1/4 全部通过后才可执行）。另规定 **MySQL DDL 自动提交下"部分完成后重试"的逐状态语义**（六种中间状态各一行：重跑只读检查 / `safeAddColumn` 跳过 / 回填无操作 / **PRE 失败 ⇒ 再次中止、列与回填保留**（DDL 已提交、无法回滚）、索引已存在 ⇒ 跳过），并规定 **feature gate 开启的三个硬条件**（PRE-A/B/C **实测**通过 ＋ 索引在**当前目标库**上确实存在 ＋ 每次启动/迁移后重新校验）；任一不成立则委外跟踪写入路径**保持关闭**。**禁止**删历史行 / 补写 `source_item_id` / 臆造 `identity_key` 来让检查通过。另更正一处执行性事实：MySQL **不支持** `CREATE UNIQUE INDEX IF NOT EXISTS`，唯一索引须由 `mysql-schema.js` 的 `generatedPartialIndex` 路径从 SQLite 快照生成。
- **落地**：§26.33.4.6.1（PRE-A/B/C 三项）、§26.33.7（M-15 行 + 重试语义表 + feature gate 条件）、§26.33.15（T-01/T-07）。

### R4-09 VAL-12 / T-02 一致性（已闭合）

- **发现**：`VAL-12`（§26.33.10.2）写"SQLite 部分索引与 MySQL 摘要生成列路径**语义等价**"，与 `T-02`（§26.33.15）"**形式上不等价**"**直接冲突**。同时 §26.33.4.6.1 证据块里一句"身份占用保证在 SQLite 与 MySQL 上都成立"**过度断言**。

### R4-10 C-07 `OVER_RESERVED` 持久模型（已闭合）

- **发现**：R3 只说"必须把超出的预留**登记为** `OVER_RESERVED`"，**没有任何持久载体**、没有粒度、没有识别规则、没有解除规则。
- **裁定**（六项）：① **粒度 = 账单行级持久**（`supplier_bill_items.reservation_state` / `over_reserved_quantity` / `over_reserved_reason` / `over_reserved_detected_at`，新增迁移 **M-18**）+ **账单级派生**（`reservationState`；**不新增**账单表列，**不改变** `closureState` 的既有三态）；② **超额行仍属 active 预留集合**（仍占用容量 ⇒ 超额**不会**把容量让给新行；**不得**自动作废/自动缩减/移出 `base_quantity`）；③ **确定性识别**：按 `(supplier_bills.created_at, supplier_bill_items.bill_id, line_no, supplier_bill_items.id)` 全序排序（`supplier_bill_items` **无** `created_at`/`updated_at`），逐行累计 `base_quantity`，`cum(i) > GrossEligible` 的行被标记，`over_reserved_quantity = min(base_qty(i), max(0, cum(i) − GrossEligible))` ⇒ **不依赖插入顺序的偶然性**；④ **被阻止过账的行** = 全部 `OVER_RESERVED` 行（409 `PROCESSING_FEE_OVER_RESERVED`，账单保持 DRAFT、零 AP/GL 写入）；⑤ **取消/重开**：作废使该账单退出 active 集合 → 重算后其余行标记**可被清除**（**只写标记、绝不写数量**）；"重开"是**新账单行**重新走容量检查，**不得**复活原预留；⑥ **五条防静默释放/缩减的硬约束**（重算只写四列、禁止触碰数量列、`base_quantity` 的减少必须经 canonical 显式业务动作并写审计、**不得**自动取消或缩减既有 DRAFT 预留、每次重算写审计 `RECOMPUTE_RESERVATION`、重算必须锁内重读）。
- **落地**：§26.33.1（`M1-D-33`）、§26.33.7（M-18）、§26.33.10.3（R4-10 六项）、§26.33.11、§26.33.12（`M1-GC01`）、§26.33.13（WP-5）。

### R4-11 多 PO 与交期容量（已闭合）

- **发现**：R3 只定义了通知行口径（`reservationBase`），**未**定义 A-REQ-03 明文要求的"有效订单行、**交期/容差**"上界，也**未**定义供应商/仓库相容与累计转换量的并发口径。
- **源码事实（新增，重要）**：`purchase_order_delivery_schedules.received_quantity` **全仓库从未被写入**（只被 `procurement-orders.js:40` 读取、在 `:139-140` 初始化为 0）；收货路径**从不**校验交期（`app.js` 只登记了 `createDeliverySchedule` / `listDeliverySchedules` 两个路由）⇒ **`received_quantity` 不是可用的权威容量来源**。
- **裁定**：① **四重上界**（`sourceRowRemaining` / `poLineRemaining` / `scheduleRemaining` / `orderRemaining`）逐项定义，单次转换量取其最小值；② **交期消费量的权威口径**：该 PO 行**只有一条**交期时用行级已确认收货量（无歧义）；**多条**交期时用 `received_quantity`（由转换路径在同一事务内维护），但历史行的该列恒为 0 ⇒ 若该行已有历史已确认收货 ⇒ 消费量**不可证** ⇒ **fail closed** 409 `RECEIPT_NOTICE_SCHEDULE_CAPACITY_UNKNOWN`；③ **容差口径**：`upper/lower_tolerance_pct` 按**百分数单位**消费（`5` = 5%），写入路径必须校验 `0 ≤ pct ≤ 100`（现状**未**校验）；**可转换剩余量只用上容差**，下容差属交期关闭规则、不在 M1 范围；④ **供应商与仓库相容**：来源 PO 的 `supplier_id` 必须等于通知的 `supplier_id`（可执行）；`purchase_orders` **没有仓库列** ⇒ PO 级"兼容仓库"在现有 Schema 中**不可表达**，本 Design **不**擅自加列，并把相容口径**诚实地固定在通知级**（通知携带唯一 `warehouse_id`，其全部来源转换到该仓）；⑤ **一个通知行对同一 PO 行至多一条分配** —— **裁定为"不可以"**：若允许跨同一 PO 行的多条交期，唯一键必须纳入**可空**的 `delivery_schedule_id`，会让唯一键因 NULL 互异而失效（R3 的核心教训）；`delivery_schedule_id` 表达"分配到哪一条交期"，**不参与**唯一键，跨交期份额用**多个通知行**表达（属 `A-P02` 语义，不在 M1 已批准范围）；⑥ **API**：转换请求的 `allocations[]` 新增**可选** `deliveryScheduleId`（给出时必须属于该 PO 行，否则 409 `RECEIPT_NOTICE_SCHEDULE_MISMATCH`；省略时该来源行**不受**交期上界约束并在响应中标记 `scheduleBound=false`），响应回显 `allocated[]`（含 `convertedQuantity` / `scheduleBound`）以满足 A-REQ-03 的"可查询、可审计、可追溯"；⑦ **累计转换量**为来源行上的单调累计值，转换时**锁内重读**再累加；⑧ **扩展锁序** L2a 通知行 → L2b 来源行 → L2c PO 行 → L2d 交期行（各按 id 升序）—— 现状收货路径**只**做读比较、**无**行锁，并发转换可双方通过。
- **落地**：§26.33.1（`M1-D-02`）、§26.33.4.1（R4-11 全节）、§26.33.5.1（行级/订单级/收货行级三层分层）、§26.33.6.1（API）、§26.33.7（PA-5）、§26.33.8（锁序扩展）、§26.33.11、§26.33.12（`M1-GA02`）、§26.33.13（WP-1）、§26.33.15（T-06/T-10）。

- **核心裁定（§26.33.4.2 新增"R4-6-R1 身份级 WIP 可用量模型"）**：隔离桶改为**残差** —— `legacy_unverified_wip_quantity_i = supplier_wip_i − verified_identity_wip_i`；`supplier_wip_available_i ≡ verified_identity_wip_i`。由此：正向动作使行总量与身份层**同增**，负向动作使二者**同减** ⇒ **残差（隔离量）在任何合法动作后保持不变** ⇒ "新增 50 不得改变原历史隔离量 100" 由公式**保证**，而不是靠约定。
- **两层模型**：行级（数量）+ 身份级（LOT/SERIAL，`identity_key` 复用 §26.33.4.6.1 已定义的 `'LOT:<id>'` / `'SERIAL:<id>'` / `'NONE'`）。
- **最小 additive sidecar**：`outsourcing_wip_identity_effects`（不可变签名台账）+ `outsourcing_wip_identity_balances`（锁内重读的物化余额）。**不是**第二套 Inventory / Tracking 引擎：物理库存仍只由 `applyInventoryMutation` 写、跟踪流水仍只由 `postCanonicalTrackedLeg` 写、估值余额仍只由 `issueValue`/`receiveValue` 写；sidecar 不持有任何物理数量，每行必须由同事务内的 canonical 物理腿背书。**为什么现有表不够**已在 §26.33.4.2 逐表列出（`tracked_inventory_movements` 只记物理腿、无法承载"无物理移动"的 WIP 转移且无订单归属维度；`inventory_lot_balances` 主键 `(warehouse_id, lot_id)` 无 owner/订单维度；`inventory_serials` 无归属与数量累计；`inventory` 是位置口径无血缘；历史三表无身份列）。
- **表结构**：两表全部 UNIQUE / 主键建立在 **NOT NULL** 列上 ⇒ SQLite/MySQL 严格等价；`CHECK` 由 `mysql-schema.js:204` 从 SQLite 快照翻译保留；`CREATE TABLE IF NOT EXISTS`，无表重建、无 `ALTER ... ADD COLUMN ... UNIQUE`。
- **数量公式**：`verified_identity_wip_i = Σ_b available_quantity(i,b)`；`legacy_unverified_wip_quantity_i = supplier_wip_i − verified_identity_wip_i`；`supplier_wip_available_i = verified_identity_wip_i`；`available(identity b) = supplied − consumed`。

**WIP 身份模型最终公式**

```text
supplier_wip_i = issued_i + supplemented_i - returned_i - backflushed_i
                 - transferred_out_i + transferred_in_i

verified_tracked_wip_i
    = Σ available_quantity  WHERE evidence_state = 'TRACKED'
verified_quantity_only_wip_i
    = Σ available_quantity  WHERE evidence_state = 'QUANTITY_ONLY'
legacy_unverified_wip_i
    = supplier_wip_i - verified_tracked_wip_i - verified_quantity_only_wip_i
supplier_wip_available_i
    = supplier_wip_i - legacy_unverified_wip_i
    = verified_tracked_wip_i + verified_quantity_only_wip_i

remaining_supply(effect s)   -- s 必须 effect_direction='SUPPLY'
    = s.signed_quantity
      - Σ allocated_quantity
        FROM outsourcing_wip_identity_effect_allocations
        WHERE source_supply_effect_id = s.id AND allocation_kind = 'CONSUMPTION'
      -- 不扣 TRANSFER_ORIGIN：来源扣减只由 TRANSFER_OUT 的 CONSUMPTION 分配完成
```

**新增 allocation 表的完整 DDL**

```text
outsourcing_wip_identity_effect_allocations  (R4-6-R2 新增：来源分配血缘 —— 多来源消费的权威载体)
  id TEXT PRIMARY KEY,
  effect_id TEXT NOT NULL,
  source_supply_effect_id TEXT NOT NULL,
  allocation_kind TEXT NOT NULL,         -- 'CONSUMPTION' | 'TRANSFER_ORIGIN'
  allocated_quantity REAL NOT NULL,      -- 恒 > 0
  created_at TEXT NOT NULL,
  FOREIGN KEY(effect_id) REFERENCES outsourcing_wip_identity_effects(id),
  FOREIGN KEY(source_supply_effect_id) REFERENCES outsourcing_wip_identity_effects(id),
  CHECK(allocation_kind IN ('CONSUMPTION','TRANSFER_ORIGIN')),
  CHECK(allocated_quantity > 0),
  UNIQUE(effect_id, source_supply_effect_id, allocation_kind)
```

**分配规则**：同一订单 / 同一物料行 / 同一产品 / 同一 `identity_type`/`identity_key`；按原始 supply effect 的 `created_at ASC, id ASC` **FIFO**；SERIAL 每次只能分配**一个**完整序列号数量；**不得**跨身份 / 跨产品 / 跨 UOM 混合。`CONSUMPTION` 的分配合计必须**恰好**等于消费 effect 的绝对值；`TRANSFER_ORIGIN` 的分配合计必须**恰好**等于 TRANSFER_IN 数量且与同一转移事件的 TRANSFER_OUT 的 `CONSUMPTION` 分配**逐项完全对应**；来源扣减**只**由 TRANSFER_OUT 的 `CONSUMPTION` 分配完成（不重复扣减）。
