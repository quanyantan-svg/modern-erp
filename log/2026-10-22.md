### Key Design decisions

**C1 — Credit Profile identity.** `id TEXT PRIMARY KEY` surrogate plus `salesperson_scope_key TEXT NOT NULL` normalized scope (`'*'` = aggregate, else the salesperson id). Bidirectional invariant enforced by one CHECK plus the `salesperson_id` FK. Version uniqueness is `UNIQUE (anchor_id, effective_from)` — non-null, so it is not a nullable composite UNIQUE and behaves identically on SQLite and MySQL. Effective-interval authority enforced by the canonical writer under the scope anchor lock. `credit_check_rules` gains an explicit PK. `credit_parameters` drops the column-level `UNIQUE(code)` that made versioning impossible.

**Circular FK removed.** `credit_check_results.special_approval_id` and `credit_special_approval.source_credit_check_result_id` formed a cycle in frozen §29.25.1/§29.26. `special_approval_id` was dropped; the approval -> check-result direction alone is canonical. Removes a real MySQL `ADD CONSTRAINT` ordering hazard.

**Dual-Limit fits the 14 tables with no additions.** Customer aggregate and salesperson sub-limit are distinguished by the *same* scope mechanism inside `credit_lock_anchors` and `credit_profile`, so no fifteenth table and no new table of any kind was needed. `credit_check_results` gained `check_group_id` + `scope_type` + `business_date` + `credit_profile_id` so one logical check can emit one row per applicable scope.

**P13 enforced structurally.** Because each logical check emits one row per scope and each approval binds `UNIQUE(source_credit_check_result_id)` to exactly one of those rows, an approval against one scope cannot release another applicable mandatory control. Not convention — schema.

**Cross-salesperson write skew excluded.** Step 2 of the lock order is unconditional: every credit-controlled transaction takes the SCOPE:AGGREGATE anchor `FOR UPDATE` regardless of salesperson. Two salespersons on one customer contend on one shared row; the loser re-reads committed state and re-evaluates. The design explicitly does *not* rely on two salesperson anchors to protect the shared aggregate. Fixture W10-R5 fails if that is ever implemented wrongly.

**Snapshot fingerprint.** `UNIQUE (credit_lock_anchor_id, business_date, snapshot_fingerprint)` with object identity carried by an explicit column rather than inside the digest, so one credit object's evidence can never be silently reused by another, while repeated checks of the same state legitimately reuse the immutable row.

**Deferred FK taken safely.** `credit_profile_ratings.evaluation_result_id` is created in Wave 9 as `TEXT NOT NULL` with **no REFERENCES clause on either engine**; Wave 11 adds the constraint dialect-specifically (MySQL `ADD CONSTRAINT`, SQLite table rebuild). This deliberately avoids relying on any unverified assumption about SQLite accepting an inline FK to a not-yet-created table or about when it begins enforcing.

**Anchor provisioning resolved to integrated protocol.** Supersedes §29.21.1's contradictory pair of clauses. Insert-or-converge followed by an *unconditional* re-read-and-lock is what closes the first-use race, so a separate committed transaction is not required for correctness. Works with the dual-scope model by provisioning in the fixed POLICY_SCOPE -> AGGREGATE -> SALESPERSON order.

**Rating write owner decided.** `credit_profile_ratings` is the sole canonical owner; the inline `credit_profile.rating_*` columns are a derived read projection with exactly one writer.

### Correction applied

- **§36.15.3** — eligibility table reframed: ineligibility now selects mode `AGGREGATE_ONLY` and removes exactly one privilege (own sub-limit). - **§36.15.6.1** — `AGGREGATE_ONLY` emits a **constant fragment with no bind parameter**, so there is no value that can widen it. Fragment/args are a matched pair that must throw on mismatch. `:selfSalespersonId` must be a non-empty `salesperson_profiles.id` and must not be `'*'`, `NULL` or `''`.
