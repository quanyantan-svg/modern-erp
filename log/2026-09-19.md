# 2026-09-19

## M11 — Net-Before-Explosion HOTFIX

### Defect

Real Edge acceptance run exposed a blocking MRP calculation defect.
The engine exploded the BOM from the parent **gross** requirement
instead of the parent **net MAKE** quantity. For the deterministic
fixture (Sales 10 + Forecast 10 = 20 gross, on-hand 3, open production
2 → net 15), the components received A = 40 and B = 60 instead of the
required A = 30 and B = 45.

### Root cause

`server/modules/planning.js` called `explodeBomAggregate(db, pid,
info.totalGross)` for every parent whose total gross demand was
non-zero. `info.totalGross` is the parent's raw gross demand (sales +
forecast), not the parent's net MAKE quantity. As a result, the
parent's own on-hand stock and eligible open purchase / production
supply were ignored when feeding the BOM explosion.

### Fix

- Replaced `explodeBom` and `explodeBomAggregate` with a single DFS
  walker `explodeBomNet(pid, gross, path, depth, state, …)` that
  computes the parent's net (= max(0, gross − on_hand − open_po −
  open_prod)) BEFORE walking any BOM, and only then explodes the BOM
  using the net MAKE quantity as the multiplier.
- Net ≤ 0 or non-MAKE parents contribute 0 to child demand; no BOM
  components and no BOM_EXPLOSION pegging rows are produced for them.
- Each MAKE child whose own net > 0 continues the walk recursively,
  so the next level always explodes from its own NET MAKE quantity,
  never from its gross component demand.
- Shared components are still aggregate-before-netting (the
  contribution from every parent is summed into `componentGross`,
  and netting is applied ONCE on the resulting total).
- BOM_EXPLOSION pegging quantities now reflect the corrected
  parent-net × BOM-qty contribution; stale 40/60 pegging is gone.

### Contracts preserved

- Sales open demand derivation, purchase open supply derivation,
  production open supply derivation, MAKE/BUY rule, ROUTING_MISSING
  warning, BOM cycle detection, depth limit 12, completed-run
  immutability, demand source modes (SALES_ORDERS / FORECAST /
  SALES_PLUS_FORECAST), permissions (MRP_VIEW / MRP_MANAGE only on
  `test_admin`), inventory neutrality, accounting neutrality, and
  Approval Center neutrality are unchanged.
- Schema is unchanged. Historical COMPLETED MRP rows are not
  rewritten automatically; a new MRP run must be created to obtain
  the corrected arithmetic.
- Transactional atomicity is preserved: cycle / depth / validation
  failures leave zero rows behind and the run remains in DRAFT.
