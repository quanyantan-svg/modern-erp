# 2026-09-19

## M12 — Production / Purchase Instruction & Purchase Requisition

### Scope

- Added three new planning-document families on top of the M11 immutable MRP snapshot:
  - Production Instruction (`production_instructions` / `production_instruction_items`) bridging MAKE suggestions to Production Orders.
  - Purchase Instruction (`purchase_instructions` / `purchase_instruction_items`) bridging BUY suggestions to Purchase Requisitions.
  - Purchase Requisition (`purchase_requisitions` / `purchase_requisition_items`) bridging Purchase Instructions to Purchase Orders, with approval.
- All new tables are append-only and never rewrite `mrp_run_results`. The MRP canonical `suggested_quantity` stays immutable; partial-conversion metadata (`converted_quantity` / `remaining_quantity`) is computed read-only by joining the active state of the planning documents.

### Lifecycle contracts

- Production Instruction and Purchase Instruction: `DRAFT → RELEASED → CANCELLED`.
  - `DRAFT` cancel succeeds; `RELEASED` cancel succeeds only when no downstream Production Order / Purchase Requisition has been generated.
  - Cancelling when a downstream document exists returns `409`.
- Purchase Requisition: `DRAFT → SUBMITTED → APPROVED / REJECTED → CANCELLED`.
  - Submit requires at least one item.
  - Approval blocked for the creator (`actor.id === header.creator_id` returns `409`).
  - Rejection requires a non-empty reason.
  - `APPROVED` cancel succeeds only when no Purchase Order has been generated.

### Eligibility and conversion safety

- Production Instruction: only `mrp_run_results.suggestion_type = 'MAKE' && net_requirement > 0`; `400` otherwise.
- Purchase Instruction: only `mrp_run_results.suggestion_type = 'BUY' && net_requirement > 0`; `400` otherwise.
- `mrp_runs.status != 'COMPLETED'` returns `409`.
- Per-item creation re-reads `SUM(quantity)` of all active instructions against the same `mrp_result_id` inside the transaction. Requested quantity must be `<= remaining`; otherwise `409` over-conversion.
- Conversion metadata surfaced in `GET /api/planning/mrp/runs/:id` as `converted_quantity` and `remaining_quantity` (read-only).

### Downstream generation

- `POST /api/production-instructions/:id/generate-production-order` requires the header to be `RELEASED`. The user picks one `itemId` from the released instruction; the server reuses the canonical Production Order creation path (`createProductionOrder`) with `bom_id`, `product_id`, `quantity` from the instruction item, `planned_start` from `need_by_date`, and a remark that records the source instruction. The instruction item is updated with the generated `production_order_id`; a `UNIQUE` partial index enforces one PO per item.
- `POST /api/purchase-requisitions/:id/generate-purchase-order` requires the header to be `APPROVED`; the user picks a `supplier_id`; the server creates a `DRAFT` Purchase Order reusing the canonical PO creation path; the requisition header gets `purchase_order_id`; a `UNIQUE` partial index enforces one PO per requisition.
- `POST /api/purchase-instructions/:id` (frontend "生成请购单" button) generates a `DRAFT` Purchase Requisition directly bound to the released instruction item via `purchase_instruction_item_id`; the back-link prevents a second requisition from the same instruction item.

### Approval Center integration

- `PURCHASE_REQUISITION` is added to the `DOCUMENTS` array in `server/modules/approvals.js`. It joins the existing four approval families:
  - `SALES_ORDER`, `PURCHASE_ORDER`, `INVENTORY_CHECK`, `ACCOUNTING_VOUCHER`, `PURCHASE_REQUISITION`.
- The `whereFor` filter respects creator ≠ reviewer and the `SUBMITTED → APPROVED / REJECTED` lifecycle.
- The `line previews` block does not need item-level rendering for requisitions (no amount is faked; the normalized item carries `systemQuantity` from the requisition lines).

### Permission registry

- Registered 7 new canonical permission codes:
  - `PRODUCTION_INSTRUCTION_VIEW`, `PRODUCTION_INSTRUCTION_MANAGE`,
  - `PURCHASE_INSTRUCTION_VIEW`, `PURCHASE_INSTRUCTION_MANAGE`,
  - `PURCHASE_REQUISITION_VIEW`, `PURCHASE_REQUISITION_MANAGE`, `PURCHASE_REQUISITION_APPROVE`.
- Total permission count goes from `100` to `107`.
- `role-admin` inherits all 7.
- `role-reviewer` gains `PURCHASE_REQUISITION_VIEW` + `PURCHASE_REQUISITION_APPROVE` (audit decision: mirrors the existing `PURCHASE_ORDERS_APPROVE` pattern; no second approval family needs a separate role).
- `role-sales`, `role-warehouse`, `role-accounting` do not gain any M12 permission. (Audit-confirmed.)

### Number generators

- Production Instruction: `PI-YYYYMMDD-NNNN` (daily sequence).
- Purchase Instruction: `PUI-YYYYMMDD-NNNN`.
- Purchase Requisition: `PREQ-YYYYMMDD-NNNN`.
- Generated Production Order keeps `MO-...`; generated Purchase Order keeps `PO-...`. None of the prefixes collide with `PR-` (Production Receipt) or with `BOM-...`.

### Inventory / accounting / approval neutrality

- `inventory_transactions` count delta = 0 across the planning flow.
- `accounting_vouchers` count delta = 0.
- Only the explicit "生成制令单" / "生成请购单" / "生成采购订单" actions mutate business documents, and only via the canonical production / purchase order creation paths.
