## V1.4.1 — MySQL V1.3 → V1.4 schema upgrade-path hotfix

### 起因与边界

- 不变更为：`business_date` 列定义、permission/role mapping、API 行为合同、SQLite 路径、roles、approval families、C01–C05 任何业务段、legacy 数据的 NULL 语义。
- 不 touch：v1.4.0 tag、生产、未受保护 DB、不可恢复的 schema 改动。
- 本次只修一个 narrow upgrade-path bug：从 V1.3 production MySQL 数据库升级到 v1.4.0 时，`inventory_transfers.business_date` / `inventory_checks.business_date` 列缺失。

### Phase 1 — 根因审计

- 入口：`server/db.js:390 createDatabase(target)`。
- MySQL 路径：`resolveDatabaseConfig` → `server/database/mysql-adapter.js:173 createMySqlDatabase(config, { createSqliteSnapshot, seedDemo })`。
- 顺序步骤：
  1. `captureSqliteSnapshot(createSqliteSnapshot, seedDemo)`：以 `createSqliteSnapshot = createSqliteDatabase(filename)` 跑一份干净的 SQLite。该 SQLite 已走完 `migrate(db)`（含 `migrateV14E2BusinessDate`）+ `seed(db)`（含 `reconcileV14E2Permissions`），因此快照的 `inventory_transfers` / `inventory_checks` 已含 `business_date` 列；`permissions` 已有 `INVENTORY_TRANSFER_CONFIRM`。
  2. `bootstrapMySql(adapter, snapshot)`：见 `server/database/mysql-schema.js:154-213`。
     - 当目标 MySQL 已含 `mysql_backend_metadata`（`complete=true`）—— 即已 bootstrap 过的 V1.3 production 库 —— 仅做 `CREATE TABLE IF NOT EXISTS`（对已存在表是 **no-op**）+ `SELECT 1 FROM information_schema.tables` 完整性校验。
     - 然后才走 `INSERT IGNORE INTO ${table}` 把每张 snapshot 表的数据行复制过来，`permissions` / `role_permissions` 因此被刷成包含 `INVENTORY_TRANSFER_CONFIRM` 的形态。
     - `CREATE TABLE IF NOT EXISTS` 的 no-op 是 V1.4-E2 在既有 MySQL 上的 wiring 缺口：snapshot 里 `inventory_transfers.business_date` / `inventory_checks.business_date` 列不会通过 DDL 落到 V1.3 live 表上；权限恰恰因为 snapshot 已含行而被 `INSERT IGNORE` 应用。
- 因此生产 v1.4.0 上线后看到的现象得到解释：权限类迁移通过，列类迁移不通过。

### Phase 2 — 修复设计（最窄、生产安全）

- 实施点：`server/database/mysql-adapter.js:173 createMySqlDatabase`。
- 行为：`bootstrapMySql(adapter, snapshot)` 之后追加对 **`adapter`** 本身调用同一份权威迁移实现：
  - `migrateV14E2BusinessDate(adapter)`；
  - `ensureV14E2ConfirmPermission(adapter)`；
  - `ensureV14E2CanonicalRolePermissions(adapter)`。
- 这些函数都从 `server/migrations/v14-e2-business-date.js` 直接 import —— 该模块是叶子节点、无其它 import，因此不引入循环依赖风险；不修改 `bootstrapMySql`，避免变成不受控的 schema-diff 引擎。
- 不重复实现，不复制 SQL；幂等性由各函数内部的列-存在性 probe 与 `INSERT OR IGNORE` 保证，所以 fresh / upgrade / 重复 init 三条路径共用同一份权威代码。
- 不修改 schema 范围、permission data migration 范围；不动 `production_orders.completion_date` / `inventory_transactions.business_date_origin` / 不增加索引。
- 不修改后端业务模块、handler、DTO、permission check、approval family；不动前端。
