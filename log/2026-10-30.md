### Facts established for the design, without a MySQL server

- The emitted MySQL DDL gives `customers.code VARCHAR(128)` under `utf8mb4_0900_ai_ci` with
  `UNIQUE (code)`, `customers.name LONGTEXT`, `customers.active BIGINT`, `credit_profile.credit_object_type
  LONGTEXT`, `credit_profile.effective_from VARCHAR(128)` and `credit_profile.effective_to LONGTEXT`. The
  probe drove `bootstrapMySql` with a recording mock adapter; the probe script lives in the local
  temporary directory and the repository was not changed.
- `credit_object_type` is written through `requiredCode`, which bounds it to 50 characters, restricts it to
  `[A-Za-z0-9_-]` and uppercases it. The MySQL group-key truncation boundary of 1024 bytes is therefore
  unreachable for the supported range, and a case-only collision of that field is impossible. The
  `LONGTEXT` type alone does not prove a collision, and the short current fixture alone does not prove the
  supported range; the production writer contract settles both.
- The `UNIQUE (code)` key and the `PRIMARY KEY (id)` are themselves under the accent- and
  case-insensitive collation, so two identities that differ only by case or accent cannot be stored on
  MySQL at all. This is a storage-level environment difference and is classified as such, not as a
  business result.
- The free-text `customers.name` is the one dimension where the engines can genuinely diverge, because
  the SQLite `LOWER` folds ASCII only while the MySQL collation folds case and accents. The Requirement
  registers this as an open decision; the gate measures it and never asserts cross-engine equality on it.

  boundaries, but its customers are `id.toUpperCase()` with the name `id`, so it contains neither a
  mixed-case code nor an accent nor a second Credit Object nor an ambiguous effective version. The gate
  therefore needs its own dedicated fixture helper that extends the shared world without modifying the
  shared fixture files, so that the frozen U2 E3 suite keeps its exact data.
- The strict TAP contract of the protected campaign is exact: one `TAP version 13` header, exactly one
  top-level plan, contiguous unique ids, plain `ok` records, every summary field exactly once and zero
  fail, cancelled, skipped and todo. The new suite must therefore be flat top-level with ten tests.

### Risk A — the Exact Identity Collation audit

The production path that was read: the exact identity input parsing in
`server/modules/credit-query-options.js` `readInput`; the identity predicate in
`buildAuthorizedRelation`; the free-text search over the derived search key columns with
`LIKE ? ESCAPE '!'`; the read scope resolver `server/modules/credit-scope.js`
`resolveCreditProfileReadScope` and `resolveCreditReadMode` with the predicate
`(cp.salesperson_scope_key = '*' OR cp.salesperson_scope_key = ?)`; the anchor shape guard
`server/modules/credit-anchor.js` `ensureCreditLockAnchor` and `sameShape`; and the MySQL physical
collations read from the emitted DDL.

The MySQL physical contract of the identity columns, all under `utf8mb4_0900_ai_ci` and therefore
case-insensitive: `customers.id` as the primary key, `customers.code` as a unique key,
`credit_profile.customer_id`, `credit_profile.credit_object_type`,
`credit_profile.credit_object_id`, `credit_profile.salesperson_scope_key` and
`credit_lock_anchors.anchor_key` as a unique key. SQLite declares no explicit collation and uses the
default `BINARY` comparison.

The seven answers:

1. the divergence is confined to the **exact identity filter**. The free-text search compares the
   derived, byte-exact search key columns and is engine-consistent; S04 and S10 prove it with **zero**
   divergent probes over the eleven approved probes;
2. the differing comparisons are the equality on the customer identity and the Credit Object identity
   under the identity column collation. The Credit Object type cannot differ, because the production
   input contract upper-cases it before the comparison;
3. **a wrong business identity cannot be returned.** On MySQL the customer identity primary key, the
   customer code unique key and the Credit lock anchor key unique key are case-insensitive, so two
   business identities differing only by case cannot coexist, and the anchor shape guard compares the
   stored shape with byte equality, so a case-variant identity is refused on write with
   `CREDIT_ANCHOR_SHAPE_CONFLICT`; on SQLite the reference lookup is byte-sensitive and refuses it with
   `404 客户不存在`. Each engine resolves inside an unambiguous identity space and resolves to the
   canonical identity;
4. the **authorization boundary is unaffected**. The scope predicate is conjoined in the same where
   clause and gates every candidate row, its bound value is derived from the server's own salesperson
   record and is written from that same value into the scope key, and the denied mode refuses before any
   query runs. The measured case-variant resolution returned `cus-w11-self`, inside the reader's
   authorized set of fifteen;
5. **no unauthorized disclosure is possible**, because the identity predicate can only narrow the
   already authorized relation, and the neutral response for an unknown and for an unauthorized
   identity stays byte-identical on both engines;
6. the **current Requirement does not state an identity case policy**. R-U3-SEARCH-03 defines the
   filter only as an equality comparison. The R-U3-GATE-04 open decision covered the customer-name
   search and was resolved by R-U3-SEARCH-01; it never covered the identity filter. The approved parity
   taxonomy of R-U3-GATE-03 does classify this case, as a test environment difference and as an
   acceptable database implementation difference, with the disposition that it is measured on both engines,
   reported, and never widens the authorized set;
7. the difference is therefore an **acceptable, documented known limitation**, not a business semantic
   inconsistency that must be corrected. Correcting it would require declaring one engine authoritative
   or changing the approved Search Fold or the literal search contract, both prohibited.

**Disposition:** `ACCEPTED_RESIDUAL`. The taxonomy already classifies and disposes of it, and the
condition it attaches — never widen the authorized set — is proven by the code analysis and by the S02,
S04, S08 and S10 results. No second Requirement was created; the audit conclusion is recorded in
R-U3-INV-06. The explicit business risk acceptance remains a user decision.
