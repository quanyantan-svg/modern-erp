# 最小重构设计说明

## 1. 重构目标

本项目不是把反编译代码逐行翻译，而是保留旧系统可解释的业务概念，用现代结构重新实现一条最小闭环。目标是让初学者能够运行、演示、阅读和继续扩展。

## 2. 新旧概念映射

| 旧系统 | 新系统 | 说明 |
|---|---|---|
| `SKY_Users` | `users` | 登录用户 |
| `SKY_Roles` | `roles` | 角色模板 |
| `SKY_Role_Permission` | `role_permissions` | 角色拥有的功能权限 |
| `SYS_CusA` | `customers` | 客户主档 |
| `SYS_GoodInA` | `products` | 货品主档 |
| `SDS_SoA` | `sales_orders` | 销售订单头 |
| `SDS_SoB` | `sales_order_items` | 销售订单明细 |
| `WF_AgentBox` 等 | 状态接口 + `audit_logs` | 练习版单级审核与操作轨迹 |
| 字符状态码 | `DRAFT/SUBMITTED/APPROVED/REJECTED` | 使用可读枚举代替魔法数字 |
| 权限位集合 | 权限代码关联表 | 牺牲少量存储，换取可读性 |

## 3. 分层结构

```text
React 页面
   ↓ JSON/HTTP
API 路由与权限校验
   ↓
业务规则与状态转换
   ↓
SQLite 表和事务
```

前端不直接接触数据库。后端不相信前端计算的订单总额，而是根据明细数量和单价重新计算。涉及订单头和多条明细的写入全部放在同一个事务中：要么一起成功，要么一起失败。

## 4. 权限模型

练习版使用 RBAC（Role-Based Access Control，基于角色的访问控制）：

```text
用户 → 一个角色 → 多项权限 → 决定菜单和 API 操作
```

前端隐藏无权菜单是为了改善体验；真正的安全检查仍在后端完成。即使有人绕过页面直接调用 API，后端也会返回 403。

## 5. 订单状态机

```text
新建
 ↓
DRAFT 草稿 ──提交──→ SUBMITTED 待审核
   ↑                         │
   └──修改后保存── REJECTED ←┤ 驳回
                             │
                             └──通过──→ APPROVED 已审核
```

状态机的意义是明确允许的变化。系统不会允许已审核订单再次提交，也不会允许草稿直接审核。

## 6. 为什么审核不扣库存

旧 ERP 中销售订单 `SDS_SoA/B` 与销售出货 `SDS_OutA/B` 是两种单据。订单代表双方约定，出货才代表仓库实物离开。因此本阶段只做到订单审核，不修改货品库存。下一阶段加入出货单时，库存扣减应由出货审核/过账触发。

## 7. 金额设计

金额以“分”为整数保存，例如 2599.00 元保存为 `259900`。这避免二进制浮点数产生 `0.1 + 0.2` 不精确的问题。数量仍可使用小数，以适应重量、长度等计量方式。

## 8. 有意缩小的范围

- 一个用户只属于一个角色；
- 单级审核，不含会签和多级流程图；
- 单一组织、人民币；
- 库存数量是基础资料上的演示字段，没有库存流水；
- 没有连接旧库，也没有迁移生产数据；
- 运行目标是本地教学，不是公网生产环境。

这些限制不是遗漏，而是为了先验证最小业务闭环。后续可以按“组织与数据范围 → 多级审批 → 出货与库存流水 → 应收”的顺序扩展。
