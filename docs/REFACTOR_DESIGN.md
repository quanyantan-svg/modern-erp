# Modern ERP 完整重构设计说明

## 1. 重构目标

本项目不是对反编译代码进行逐行翻译，而是先系统梳理旧 ERP 的业务概念、数据关系、权限边界和单据状态，再以现代技术栈进行模块化重建。重构目标是尽可能完整覆盖原系统可识别的核心能力，形成可运行、可验证、可迁移、可维护并可继续扩展的 Modern ERP。

完整重构遵循以下原则：

- 业务覆盖：基础资料、销售、采购、仓储、财务、生产、质量、CRM、项目、OA、预警和报表均纳入统一规划；
- 数据一致性：单据头、明细、库存、账款和凭证通过事务及状态机保证一致；
- 权限一致性：菜单权限、API 权限和审计记录形成闭环；
- 模块边界：前后端均按业务域拆分，公共能力集中复用，避免单文件持续膨胀；
- 可验证性：关键状态转换、金额计算、库存变化和越权访问必须具备自动化测试；
- 可迁移性：保留旧表到新模型的映射，为历史数据清洗、转换、校验和回滚提供依据。

## 2. 新旧概念映射

| 旧系统 | 新系统 | 说明 |
|---|---|---|
| `SKY_Users` | `users` | 登录用户 |
| `SKY_Roles` | `roles` | 角色模板 |
| `SKY_Role_Permission` | `role_permissions` | 角色拥有的功能权限 |
| `SYS_CusA` | `customers` | 客户主档 |
| `SYS_GoodInA` | `products` | 货品主档 |
| `SDS_SoA` | `sales_orders` | 销售订单头 |
| `SDS_SoB` | `sales_order_items` | 销售订单明细 |
| `WF_AgentBox` 等 | 状态接口 + `audit_logs` | 练习版单级审核与操作轨迹 |
| 字符状态码 | `DRAFT/SUBMITTED/APPROVED/REJECTED` | 使用可读枚举代替魔法数字 |
| 权限位集合 | 权限代码关联表 | 牺牲少量存储，换取可读性 |

## 3. 分层结构

```text
React 页面
   ↓ JSON/HTTP
API 路由与权限校验
   ↓
业务规则与状态转换
   ↓
SQLite 表和事务
```

前端不直接接触数据库。后端不相信前端计算的订单总额，而是根据明细数量和单价重新计算。涉及订单头和多条明细的写入全部放在同一个事务中：要么一起成功，要么一起失败。

## 4. 权限模型

系统使用 RBAC（Role-Based Access Control，基于角色的访问控制）：

```text
用户 → 一个角色 → 多项权限 → 决定菜单和 API 操作
```

前端隐藏无权菜单是为了改善体验；真正的安全检查仍在后端完成。即使有人绕过页面直接调用 API，后端也会返回 403。

## 5. 订单状态机

```text
新建
 ↓
DRAFT 草稿 ──提交──→ SUBMITTED 待审核
   ↑                         │
   └──修改后保存── REJECTED ←┤ 驳回
                             │
                             └──通过──→ APPROVED 已审核
```

状态机的意义是明确允许的变化。系统不会允许已审核订单再次提交，也不会允许草稿直接审核。

## 6. 单据与库存边界

旧 ERP 中销售订单 `SDS_SoA/B` 与销售出货 `SDS_OutA/B` 是两种单据。订单代表双方约定，出货才代表仓库实物离开。因此销售订单审核不直接扣减库存；销售出库确认负责扣减库存并形成库存流水、应收记录及后续凭证依据。采购入库、退货、调拨和生产领退料遵循同样的“业务单据确认后影响库存”原则。

## 7. 金额设计

金额以“分”为整数保存，例如 2599.00 元保存为 `259900`。这避免二进制浮点数产生 `0.1 + 0.2` 不精确的问题。数量仍可使用小数，以适应重量、长度等计量方式。

## 8. 完整重构范围与验收标准

重构不以演示页面数量作为完成依据，而以下列结果作为验收标准：

- 原系统中能够识别的核心模块均有新模型、API、页面、权限和操作记录；
- 销售、采购、入库、出库、退货、调拨、生产、应收应付和会计凭证可以形成跨模块闭环；
- 支持多角色、多级审批、组织与数据范围控制，关键操作可以追溯；
- 库存以仓库和货品维度维护，并由库存流水重算、核对和审计；
- 金额、税额、成本和余额使用确定性计算规则，结账后受到期间控制；
- 旧库迁移具备字段映射、数据清洗、批次导入、总量核对和失败回滚方案；
- 核心业务具备自动化测试、接口冒烟测试和可重复的演示数据初始化；
- 代码按业务域拆分，禁止把新增模块继续堆叠到单一前端或后端文件；
- 部署配置、密钥、日志、备份和恢复满足从本地验证走向正式环境的要求。

当前 SQLite 环境用于开发和自动化验证，不代表最终部署边界。后续迭代必须持续对照旧系统清单补齐差异，直至模块、数据和流程验收全部通过。
