# V1.3 Phase 7B — MySQL concurrency contract

## Scope and result

Phase 7B hardens the frozen V1.3 functional core for independent Node processes using independent MySQL 8 sessions. It adds no business capability. SQLite retains its existing `BEGIN IMMEDIATE` behavior; SQLite is not used as evidence of MySQL concurrency correctness.

The acceptance harness starts eight persistent child processes. Every process owns a separate application adapter, worker thread, and MySQL connection. Contending commands therefore reach InnoDB from independent sessions and cannot be serialized by the normal single adapter Worker queue. A ninth process uses a zero-retry policy to prove controlled retry exhaustion.

## Isolation and locking

Every MySQL session explicitly uses `READ COMMITTED`, UTC, and a bounded two-second `innodb_lock_wait_timeout`.

All application write transactions acquire `mysql_transaction_gates(gate_id=1)` with `SELECT ... FOR UPDATE` and retain that row lock until commit or rollback. The lock order is:

1. For idempotent requests only, acquire the MySQL advisory lock derived from operation, document and idempotency key.
2. Begin the InnoDB transaction.
3. Lock the singleton application-write gate row.
4. Read/check and mutate business rows, tracked identities, valuation pools, ledgers, vouchers and audit records.
5. Commit or roll back.
6. Release the idempotency advisory lock.

This is the minimum safe Phase 7B baseline for the current application, whose invariants often span several tables and whose shared `transaction()` boundary covers the critical confirmations, postings, settlements, closes, activation and reversals. It is deliberately conservative: independent write transactions serialize even when they touch unrelated documents. That sacrifices throughput, not correctness. Phase 7C may introduce deterministic resource-key locks after workload measurement, provided it preserves this contract.

No in-process mutex is part of the correctness model. InnoDB owns the write serialization, and MySQL unique constraints remain the last line of defense for document allocations, source-linked vouchers, idempotency records, tracked identities and other natural keys.

## Mutation classification

| Critical mutation | Classification after Phase 7B | Enforcement |
|---|---|---|
| Document status confirm/post/approve/reverse | `SAFE_BY_ROW_LOCK` | Transaction gate held through status check, all effects and status update |
| Stock availability and remaining source quantity | `SAFE_BY_ROW_LOCK` | Check and update occur under the same gated transaction |
| NONE/LOT/SERIAL consumption | `SAFE_BY_ROW_LOCK` + `SAFE_BY_UNIQUE_CONSTRAINT` | Gate protects balances; existing identity/source uniqueness rejects duplicates |
| Valuation quantity/value pools and WIP | `SAFE_BY_ROW_LOCK` | Pool reads, movements, cache and GL effects share the transaction |
| AR/AP allocation, credits, refunds and write-offs | `SAFE_BY_ROW_LOCK` | Open balance and allocation effects share the transaction |
| Document sequences | `SAFE_BY_ATOMIC_UPDATE` + `SAFE_BY_IDEMPOTENCY` | MySQL upsert increments atomically; allocation key uniquely replays a number |
| Request idempotency | `SAFE_BY_IDEMPOTENCY` + `SAFE_BY_UNIQUE_CONSTRAINT` | Per-key advisory lease closes the pre-transaction race; record key is unique |
| System voucher creation | `SAFE_BY_UNIQUE_CONSTRAINT` + `SAFE_BY_ROW_LOCK` | Existing source uniqueness plus gated transaction |
| Inventory/accounting close vs posting | `SAFE_BY_ROW_LOCK` | Both take the same transaction gate; post-open check cannot straddle close |
| Go-live activation vs normal posting | `SAFE_BY_ROW_LOCK` | Activation and business transaction serialize on the gate |

No critical Phase 7B mutation remains classified `NEEDS_FIX` under the conservative gate contract.

## Idempotency under concurrency

`idempotencyReplay()` takes a database advisory lock whose 64-byte-safe name is a SHA-256 derivative of operation type, document ID and key. A first request retains the lease until its transaction commits or finally rolls back. A concurrent equal request waits, then reads and returns the committed result. A changed fingerprint returns HTTP conflict. Transaction retry keeps the same key/lease and re-runs the whole callback; it cannot expose a partially committed effect.

Advisory lock acquisition is bounded at ten seconds. Failure is a controlled service-unavailable response, not an unbounded wait.

## Deadlock and timeout policy

Only MySQL deadlock (`ER_LOCK_DEADLOCK`, errno 1213, SQLSTATE 40001) and lock-timeout (`ER_LOCK_WAIT_TIMEOUT`, errno 1205) failures are retryable. The complete transaction callback is retried at most `ERP_DB_TX_RETRY_MAX` times (default 3, accepted range 0–10) with bounded exponential waits of 20, 40, 80 milliseconds, capped at 250 milliseconds. The same closure and idempotency identity are retained.

Business-rule and validation failures are never retried. On final retry exhaustion the original database error is returned with `transactionRetryExhausted=true` and the attempt count. Rollback/release failures do not hide the authoritative failure.

## Real MySQL race coverage

The Phase 7B suite uses real row-lock waiting across processes. It verifies:

- retry after a real gate-row lock timeout, controlled zero-retry exhaustion, and one-attempt business failures;
- same-key/same-payload exact replay and same-key/different-payload conflict using the production idempotency helpers;
- single-effect status transitions for Purchase Receipt, Sales Delivery, Sales Invoice, Supplier Bill, Material Issue, Production Receipt, Inventory Count and reversal categories;
- stock 10 vs two consumes of 7 for NONE and LOT, plus two consumers of one SERIAL identity;
- SO delivery, PO receipt, delivered-unbilled invoice and received-unbilled bill limits;
- AR collection, AP payment, credit application, refund and write-off open-balance limits;
- moving-average, lot and serial quantity/value conservation, including exact zero-value full depletion;
- material support, operation input, final GOOD allowance and material-return limits;
- 40 parallel allocations over eight sessions, uniqueness, ownership and idempotent number replay;
- inventory close, accounting close and settlement-vs-close outcomes;
- go-live activation vs first normal business operation;
- original-vs-reversal and double-reversal ordering;
- post-stress nonnegative balances, effect uniqueness and the production System Health checker in check-only/no-repair mode.

The contention matrix uses small domain-shaped rows for deterministic race orchestration while exercising the production transaction, idempotency, sequence and System Health code. Existing Phase 0–7A suites continue to exercise the complete business documents and accounting effects. Because all relevant business handlers enter the same database-enforced transaction gate, their multi-table effects inherit the tested serialization contract.

## Close/post and activation outcomes

Close and post cannot pass each other inside the protected interval. If posting owns the gate first, it commits and the later close includes it. If close owns the gate first, later posting observes the closed period and is rejected. The same order applies to accounting close versus invoice, bill or settlement posting.

Opening-batch post/activation holds the gate until the opening state is complete. A normal first transaction either observes `ACTIVE` after activation commits or is rejected before producing an effect. Opening changes remain prohibited after activation by the existing state rules.

## Known limits

- The singleton write gate intentionally limits write throughput and is not a Phase 7C performance design.
- Reads outside a write transaction are not snapshot-serialized; authoritative mutation checks must remain inside `transaction()`.
- MySQL advisory locks are connection-scoped. The adapter releases tracked locks after commit/final rollback, and MySQL also releases them if a connection terminates.
- The stress shape validates correctness with eight sessions and 40 parallel number allocations. It is not a capacity benchmark.
- The test database is disposable and is reset by the gate. Production is never contacted.
