### MRP OVERLAP ROOT CAUSE

The overlap is **presentation, not data**.

1. **Tabbed surface ambiguity** — `PlanningHub` exposes a tab pair (`计划预测` / `MRP 物料需求计划`) with the same `Panel` title and subtitle, so users read them as the same concept.
2. **Shared conceptual model** — both are "planning artifacts". The user cannot articulate: forecast is the *human input*; MRP is the *engine*; material requirements plan is the *output view*.
3. **Mobile launcher placement** — both live under `基础资料` (slate accent) instead of being highlighted as the chain they actually drive (`计划与生产`).
4. **Result table is a "table" not a "plan"** — the full required columns are already there (`gross_requirement`, on_hand, open_po, open_prod, net, MAKE/BUY, suggested qty, need_by_date, warning, trace). But the table is one wide row per product, no derived mobile tabs, no time-grouping, no shortage filter.

Backend already supports everything required. **No new data model is needed.**

# PROBLEM 2 — DELETE / ARCHIVE / DISABLE

## MASTER DATA DELETE RULE

**Rule:**
- Unreferenced (no FK pointing at this row) → **HARD-DELETE ALLOWED** for `MANAGE` role.
- Referenced by any business record → **cannot hard-delete**; use `active = 0` (the existing soft-disable column on every master-data row, see `server/db.js:650–1143`).
- All seven canonical master-data families (`customers`, `suppliers`, `products`, `warehouses`, `boms`, `product_routings`, `departments`, `aux_projects`, `currencies`) **already carry `active INTEGER NOT NULL DEFAULT 1`**. No new schema column required.
- List filters must default to `active = 1` and offer a "显示已停用" toggle that reveals inactive rows read-only.

## BUSINESS DOCUMENT DELETE RULE

**Three lifecycle buckets**, all already enforced:

| Bucket | Behavior |
| --- | --- |
| DRAFT with no downstream/economic/stock/accounting effect | **Hard-delete allowed** (e.g. `contact`, `sales_activity`, `timesheet`, `product_routing_operation`) |
| SUBMITTED / APPROVED / RELEASED | No physical delete. Cancel / reject only. |
| CONFIRMED / COMPLETED / POSTED | **Never delete**. Use business reversal / cancellation where supported. |

No cascade deletes are introduced anywhere in the audit (read `server/migrations/extended-schema.js` and M11/M12/M13/M14 modules — existing `ON DELETE CASCADE` is limited to header → items, never header → other-documents).

## REFERENCED DATA ARCHIVE RULE

**Rule:** No `archived_at` / `deleted_at` columns required.
- Status enum already provides the lifecycle gate.
- For `SUBMITTED` and beyond, status is the archive; the row stays queryable, listable, and traceable, but no mutation is permitted.
- Master data uses `active = 0` (already present on all eight families).

## SCHEMA CHANGES PROPOSED

| Change | Required? | Notes |
| --- | --- | --- |
| New `archived_at` / `deleted_at` columns | **NO** | Status + `active` are sufficient |
| New `is_active` columns | **NO** | `active` already exists on every master-data table (`server/db.js` migrations and `migrations/*.js`) |
| Any new hard-delete cascade | **NO** | Forbidden by audit contract |
| 7 new table-level `*_archive` mirror tables | **NO** | No archive mirror required |

| CONFIRMED | 已确认 | 已确认 |
| COMPLETED | 已计算 / 已完成 | 已完成 (MRP run specifically: 已完成) |
| CANCELLED | 已取消 | 已取消 |
| CLOSED | 已结账 | 已结账 |
| REOPENED | 已重新开放 | 已重新开放 |
| `active=1/0` (master) | 启用 / 停用 | 启用 / 停用 (already correct) |

**Decision:** Status enum → Chinese label mapping moves to a single `src/lib/status.js` (`STATUS_LABEL = { DRAFT: '草稿', ... }`); every page imports from it. No raw enum (`row.status === 'CANCELLED'`) comparisons for display; comparisons happen via `statusLabel(row.status)`.

### Domain-specific mapping exceptions

- Forecast: `ACTIVE → 已生效` (different from "启用" because activation is a workflow action, not a flag).
- BOM: `ACTIVE / DISCONTINUED → 启用 / 已停用` (already distinct from forecast).
- Routing: `ACTIVE / INACTIVE → 启用 / 已停用`.
- Period closure: `OPEN / CLOSED → 未结 / 已结账` (no separate "reopen" enum; reopen is a verb on a CLOSED record).
