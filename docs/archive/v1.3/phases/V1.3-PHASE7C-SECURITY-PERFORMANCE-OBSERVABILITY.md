## Scope and freeze

This phase changes operational hardening only. It adds no ERP feature, role, permission, approval family, or business-state transition. The Phase 7B singleton InnoDB transaction gate remains in place. The four pre-existing untracked documents/scripts recorded during preflight were not modified.

## Security model

The application uses opaque bearer sessions. A login token is generated with `crypto.randomBytes` (32–64 bytes), only its SHA-256 digest is stored, and the database session has an absolute expiry (default 12 hours, configurable from 1–168 hours). Passwords are salted and hashed with Node's `scrypt`; plaintext passwords and bearer tokens are not written to application logs or audit records. Logout deletes the session digest. Authentication joins the active user on every request, so expired sessions and sessions belonging to disabled users are rejected.

There is no cookie authentication, so cookie flags and CSRF tokens are not applicable. Browsers do not automatically attach the bearer token cross-site, and the server emits no permissive CORS header. There is also no session-signing secret: sessions are server-side random opaque tokens, not signed client claims, so a production session secret is not applicable.

The login abuse control locks by normalized username after five failed attempts for 15 minutes by default. Phase 7C fixed the order of operations so the username is parsed before checking the lock. Before this fix, the pre-check always looked up an empty username and a locked account could attempt a correct password. Locked requests now remain blocked and include `Retry-After`.

Administrative changes to another user's password, role, or active state revoke that user's existing sessions. Sensitive user fields are allowlisted; fields such as `password_hash` cannot be mass-assigned. Boolean active state must be an actual JSON boolean.

## Authorization and direct-object access

Authorization remains enforced in backend handlers through `allow`/`allowAny`; frontend navigation is not an authority. The Phase 7C suite directly verifies:

- unauthenticated `POST /api/orders` is rejected;
- a role with only `ORDERS_VIEW` cannot create or update an order, including a guessed ID;
- that view-only role cannot read bank accounts or System Health;
- sensitive user fields cannot be changed by an otherwise authorized administrator request containing unsupported fields;
- a rejected mass-assignment request leaves the database unchanged.

The broader frozen suite continues to cover the canonical roles and domain-specific authorization. No permission was broadened in 7C.

## Input and HTTP hardening

JSON bodies are limited to 1,000,000 bytes by default (`HTTP_JSON_LIMIT_BYTES`, constrained to 1 KiB–10 MB), must use `application/json` when non-empty, must be a JSON object, and produce controlled 400/413/415 responses. Authentication and user-management inputs use explicit field allowlists. SQL values continue to use prepared parameters. Existing domain validators retain integer-cent, quantity, date, enum, and state checks.

Static file resolution now uses `path.relative` containment rather than a string-prefix check. API responses use `Cache-Control: no-store`. Responses include CSP, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, and a restrictive Permissions Policy. The API emits no `Access-Control-Allow-Origin` header and no framework fingerprint header. The existing SPA fallback is preserved.

Known input limit: several old business handlers accept only their documented fields by selecting values explicitly but do not yet reject every unknown non-sensitive field. Phase 7C rejects unknown fields on the most sensitive authentication/user surfaces and preserves frozen business compatibility elsewhere.

## Logging and error observability

The production entry point emits one-line JSON records with `timestamp`, `level`, `service`, and `event`. Mutating requests are logged at INFO; requests above `SLOW_REQUEST_MS` (default 1000 ms) are WARN. Every response carries `X-Request-Id`; a caller-supplied ID is accepted only when it matches a constrained 8–100 character format.

Unhandled errors log request ID, method, route, safe user ID, category, and stack server-side at ERROR. The client receives only a generic message and the request ID. The logger recursively redacts authorization, cookies, passwords, secrets, tokens, API keys, and database-password-shaped fields. It also masks bearer or assignment-shaped secrets embedded in strings. Request bodies and headers are never logged.

MySQL queries over `SLOW_QUERY_MS` (default 500 ms) log only duration, a coarse operation/table label, and a SHA-256 SQL fingerprint. SQL parameters and raw SQL are not logged.

The immutable business audit trail remains separate and unchanged.

## MySQL performance and singleton-gate decision

Preflight found no `ERP_DB_HOST`, `ERP_DB_PORT`, `ERP_DB_NAME`, `ERP_DB_USER`, `ERP_DB_PASSWORD`, or reset opt-in in this environment. Both MySQL Phase 7A and Phase 7B correctly refused to run. No production or unknown database was contacted.

Phase 7C adds `pnpm test:mysql:performance`. It requires all MySQL variables, `ERP_MYSQL_TEST_ALLOW_RESET=true`, and a database name containing `test`, `phase7c`, or `disposable`. It creates 20 genuinely independent MySQL sessions and measures the unchanged singleton gate at 1/5/10/20 writers using different resource rows. Each level records throughput, p50/p95/p99/max latency, estimated queue wait, errors, and error rate. A fixed 5 ms transaction body makes serialization cost observable rather than measuring network noise alone. The harness is currently environment-blocked and therefore has no legitimate result to publish.

### Decision

**KEEP GLOBAL GATE.** There is no Phase 7C evidence proving the current gate unacceptable, so lock granularity was not weakened or speculatively redesigned. This is a conservative interim decision, not a completed performance acceptance. Running the 1/5/10/20 benchmark and the full Phase 7B suite on disposable MySQL is mandatory before Phase 7D.

Provisional SME acceptance thresholds for that run are: <1% error rate, no deadlock/timeout at supported concurrency, representative read p95 <= 500 ms, mutation p95 <= 750 ms, and singleton-gate p95 <= 1,000 ms at 20 writers with at least 20 committed transactions/second. These are operational targets, not measured results.

## Dataset, endpoint performance, EXPLAIN, and indexes

A realistic disposable MySQL dataset and MySQL `EXPLAIN` evidence could not be produced without a disposable MySQL connection. Consequently no latency, query-plan, or lock-wait number is claimed for inventory, movements, outstanding SO/PO, AR/AP, GL, System Health, trace, MRP, WIP/cost, invoice, bill, valuation, aging, or reconciliation endpoints. No speculative index was added.

Existing protections observed during the audit include capped decision reports, capped AR/AP lists, capped party lookups, source/foreign-key indexes, business-date valuation indexes, product/warehouse lot indexes, serial location indexes, voucher-source indexes, and settlement open-item indexes. Some older master-data and analytical list routes remain unbounded and are a known performance risk; changing their default result semantics without MySQL data and UI acceptance evidence was intentionally deferred.

Required acceptance dataset profile for the disposable MySQL run:

- at least 10,000 products, 2,000 customers, 1,000 suppliers, and 20 warehouses;
- at least 50,000 SO/PO headers and 250,000 lines;
- at least 1,000,000 inventory/valuation movements;
- at least 100,000 AR/AP open/history items and 250,000 voucher entries;
- at least 100,000 lot/serial movements and genealogy links;
- at least 10,000 production orders/operations;
- at least 50,000 invoices/bills.

`EXPLAIN ANALYZE` must be captured for every query exceeding the provisional p95 target. Only plan-backed index or query changes should follow.

## Known limits and deferred risks

1. MySQL performance acceptance is incomplete until a disposable MySQL 8 instance is supplied.
2. The global gate is retained; its maximum sustainable write throughput is unknown in this environment.
3. Old unbounded list/report routes require evidence-led pagination after realistic-data UI testing.
4. Password policy remains the compatible six-character minimum for existing administration flows. Scrypt protects storage, but a stronger production password policy is recommended for a later explicitly approved compatibility change.
5. Bearer tokens live in browser local storage. CSP and same-origin policy reduce exposure, but an HttpOnly-cookie migration would require a deliberate CSRF/authentication design change and is outside the frozen phase.
