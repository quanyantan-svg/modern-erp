# 方天 ERP 系统入门梳理（零基础版）

## 1. 先理解：ERP 到底是什么

ERP 是 Enterprise Resource Planning（企业资源计划）的缩写。可以先把它理解成企业共同使用的一本“电子总账本 + 工作流系统”。销售、采购、仓库、生产、质量和财务不再各自记 Excel，而是在同一个系统里记录同一批业务。

例如，客户订购 100 件产品，不只是销售部门记一条数据：

1. 销售建立销售订单；
2. 系统检查库存是否足够；
3. 不足时，计划部门计算需要生产多少、采购多少原料；
4. 采购向供应商下单；
5. 仓库验收原料并增加库存；
6. 生产领料、加工、报工；
7. 质量部门检验；
8. 成品入库后，仓库按销售订单出货；
9. 财务形成应收款、应付款和会计凭证。

ERP 的价值不是“有很多页面”，而是让上述记录能够相互引用、相互约束和追踪。

## 2. 阅读本系统前必须知道的词

### 2.1 模块

模块是一组解决同类业务问题的功能。例如采购模块负责请购、询价、采购订单和收货；库存模块负责入库、出库、调拨和盘点。

### 2.2 基础资料

基础资料是会被许多单据重复引用的公共档案，例如客户、供应商、货品、单位、仓库、币种、税率、结算方式、员工和部门。基础资料不是一次交易，但没有它们就无法填写交易单据。

### 2.3 单据

单据是一笔业务活动在系统中的记录，相当于纸质表单的电子版。例如采购订单、销售订单、领料单、入库单和收款单。

大部分单据包含：

- 单据头：整张单共有的信息，如单号、日期、客户、部门和状态；
- 单据明细：每一行货品的信息，如货号、数量、单价和金额。

本系统经常使用 `A` 表保存单据头、`B` 表保存明细。例如 `SDS_SoA` 是销售订单头，`SDS_SoB` 是销售订单明细。

### 2.4 审核、过账和月结

- 保存：把草稿写入数据库；
- 提交：表示填写人认为单据已经完成；
- 审核：有权限的人确认业务有效；
- 反审：撤销审核；
- 过账：让单据正式影响库存或账务；
- 结账：确认应收或应付金额；
- 月结：关闭某个月份，防止之后随意修改历史数据。

不同类型单据不一定拥有全部状态。代码中大量使用 `0`、`1`、`2`、`3`、`4`、`6` 等字符表示状态，实际中文含义需结合每种单据的参数配置确认，不能假设所有单据的数字含义相同。

### 2.5 API（接口）

API 可以理解为“其他程序使用系统功能的窗口”。人在浏览器中填写页面；手机、MES、看板或第三方系统则通过 API 发送 JSON 数据。例如 `POST /api/SDS_So` 可以提交销售订单数据。

API 不是数据库，也不是页面。它位于调用方和业务逻辑之间，负责接收参数、检查身份和权限、调用业务逻辑，再返回结果。

### 2.6 权限

权限回答三个问题：

1. 你能否进入某个功能？
2. 进入后能执行查询、新增、修改、删除、审核中的哪些动作？
3. 你能看到本人、部门、本机构还是全部数据？

## 3. 系统模块地图

以下分类依据页面目录、反编译类名和现有知识库。英文缩写是程序内部代号，不必死记。

| 业务领域 | 代码前缀 | 解决的问题 | 代表性内容 |
|---|---|---|---|
| 系统与基础资料 | `SYS`、`SKY`、`HR` | 规定“公司里有哪些人、物、组织和规则” | 用户、组织、部门、角色、客户、供应商、货品、单位、仓库、币种、税率、结算方式、系统参数 |
| 采购管理 | `POS` | 企业需要什么、向谁买、何时到货、买了多少 | 请购、询价、采购订单、采购变更、采购验收、退货、采购跟踪 |
| 销售管理 | `SDS` | 客户要什么、卖多少、何时交货、实际出了多少 | 报价、销售订单、订单变更、折扣、出货、退货、销售分析 |
| 仓储库存 | `WHS` | 仓库里有什么、在哪里、数量如何变化 | 库存初始化、调拨、调整、盘点、报废、借用、条码、即时库存、月结 |
| 产品结构 | `BOM` | 一个产品由哪些原料和零件组成、经过哪些工作中心 | BOM、工程 BOM、工作中心、工作站、产能、标准工时 |
| 需求与物料计划 | `EPS`、MRP 页面 | 根据订单、预测和库存计算要采购什么、生产什么 | 物料需求分析、采购建议、生产建议、订单排程 |
| 生产订单 | `MOS` | 决定生产什么、领多少料、完工多少 | 生产计划/制令、计划变更、生产领料、裁切、成品入库、在制品 |
| 制造执行 | `MMS`、`CNC`、MES | 管理工艺、机台、工序、人员报工和现场数据 | 工艺路线、工序作业、机台排程、设备、模具、报工、RFID、数控机采集 |
| 品质管理 | `QC` | 来料、加工过程和成品是否合格，异常如何整改 | 检验单、过程检验、完工检验、不良记录、质量异常、返工和改善 |
| 应付管理 | `APS` | 公司欠供应商多少钱、何时付款 | 应付结账、发票、付款、核销、账龄分析 |
| 应收管理 | `ARS` | 客户欠公司多少钱、何时收款 | 应收结账、发票、收款、核销、账龄分析 |
| 总账会计 | `GLS`、`GLA` | 把各业务转成会计记录并生成财务报表 | 会计凭证、试算平衡、现金流、资产负债表、损益表、月末结转 |
| 固定资产 | `FAS` | 管理设备等长期资产的增加、变更、折旧和处置 | 资产初始化、资产卡片、调整、折旧、台账 |
| 预算与票据 | `BUD`、`BIL` | 控制预算以及应收/应付票据 | 预算、支票、票据到期计划 |
| OA、CRM、项目 | `OA`、`OA_CRM`、`OA_ITEM` | 管理客户跟进、办公事务和项目任务 | CRM 客户、联系记录、项目、任务、进度、费用和协作 |
| 工作流 | `WF`、`WFS` | 决定一张单由谁审批、按什么顺序审批 | 流程设计、待办、已办、代理、会签、抄送、通知、动态表单 |
| PLM | `PLM` | 管理产品图纸、技术文件、物料结构和发布 | 文档目录、版本、权限、发布、接收、设计 BOM |
| 报表与看板 | `Report`、`Board`、`KB` | 把业务数据汇总给管理人员查看 | 销售分析、库存报表、生产状态、质量异常、绩效看板 |

`AMA`、`GRC`、`MOT` 等少量前缀在代码中存在，但仅凭现有反编译文件无法可靠展开全部业务含义。正式报告中应标为“待数据库菜单名称确认”，不要根据英文缩写随意编造。

## 4. 各模块如何串联

### 4.1 所有流程的地基：基础资料

业务开始前，系统先要有组织、用户、客户、供应商、货品、仓库和会计参数。采购订单和销售订单并不会重复保存完整客户档案，而是保存客户或供应商的编号/ID并引用基础资料。

所以基础资料出错会向后影响整条链。例如货品单位配置错误，采购数量、库存数量、生产领料和销售出货都可能错误。

### 4.2 采购到付款（P2P）

典型链路如下：

```text
内部提出需求
  → 请购单 POS_RePoA/B
  →（可选）询价/比价 POS_AskpriceA/B
  → 采购订单 POS_PoA/B
  → 到货与采购验收 POS_RecA/B
  →（需要时）来料质量检验 QC
  → 库存增加
  → 应付结账 APS_AccountA/B
  → 供应商发票 APS_InvoiceA/B
  → 付款/核销 APS_ReceiptA/B
  → 总账凭证 GLS_VocA/B
```

“请购”只是公司内部说需要购买；“采购订单”才是向供应商下达购买要求；“验收”表示货到了；“应付”表示公司因此欠供应商钱。这几步不能混为一张表，因为它们发生在不同时间，也由不同岗位负责。

代码中存在 `POS_RepoToPo`，说明系统支持把请购资料带入采购订单，而不是重新手工录入。采购跟踪报表则用于比较订购量、到货量和未交量。

### 4.3 销售到收款（O2C）

```text
客户询价
  → 销售报价 SDS_QuotA/B
  → 销售订单 SDS_SoA/B
  →（库存不足时触发采购或生产计划）
  → 销售出货 SDS_OutA/B
  → 库存减少
  → 应收结账 ARS_AccountA/B
  → 客户发票 ARS_InvoiceA/B
  → 收款/核销 ARS_ReceiptA/B
  → 总账凭证 GLS_VocA/B
```

代码中存在 `SDS_Sob_ToOut`，表示销售订单明细可以转为出货单。订单跟踪报表把订单、生产/采购进度、出货和回款联系起来。退货、折扣、订单变更则以独立单据保留修改痕迹。

### 4.4 库存是采购、销售和生产的共同中枢

库存不是只有一个“当前数量”。它必须记录数量为什么变化：

- 采购验收：原料增加；
- 销售出货：商品减少；
- 生产领料 `MOS_OutA/B`：原料减少；
- 生产入库 `MOS_RecA/B`：成品增加；
- 仓库调拨 `WHS_MoveA/B`：一个仓减少、另一个仓增加；
- 盘点 `WHS_CouA/B`：账面数量和实物数量比较；
- 调整 `WHS_AdjA/B`：对差异进行正式修正；
- 报废：库存减少并记录原因。

库存月结会保存月末结果并锁住历史期间。代码明确阻止修改结账日及以前的数据，也要求反结转按月份倒序进行。这是为了避免今天修改三个月前的数量后，财务成本全部变化。

### 4.5 计划、生产、质量和库存

```text
销售订单/销售预测
  + 当前库存
  + 已采购但未到货数量
  + 已安排但未完工数量
  + BOM 用料关系
          ↓
      MRP 需求计算（EPS）
       ↙              ↘
采购建议 MRP_Cmd_Pos   生产建议 MRP_Cmd_Mos
       ↓                ↓
   采购订单          生产计划/制令 MOS_PlanA/B
                         ↓
                 生产领料 MOS_OutA/B
                         ↓
              工艺、排程、报工 MMS_Crafts/Work
                         ↓
                   过程/完工检验 QC
                         ↓
                 成品入库 MOS_RecA/B
                         ↓
                  可用于销售出货
```

MRP（Material Requirements Planning，物料需求计划）解决的问题是：“为了按期完成订单，扣除已有库存后，还差多少原料，需要何时采购或生产？”BOM 则相当于产品配方。例如 1 台设备需要 2 个零件 A、4 个零件 B，生产 10 台时先计算理论需求，再扣减现有库存。

MOS 更偏生产订单和物料进出；MMS 更偏车间现场、工艺、机台、人员和工序执行。两者共同构成制造管理。

### 4.6 业务最终进入财务

采购、销售、库存和生产记录的是“发生了什么业务”；财务记录的是“这件事对金额和会计科目有什么影响”。

- 采购验收可能形成应付；
- 销售出货可能形成应收和销售成本；
- 生产领料、入库和库存结转参与产品成本；
- 固定资产产生折旧；
- 应收收款和应付付款减少往来余额；
- 最终由总账凭证汇总到资产负债表、利润表和现金流量表。

现有代码表明库存月结、成本结转和总账月末处理存在先后约束，因此财务不是独立的最后一步，而是在限制前面业务数据能否继续修改。

## 5. 表、单据、接口和权限是什么关系

以销售订单为例：

```text
用户进入“销售订单”菜单
  → 菜单对应一个功能 ID（func_id）
  → 权限系统检查用户在当前组织能否打开、查询或新增
  → 页面 SDS_SoA.aspx 收集用户输入
  → 页面后端/BLL 或 API Controller 接收数据
  → 通用单据引擎验证必填项、状态、客户和货品
  → 写入主表 SDS_SoA 与明细表 SDS_SoB
  → 如果配置了审批流，生成 WF 待办
  → 审核通过后改变单据状态
  → 后续出货单通过来源 ID/来源行 ID引用销售订单
```

这里的关系是：

- 页面：给人操作；
- API：给其他软件或新前端操作；
- Controller：API 的入口；
- BLL/Service：执行真正的业务规则；
- 表：长期保存结果；
- 工作流：控制谁来批准；
- 权限：控制谁能看到和执行；
- 功能 ID：把菜单、权限、单据配置和接口联系起来。

### 5.1 主要表的类别

| 类别 | 代表表 | 作用 |
|---|---|---|
| 用户与组织 | `SKY_Users`、`SKY_Roles`、`SKY_UsersRoles`、`SKY_Orangise` | 谁在使用系统，属于哪个组织和角色 |
| 菜单与权限 | `SKY_Functions`、`SKY_Role_Permission`、`SKY_User_Permission` | 能看到哪些菜单、执行哪些操作 |
| 许可 | `SKY_Register` | 系统有效期、模块和用户数许可 |
| 基础资料 | `SYS_GoodInA`、`SYS_CusA`、`SYS_WhouseA/B/C` | 货品、客户/供应商、仓库等公共档案 |
| 采购 | `POS_RePoA/B`、`POS_PoA/B`、`POS_RecA/B` | 请购、采购订单和采购验收 |
| 销售 | `SDS_QuotA/B`、`SDS_SoA/B`、`SDS_OutA/B` | 报价、销售订单和出货 |
| 库存 | `WHS_MoveA/B`、`WHS_AdjA/B`、`WHS_CouA/B` | 调拨、调整和盘点 |
| 生产 | `BOM_BOMA/B`、`MOS_PlanA/B`、`MOS_OutA/B`、`MOS_RecA/B`、`MMS_WorkA/B` | BOM、制令、领料、入库和报工 |
| 质量 | `QC_ChkA/B`、`QC_Worka`、`QC_FinishA/B`、`QC_AbnorReportA` | 检验、完工检验和异常 |
| 往来财务 | `APS_AccountA/B`、`ARS_AccountA/B` | 应付和应收 |
| 总账 | `GLS_VocA/B` | 会计凭证头和分录 |
| 工作流 | `WF_WorkFlowModel`、`WF_WorkFlowRun`、`WF_AgentBox` 等 | 流程定义、运行实例和待办 |

表名来自已有文档和代码引用。由于缺少数据库完整导出，字段、主外键和触发器仍需以后用真实数据库确认。

### 5.2 API 的两种类型

业务专用接口例如：

- `SDS_SoController`：销售订单；
- `POS_RecController`：采购验收；
- `WHS_MoveController`：库存调拨；
- `MOS_PlanController`：生产计划/制令；
- `MMS_WorkController`：工序作业；
- `QC_FinishController`：完工检验。

公共单据接口例如：

- `BillViewController`：统一查询单据和明细；
- `BillOperationController`：审核、反审、结账、反结账、过账和删除；
- `BillCheckController`：工作流签核、撤销和抄送；
- `CommonController`：公共字段和导入能力。

因此新旧前端不必为每张单据重复发明所有操作，很多共同行为由公共接口承担。

## 6. 权限是怎样一层层工作的

一次操作大致经过以下检查：

1. 许可证检查：系统和对应模块是否注册、是否过期；
2. 身份检查：登录票据、Session 或 JWT 是否有效；
3. 组织上下文：用户当前登录的是哪个公司/机构，并据此选择业务数据库；
4. 菜单权限：是否有当前 `func_id`；
5. 操作权限：是否能查询、新增、修改、删除、审核等；
6. 数据范围：只能看本人、本部门、本机构，还是全部数据；
7. 单据状态：已审核、已过账或已月结的数据是否允许修改；
8. 工作流：如果单据需要审批，当前用户是否正是这一环节的审批人。

角色可以理解为一组权限模板，例如“采购员”“仓库主管”“财务经理”。用户加入角色后获得角色权限；系统也保留用户级权限。权限最终保存为数值位集合（bit mask），也就是用一个数字同时表示多个按钮是否允许。这个设计节省空间，但不直观，排错困难。

## 7. 哪些代码是公共框架，哪些是具体业务

### 7.1 公共框架

公共框架像建筑物的地基、电梯和水电系统，可以被所有业务模块使用：

- `SKY.NetFrameWork.dll`：网站启动、登录、Web API、通用页面、上传、查询、报表和 HTTP 模块；
- `SKY.NetFrameWork.Lib.dll`：日期/数值处理、JSON、加密、缓存、日志、压缩、二维码、多语言等工具；
- `SKY.NetFrameWork.Model.dll`：用户、组织、查询条件、单据状态、操作结果等数据结构；
- `SKY.NetFrameWork.Contracts.dll`：公共接口约定；
- `SKY.NetFrameWork.Service.dll/Contracts`：通用单据保存、验证、转换、审核、过账和状态变化；
- `SKY.NetFrameWork.SQLServerDAL.dll`、`IDAL`、`DBUtility`、`DALFactory`：数据库访问；
- `SKY.NetFrameWork.WebControls.dll`：文本框、查询框、分页等公共网页控件；
- `BLL/Auth`、`BLL/Perm`、`BLL/WF` 和 `BLL/Web/common`：登录、权限、工作流和公共业务能力；
- `scripts`、`Controls`、`Seek`、`Report`：公共 JavaScript、页面控件、查询选择器和报表。

### 7.2 具体业务

具体业务回答“销售订单怎么保存”“采购验收怎样检查超收”“生产领料怎样扣库存”等问题：

- `BLL/Web/POS`、`SDS`、`WHS`、`MMS`、`MOS`、`QC` 等目录；
- `Service/Apps/POS`、`SDS`、`WHS` 等模块化单据实现；
- `API/Bills` 下的业务 Controller；
- `Pages/POS`、`Pages/SDS`、`Pages/WHS` 等业务页面；
- 数据库中各模块的表、函数、视图、触发器和存储过程。

一个简单判断方法是：如果去掉“销售”后其他模块仍然需要它，它多半是公共框架；如果它只讲销售订单、客户价格或出货规则，它就是具体业务。

## 8. 旧系统目前存在的主要问题

### 8.1 当前材料不是完整源码

工作区由部署包和 DLL 反编译代码组成。虽然 DLL 齐全，可以用于理解和部署，但反编译项目缺少原始解决方案、原始注释、测试、构建脚本和部分工程信息。数据库完整备份及全部存储过程也不在工作区。因此不能认为“看到 C# 文件”就等于拥有完整可维护源码。

### 8.2 技术年代较老

系统使用 .NET Framework 4.6、ASP.NET WebForms、ExtJS/Ext.NET 和 jQuery 1.8.2。它们曾经适合企业系统，但现在招聘、社区生态、浏览器兼容和安全维护都弱于 ASP.NET Core、Vue/React 等现代技术。

### 8.3 前后端和业务逻辑耦合较重

大量页面同时依赖 ASPX、页面后台、JavaScript、BLL 和 SQL。修改一个字段可能需要跨多个文件和数据库对象，学习和测试成本高。

### 8.4 业务规则分散

同一条业务规则可能分别存在于：

- 页面 JavaScript；
- C# 页面后台；
- BLL/Service；
- 通用单据配置；
- 存储过程、函数和触发器。

只重写页面或只翻译 C# 都无法完整复刻系统。

### 8.5 SQL 使用方式不统一

系统既有 Dapper 参数化查询，也存在大量字符串拼接 SQL、临时表和存储过程。粗略扫描发现约 454 个 C# 文件包含直接拼接 SQL 的模式，约 230 个文件调用存储过程或类似过程逻辑。字符串拼接会增加 SQL 注入、引号错误和维护困难的风险；复杂业务压在数据库里也会让自动测试和迁移更困难。

### 8.6 类型不够明确

代码大量使用 `DataTable`、`Hashtable`、`dynamic` 和字符串字段名。它们很灵活，但把很多错误推迟到程序运行时才发现。现代重构通常会使用明确的请求模型、实体模型和返回模型。

### 8.7 魔法数字和缩写过多

状态值、操作码、功能 GUID 和模块缩写散落在代码中。例如 `a01` 或状态 `'3','4','6'` 的含义必须查配置或上下文。对新人非常不友好，也容易改错。

### 8.8 权限模型强大但复杂

角色权限会合并到用户权限，操作权限又存为位集合，还叠加组织和数据范围。功能强，但权限来源难追踪。现代化时应保留能力，同时提供可解释的权限规则和审计界面。

### 8.9 部署依赖环境

系统依赖 IIS、SQL Server、Windows 路径、RSA 机器密钥、模块许可证、上传目录、Socket.IO、计划任务和一些外部软件。配置从原服务器直接搬到另一台机器通常不能立即运行。

### 8.10 安全和错误处理需要重新审查

部署配置关闭了请求验证并打开详细错误；部分接口允许在查询字符串传 token；旧式票据中包含用于重新验证的信息；部分 SQL 使用字符串拼接。以上不代表系统一定已经被攻击，但现代重构前必须进行专门安全审计，不能把旧实现原样照搬。

### 8.11 文档与实际材料有不一致

现有文档一处写 1,078 张表，另一处写 437 张表；UI 文档提到 React 18，但工作区中没有对应 React 原始项目。这说明已有文档只能作为线索，最终应以真实数据库、运行菜单和代码交叉验证。

### 8.12 自动化测试与版本历史缺失

当前没有可见的单元测试、集成测试、持续集成配置和原始 Git 历史。重构时如果没有先建立测试，很容易出现“新页面看起来一样，但金额、库存或状态算错”的问题。

## 9. 对第一次练手重构的建议

不要一次重做全部 ERP。第一次适合选择一条小而完整的链路：

```text
登录 → 用户/角色 → 客户 → 货品 → 销售订单 → 提交 → 审核 → 查看订单
```

这个范围能练习：

- 前端页面；
- 后端 API；
- 数据库主表/明细表；
- 登录和权限；
- 单据状态；
- 简单审批；
- 操作日志；
- 测试和部署。

第一版可以不做真实财务、复杂 MRP、成本核算和全部旧表兼容。这些领域规则复杂，适合在基础版本稳定后逐步加入。

## 10. 当前结论的可信度说明

- “已确认”：直接来自页面目录、反编译类、API、表配置和代码行为；
- “典型链路”：符合代码结构和制造业 ERP 常规流程，但具体企业可能关闭或跳过某些步骤；
- “待确认”：数据库没有完整导出，无法核实全部字段、外键、存储过程、菜单中文名和许可证配置；
- 任何涉及金额、库存数量和单据状态的重构，都必须用真实样例数据和原系统运行结果进行对照测试。
