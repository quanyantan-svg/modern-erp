## 1. Executive Summary

**Decision: PHASE 6D + 6E REQUIRED. Phase 7 is premature for the intended integrated manufacturing ERP.**

Phases 0–6C established a substantial operational core: source-linked sales and purchasing, authoritative IQC/OQC gates, partial fulfillment guards, production instructions and BOM/routing snapshots, material and finished-goods movements, settlement/open-item controls, lot/serial traceability, and analytical manufacturing execution. The full existing suite passes (1,335 runtime tests, 0 failures, 0 skipped, 0 todo).

The remaining problem is not lack of screens. It is that physical inventory, commercial billing, and financial accounting do not yet form one financially authoritative system:

- Inventory transactions contain quantity but no financial amount, cost layer, or valuation identity. Production issue/return/receipt/reversal, scrap, adjustment, and count do not post authoritative inventory/WIP/variance entries.
- Sales Delivery posts AR/revenue at selling price but no COGS/inventory relief. Purchase Receipt posts inventory/AP at PO price, but no vendor-bill variance or matching model exists.
- No sales invoice/billing document, supplier invoice/vendor bill, or coherent transactional tax model exists. Shipment/receipt are therefore forced to be both physical and financial events.
- Accounting and inventory periods are independent. Most production and inventory movements do not check either close, so late/backdated stock changes can coexist with closed finance or frozen inventory snapshots.
- The emergency cleanup engine predates important Phase 6A/6B/6C dependencies and can delete/rewrite canonical quantity, AR/AP, and vouchers without complete awareness of idempotency, lot/serial, genealogy, reversal, settlement-account, operation-report, or cost-summary records.
- Several backend authorization mismatches remain, including a write operation authorized by `INVENTORY_VIEW` and bank/fixed-asset mutations authorized by `ACCOUNTING_VIEW`.

Accordingly, the current product is a strong **single-company, CNY, discrete-manufacturing operational-control system with simplified shipment/receipt-basis gross accounting and analytical production cost**. It is not yet an integrated financial manufacturing ERP and must not claim authoritative inventory value, COGS, WIP, tax, or statutory financial reporting.

### Headline answers

| Question | Answer |
|---|---|
| Financially authoritative inventory as of date X | **NO** |
| Authoritative COGS per Sales Delivery | **NO** |
| Authoritative WIP financial value | **NO** |
| Inventory value roll-forward reconciles to GL | **NO** |

| Cash/bank operational balance reconciles to GL | **PARTIAL** — Phase 6A settlement movements reconcile internally, but legacy cash journals/bank balances and GL are separate truths |

## 2. Current Honest Product Scope

The narrowest scope supported by code today is:

- one company/legal entity;
- one effective base currency, CNY;
- discrete manufacturing with BOMs and mostly linear routing execution;
- one stored unit per SKU, with fractional quantities but no cross-UOM conversion;
- optional NONE/LOT/SERIAL tracking;
- source-linked SO → Delivery → Return and Purchase Instruction → PR → PO → Receipt → Return;
- receipt/shipment-basis gross AP/AR and revenue recognition;
- configurable incoming/outgoing quality inspection;
- material planning with on-hand, open PO, and open production-order netting;
- settlement, prepayment/unapplied credit, refund, write-off, and reversal controls;
- analytical, not financial, production cost/WIP/capacity/yield reporting.

Unsupported or misleading if claimed: tax-compliant invoicing, 2-way/3-way matching, authoritative inventory valuation/COGS/WIP, multi-currency accounting, UOM conversion, controlled go-live conversion, advanced APS, full MES/OEE, and full QMS/CAPA.

## 3. V1.3 Architecture / Domain Map

The actual architecture is a React client over a native Node HTTP API and a SQLite domain database. The target MySQL production architecture remains Phase 7 work.

| Domain | Canonical records | Current effect |
|---|---|---|
| Commercial | SO/PO and immutable source line links | commitment and price provenance |
| Logistics | Receipt/Delivery/Returns | quantity ledger, AR/AP source, gross voucher |
| Quality | QCP snapshots, IQC/OQC | blocks Receipt/Delivery until PASS or explicit waiver |
| Inventory | `inventory`, `inventory_transactions`, tracked dimensions | quantity truth; no value ledger |
| Planning | Forecast, MRP run snapshots, instructions, PR | recommendation and controlled release |
| Production | PO, BOM/routing snapshots, issues/returns/receipts, operation reports | physical execution and analytics |

| Accounting | voucher headers/entries, posting workflow, periods | balanced posted journal, incomplete event coverage |
| Reporting | document analytics and voucher-derived statements | mixed authoritative/analytical quality |

The critical missing bridge is **quantity/cost evidence → financial valuation entries → reconciliation**.

## 4. Order-to-Cash

### Reconstructed chain

Customer/CRM → Sales Order (commercial/date/contact/address/payment snapshot) → submission/approval → source-linked Delivery draft → QCP snapshot/OQC PASS → Delivery confirmation → stock OUT + revenue/AR voucher + AR source item → source-linked Sales Return/Discount → credit application → Collection/Prepayment/Refund/Write-off/Reversal.

Implemented controls include requested delivery date, partial delivery and cumulative source-line guards, immutable source price, warehouse inability to reprice, optional lot/serial allocation, OQC freshness, due-date derivation, allocation-level settlement, persistent idempotency on important Phase 6A paths, and closed accounting-period rollback for Delivery/Return.

Gaps:

- Delivery simultaneously means physical shipment, billing, revenue recognition, and AR creation (`server/app.js`, `confirmSalesDelivery`).
- Deposits can exist as unapplied balances, but there is no pro-forma, milestone, progress, advance invoice, billing schedule, or bill-after-delivery document.
- There is no way to ship without billing, bill without shipping, consolidate deliveries into one bill, split one delivery across bills, or represent invoice price differences.
- COGS and inventory financial relief are absent.
- Sales return reverses selling-price revenue/AR but not original COGS/inventory value.

**Conclusion:** shipment-basis billing is a coherent simplification only for a tightly documented scope in which every confirmed shipment is immediately billable at the SO price. It is not sufficient for general commercial use. Preserve the current flow as a configurable direct-bill path, but add a separate billing layer rather than replacing physical Delivery.

## 5. Procure-to-Pay

### Reconstructed chain

Supplier → Purchase Instruction → PR → approval → source-linked PO → approval → source-linked Receipt draft → QCP snapshot/IQC PASS → Receipt confirmation → stock IN + inventory/AP voucher + AP source item → Purchase Return/Discount → Payment/Prepayment/Credit/Refund/Write-off/Reversal.

Implemented controls include expected dates, partial PO/receipt, source pricing, cumulative quantities, lot/serial tracking, due dates, settlement allocations, period checks on accounting-backed confirmation, and source-linked returns.

Gaps:

- Receipt is forced to be the supplier bill at PO price (`confirmPurchaseReceipt` debits inventory and credits AP for the receipt total).
- Invoice-before-receipt, receipt-before-invoice, consolidated/split bills, invoice quantity differences, freight/landed cost, and invoice price/tax differences cannot be represented.
- 2-way and 3-way matching are absent.
- Goods-received-not-invoiced/accrual and purchase-price variance are absent.

**Conclusion:** receipt-based AP is acceptable only as a documented simplified model. It is not trustworthy general-purpose AP for businesses where supplier invoices differ in timing, quantity, price, or tax.

## 6. Tax / Invoice Model

No runtime sales/purchase transaction schema implements tax rate, tax base, tax amount, inclusive/exclusive price, multi-rate allocation, tax rounding, invoice number/date/status, credit/debit invoice, output VAT, input VAT, or tax reporting. Archived legacy research does not constitute implementation. `currencies` and accounting-entry currency columns likewise do not create a tax model.

Classification: **MISSING**, not cosmetically partial. The ERP must not claim regulatory or tax compliance.

For an integrated commercial ERP claim, sales billing, vendor bills, and transactional tax are P0. They may be excluded only by explicitly repositioning V1.3 as a non-tax operational system whose billing/tax ledger is maintained externally.

## 7. Inventory Quantity Integrity

### Canonical flow status

| Route | Quantity effect | NONE/LOT/SERIAL | Provenance/status |
|---|---|---|---|
| Purchase Receipt / Return | IN / OUT | implemented | source-linked and quality gated |
| Sales Delivery / Return | OUT / IN-to-HOLD | implemented | source-linked and quality gated |
| Material Issue / Return | OUT / IN | implemented | production-order source |
| Production Receipt / reversal | IN / OUT | implemented | production-order source and coverage guards |
| Transfer | paired OUT/IN | implemented | tracked identity preserved |
| Scrap | OUT | implemented | tracked identity preserved |
| Adjustment | signed | implemented | tracked allocation supported |
| Inventory Check | set-to-count plus ledger delta | **PARTIAL** | independent approval, but no normal tracked-allocation capture path |

The primary quantity truth is `inventory` by warehouse/product, explained by `inventory_transactions`; `inventory_lot_balances` or `inventory_serials` add dimensional truth and `/api/tracking/reconcile` checks tracked totals.

Material gaps:

- `products.stock_quantity` remains independently writable from product master APIs. MRP correctly uses `inventory`, but `/api/reports/inventory-status` joins warehouse inventory and then reports/classifies the product-level `stock_quantity`, producing a split and potentially misleading stock view.
- Non-zero inventory-check differences call `postTrackedMovement` without a corresponding normal UI/API allocation capture workflow for the check. LOT/SERIAL stocktake correction is therefore incomplete.
- Adjustment, check, transfer, scrap, and production postings do not universally enforce inventory-period closure or idempotency.
- Confirmed adjustment, count, transfer, and scrap generally lack explicit business reversal documents.

Overall inventory quantity: **PARTIAL but strong for the Phase 2/4/6B source-linked routes; not yet one universally enforced truth across every exposed route/report.**

## 8. Inventory Financial Valuation

`inventory_transactions` stores product, warehouse, direction, quantity, balance, source, and timestamp, but no unit cost, total value, cost layer, valuation method, or accounting-entry link. Tracked lots/serials store identity and provenance but not an immutable financial cost layer.

What exists:

- Purchase Receipt capitalizes PO-price total to inventory and AP.
- Purchase Return reverses the same source selling/purchase amount.
- Product standard costs and Phase 6C production cost summaries provide managerial evidence.
- Phase 6C can label material evidence authoritative/partial/estimated for analytics.

What does not exist:

- financial value ledger by product/warehouse/lot/serial;
- cost-layer consumption for sales, scrap, adjustment, production, or reversal;
- COGS entry on Sales Delivery or reversal on Sales Return;
- WIP debit/credit on material issue/return and production receipt/reversal;
- inventory gain/loss and scrap expense entries;
- inventory subledger-to-GL reconciliation.

Answers:

- Inventory on hand as of X = ¥Y, exactly reconciled to GL: **NO**.
- Authoritative COGS for a Sales Delivery: **NO**.
- Opening value + purchases + production ± adjustments − COGS − scrap = closing value = GL: **NO**.

## 10. General Ledger

Strengths: chart of accounts, exact integer-cent entries, exact debit/credit balance, source uniqueness, manual voucher workflow, creator/approver separation, posted-only financial reports, source links, period close/reopen history, and traceable voucher records.

Limitations:

- Operational vouchers default to `ENTERED`; they become financial-system-of-record entries only after submission and posting. The canonical ACCOUNTING role can submit but intentionally cannot approve, leaving voucher approval dependent on ADMIN because REVIEWER also lacks `VOUCHER_APPROVE`.
- Major inventory/production economic events never generate vouchers.
- There is no routed general-ledger/account-detail endpoint; dormant helper code is not product capability, and one dormant ledger query does not filter `POSTED`.
- No controlled opening-journal/import process or retained-earnings close exists; the balance sheet inserts a virtual “unclosed profit” amount.
- The fixed chart seed is very small and operational voucher account IDs are hard-coded.
- There is no explicit voucher reversal document for arbitrary posted manual vouchers.

**GL verdict:** structurally credible double-entry journal, but **PARTIAL as the financial system of record** because event coverage and subledger reconciliation are incomplete.

## 12. Treasury

Phase 6A settlement accounts, movement records, bank balance baselines, and CHECK-only reconciliation provide a useful controlled settlement truth. However:

- legacy `cash_journals` directly mutate `bank_accounts.balance_cents`, may be deleted with balance rollback, and do not generate/post GL vouchers;
- settlement movements also mutate bank-account cached balances through a separate path;
- bank statements/reconciliations accept caller-provided totals/differences rather than matching statement lines to book movements;
- cash transfer is a generic journal type, not a dual-sided controlled transfer workflow;
- bank account opening balances are entered directly without an opening journal.

Treasury is **PARTIAL**. Phase 6A flows are stronger than the exposed legacy cash/bank surfaces; those surfaces should be hidden until unified.

## 13. Fixed Assets / Secondary Finance

Fixed assets provide master CRUD, status/location/custodian updates, and manual depreciation records. They lack controlled acquisition/capitalization, disposal accounting, transfer history, impairment, period depreciation run, duplicate-period prevention, and voucher integration. Amount inputs also use ad-hoc rounding rather than the strict yuan/cents boundary used by newer modules.

Fixed assets are **demo/partial**, not usable as a financial subledger. Expenses/leave, bills, generic cash journals, currency maintenance, and configurable workflow screens are likewise disconnected or shallow secondary modules. Recommendation: feature-flag them out of a core V1.3 release rather than expand Phase 6D into unrelated scope.

## 14. MRP / Planning

MRP correctly snapshots runs, uses contractual SO requested-delivery dates, excludes fulfilled demand, nets on-hand plus open approved PO and open PENDING/IN_PROGRESS production supply, applies net-before-BOM explosion, handles recursive BOMs/scrap, and emits BUY/MAKE suggestions. Released instructions and generated downstream documents have dependency guards.

It remains a simplified calculator:

- `SALES_PLUS_FORECAST` adds both sources; no forecast-consumption logic prevents double demand.
- Open PRs and purchase/production instructions are not supply until they become PO/production orders.
- Lead-time fields exist but do not date suggestions; safety stock, minimum order quantity, lot size, order multiples, scheduled receipt dates, and reschedule/cancel messages are absent.
- Repeated runs are snapshots and may recommend the same shortage until released supply reaches PO/production-order state.
- Active BOM/routing selection is simplified; alternate/effectivity selection is limited.

## 15. Manufacturing

Production Instruction → Production Order, BOM/routing snapshots, work-center snapshots, material issue/return, operation report/reversal, scrap/yield, receipt/reversal, completion coverage, WIP/capacity, genealogy, idempotency on key actions, and analytical cost are implemented and well tested.

Remaining blockers are financial, not physical: no WIP/variance/inventory GL flow and no financially authoritative completion unit cost. Production movements also lack common inventory-period close enforcement.

Rework and alternate BOM/routing are P2/P3 depending customer scope. By-products/co-products, subcontract manufacturing, in-process QCP, downtime/OEE, and complex routing networks are advanced roadmap items, not V1.3 core blockers.

## 16. Quality

QCP version resolution, global/product priority, full/fixed/percentage sampling, criteria snapshots, IQC/OQC, immutable completed inspections, PASS gates, stale inspection detection/reinspection, lot/serial snapshots, HOLD/release, and traceability are present.

This is usable incoming/outgoing inspection for the narrow scope. Missing in-process quality, NCR/nonconformance workflow, CAPA/supplier corrective action, certificates/evidence attachments, and calibration are later QMS work. Lack of an allocation-aware stocktake correction and the overly broad HOLD/RELEASE permission are immediate integrity/security issues.

## 17. Traceability

The source supports the X100-style chain Supplier → PO → Receipt → IQC → component identity → Material Issue → Production Order → genealogy → finished identity → OQC → Delivery → Customer. Forward/backward queries, impact data, return provenance, hold, and receipt-reversal genealogy invalidation exist.

Risks:

- trace output returns movement history without universally filtering `reversed`, and genealogy rows are returned regardless of ACTIVE/REVERSED status; consumers must interpret flags correctly;
- no rework model exists, so rework genealogy cannot be represented;
- lifecycle cleanup does not fully model tracked tables and may leave or delete misleading history.

Traceability is **strong but not safe against the current emergency-cleanup gap**.

## 18. Master Data / UOM / Currency

Core masters exist for customer, supplier, product, warehouse, BOM, routing, work center, accounts, bank accounts, QCP, and projects. Codes are generally unique and active flags/dependency guards exist, although history/versioning varies.

UOM is a free-text product field. There is no UOM master, base/sales/purchase/BOM unit distinction, precision policy, or conversion such as 1 BOX = 10 EA. The same SKU must use one unit across purchasing, inventory, BOM, production, and sales. This is a P1 general-commercial limitation but can be scope-limited for customers that transact each SKU in one base UOM.

A currency master and accounting-entry currency columns exist, but commercial documents, open items, settlement, exchange differences, and reports are CNY-only. UI money formatting is fixed to CNY. V1.3 must be described as **single-currency CNY**; the exposed currency master should be hidden because it implies unsupported multi-currency behavior.

Tax, payment-term structured masters, Incoterms, warehouse bins/locations, and conversion masters are missing or only represented as free text. Tax is P0 for the integrated-commercial claim; bins and Incoterms are P2.

## 19. Inventory Control

Transfer, adjustment, scrap, count approval, tracked hold/release, expiry, and inventory close screens exist. Count has genuine creator/reviewer separation.

Control gaps:

- warehouse can create and confirm its own adjustment and scrap; transfer create and execution permissions both reside on WAREHOUSE;
- no value/threshold-based approval policy exists;
- confirmed adjustment/scrap/transfer/count lack normal reversal/correction documents;
- inventory-period closure does not block these movements;
- posted movement rows are normally immutable, but lifecycle cleanup can delete and rebalance them.

Dual control is required for material adjustments/scrap, with configurable thresholds rather than mandatory approval for every trivial movement.

## 20. Period Close / Month-End

Accounting close checks that no ENTERED/SUBMITTED/REJECTED vouchers remain. Reopen is ADMIN-only and reasoned/audited. Inventory close builds quantity snapshots and enforces chronological close/reopen order.

The two closes do not coordinate:

- accounting can close while inventory remains open;
- inventory can close without value or GL reconciliation;
- production, transfer, adjustment, scrap, and count can post with business dates in closed inventory/accounting periods;
- inventory snapshots use transaction `created_at` chronology, not a canonical movement business date;
- no enforced “inventory close first, reconcile, then accounting close” sequence exists.

Required close sequence after Phase 6D:

1. finish/cancel operational drafts and inspections;
2. post all inventory movements and settlement documents;
3. run quantity/tracked/subledger health checks;
4. calculate/finalize valuation, WIP, COGS, and variances;
5. reconcile inventory value, AR, AP, and cash/bank to GL;
6. close inventory period;
7. post/approve accruals and closing vouchers;
8. close accounting period;
9. require explicit current-period reversal or controlled sequential reopen for corrections.

## 21. Opening Balance / Go-Live

There is no controlled go-live process for opening inventory quantities/identities/value, AR, AP, cash/bank, GL, open SO/PO, or WIP. Product `stock_quantity`, bank `initial_balance_cents`, manual vouchers, and development seed/reset utilities are not a coherent conversion process.

Required P1 capability: staged import, validation/reconciliation preview, approval, atomic posting, immutable conversion batch, rollback-before-activation only, and a signed opening trial balance/subledger reconciliation. WIP may be excluded from initial migration scope if go-live requires completing/closing legacy WIP externally.

No user-facing CSV/Excel bulk master/import or controlled transaction-export workflow was found. Existing backup/restore scripts are not migration tools. A real customer cannot reasonably migrate thousands of records without P1 tooling.

## 22. Lifecycle / Repair

Normal V1.3 principles are largely correct: draft can be edited/deleted/cancelled; effective records are immutable and corrected by explicit return/reversal; closed-period history is protected on the newer finance paths.

Exceptions:

- inventory adjustment/scrap/transfer/count have no explicit posted reversal;
- legacy cash journals can be destructively deleted after mutating bank balances;
- bank/fixed-asset masters can be mutated under view permissions;
- emergency lifecycle cleanup deletes inventory transactions and recalculates balances and deletes vouchers/open items.

The cleanup graph covers older stock/AR/AP/voucher dependencies but not all Phase 6A/6B/6C tables: unapplied balances/applications/refunds/write-offs/reversal components, settlement-account movements/idempotency, tracked allocations/movements/identities/genealogy, operation reports/reversals, and cost summaries. This makes it a P0 bypass. Until redesigned, effective-record cleanup must be disabled; archive/analyze may remain read-only. Exceptional repair should require backup proof, dry-run hash/reconciliation output, independent approval, and post-repair CHECK results.

## 23. Roles / SOD / Authorization

Seeded canonical roles are ADMIN, SALES, REVIEWER, WAREHOUSE, ACCOUNTING, and the five approval families are SO, PO, inventory count, accounting voucher, and PR. Important Phase 1 ownership boundaries remain tested.

Findings:

- `/api/roles` still permits creation of arbitrary roles, so “exactly five” is a seed convention rather than a hard runtime invariant.
- `holdIdentity` authorizes either `INVENTORY_VIEW` or `WAREHOUSES_MANAGE`; a view permission therefore grants HOLD/RELEASE mutation.
- bank-account update and fixed-asset create/update/depreciate handlers authorize `ACCOUNTING_VIEW` instead of their MANAGE permissions.
- WAREHOUSE owns both create and execute permissions for transfer, adjustment, and scrap; only count has independent REVIEWER approval.
- no non-admin canonical role has `VOUCHER_APPROVE`; operational and manual voucher posting depends on ADMIN.
- QCP maintenance and tracking-policy maintenance are ADMIN-only despite dedicated domain work.

These are backend issues, not merely launcher visibility issues. The HOLD/RELEASE and finance VIEW→WRITE mismatches are P0 functional-security blockers.

## 24. Reporting / Decision Support

Sales/purchase summary and outstanding reports are transparent about order versus confirmed shipment/receipt metrics and include returns. Inventory movement detail is ledger-based. AR/AP, settlement, traceability, IQC/OQC, WIP, yield, capacity, cost, trial balance, income statement, and balance sheet surfaces exist.

Classification:

- document fulfillment/quantity reports: generally **AUTHORITATIVE/PARTIAL** within their stated source/status basis;
- traceability/quality: **AUTHORITATIVE/PARTIAL** subject to reversal/cleanup caveats;
- WIP/yield/capacity/production cost: **ANALYTICAL**;
- financial statements: **PARTIAL**;
- `/api/reports/inventory-status`: **MISLEADING**, because it uses writable `products.stock_quantity` rather than warehouse `inventory.quantity`;
- old sales analysis uses approved order creation date, not delivery/revenue date, and should be hidden in favor of the more explicit decision reports.

Report export is absent and pagination is inconsistent. Totals must continue to state date basis, status filters, return/reversal handling, currency, and whether they are operational or financial.

## 25. Auditability / Reconciliation

Available CHECKs are fragmented: settlement, settlement account, tracked inventory, and production cost checks exist separately. There is no operational System Health screen/job covering quantity ledger, dimensional inventory, AR/AP caches, allocations, cash/bank, genealogy, operation reports, cost summaries, voucher source uniqueness, and periods.

## 26. UX Functional Completeness

Newer details expose source documents, status, remaining quantities, quality state, tracked identities, and open balances. Error messages generally explain blocked actions.

Operational gaps remain: no month-end/reconciliation cockpit, no controlled correction path for several posted inventory documents, no invoice/match workspace, and no migration wizard. QCP/role/period dependencies remain admin-heavy. Notifications are only list/read infrastructure: no business flow calls `createNotification`, and no alert generation was found for approvals, overdue AR/AP, quality failures, shortages, expiry/HOLD, or overload.

These notification gaps are P2 because work queues and direct pages exist, but they reduce day-to-day discoverability.

## 28. Full V1.3 UAT Blueprint

Future clean UAT should use a new disposable database and assert these control points:

1. Create five-role users, CNY masters, customer/supplier payment terms, base-UOM products, warehouses, BOM/routing/work centers, QCP, and NONE/LOT/SERIAL products. Expected: unique codes, no opening stock side effects.
