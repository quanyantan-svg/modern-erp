# V1.3 Phase 6A — 财务与交易控制完整性

## 1. 权威模型

所有金额均为整数分。凭证及凭证分录是现金/银行财务余额的权威历史；`settlement_account_movements` 是带结算账户、来源单据和凭证链接的业务明细，不是第二套可任意修改的余额真相。CHECK 对账只报告差异，启动过程不修复余额。

应收权威公式：

`原始应收 - 有效退货贷项 - 有效折让 - 其他贷项 - 有效收款分配 - 显式余额应用 - 有效核销 + 对应冲销 = 当前未结`

应付公式对称。缓存列只在同一数据库事务内由不可变历史刷新；不允许人工修改 `paid/open` 缓存。

## 2. 预收、预付与未核销贷项

收款与付款确认满足：

`单据金额 = 应收/应付分配 + 用户明确选择的未核销金额`

未选择“保留预收/预付”时，系统拒绝差额。没有待核销项目时，可以显式创建客户预收款或供应商预付款，但不会创建虚假 AR/AP。`settlement_unapplied_balances` 保留往来单位、原始金额、日期、结算账户、来源收付款单和创建审计。

销售/采购退货在原来源已结清时形成未核销贷项。系统不执行未来 FIFO 自动核销。财务人员通过 `balance_applications` 明确将预收、预付或贷项用于同一往来单位的未来 AR/AP；应用本身不产生第二次现金移动。应用冲销恢复余额及目标未结金额。

余额状态图：

```text
收付款/退货贷项 ──确认──> OPEN ──应用/退款──> PARTIAL ──全部耗用──> EXHAUSTED
                                   └──应用冲销/退款冲销──> 恢复可用余额
```

## 3. 退款

客户退款可来源于客户预收款或未核销客户贷项；供应商退款对称。退款必须选择同一往来单位、可用余额、有效 CASH/BANK 结算账户、业务日期、原因及可选外部参考。金额不得超过可退款余额。

确认退款生成凭证、现金/银行方向明细、审计及来源链接。确认记录不可删除；显式退款冲销在开放期间生成等额反向凭证并恢复可退款余额。

## 4. 收付款部分冲销

原收付款单保持不可变。每次冲销创建 `settlement_reversals`，并以 `settlement_reversal_items` 精确指定原分配行或未核销组件及金额。

```text
原分配 = 当前有效分配 + 累计已冲销
原收付款金额 = 有效分配 + 可用未核销 + 已冲销组件
```

累计冲销不能超过原金额或任一组件剩余金额。已被应用或退款的预收/预付组件必须先冲销依赖。每次冲销只按本次金额生成一张等额反向凭证和反向结算账户明细。

## 5. 退货冲销

已确认销售退货和采购退货不能删除。`return_reversals`/`return_reversal_items` 按原退货行记录部分数量和金额：

```text
销售退货冲销：库存减少 + 客户贷项减少 + 原凭证部分反向
采购退货冲销：库存增加 + 供应商贷项减少 + 原凭证部分反向
```

数量不得超过原退货未冲销数量。若退货未核销贷项已经用于未来项目或退款，Phase 6A 采用 fail-closed：拒绝退货冲销，必须先冲销贷项应用或退款。拒绝事务不产生库存、贷项、凭证或审计副作用。

## 6. 小额核销（write-off）

状态机：

```text
DRAFT ──财务提交──> SUBMITTED ──管理员独立确认──> CONFIRMED
                              └──管理员驳回──> REJECTED
CONFIRMED ──显式冲销（开放期间）──> 保留原单并恢复未结余额
```

`ACCOUNTING`（`test_accounting`）创建和提交；当前五角色发布中仅 `ADMIN`（`test_admin`）确认或驳回，且创建人不能自审。未增加第六角色，也未增加通用 Approval Center 单据族。未来可扩展独立财务控制角色。

核销金额必须大于零且不超过当前未结金额。确认及冲销生成等额相反凭证并保留完整历史。

## 7. 结算账户与对账

银行收付必须引用启用的 `bank_accounts.id`；现金必须引用启用的权威库存现金科目 `1001`。自由文本不能冒充结算账户。单据保存 `settlement_account_id`、方式、外部参考和业务日期。

`GET /api/settlement/account-reconciliation` 比较每条来源链接的确认、退款、冲销业务移动与凭证现金/银行分录。返回 `mode=CHECK`，发现人为差异也不修改数据。

## 8. 会计期间

所有通过 `generateVoucher` 的 Phase 6A 确认/冲销均拒绝关闭期间。关闭期历史来源可以在当前开放期间冲销；原业务日期与冲销入账日期分别保存，不自动回填到历史期间。

会计期间重新打开仅限 `ADMIN`，必须填写原因。`period_reopen_history` 永久保存原关闭人、原关闭时间、重新打开人、时间及原因；不覆盖关闭证据。

## 9. 幂等性

`idempotency_records` 按操作类型、来源单据和 `Idempotency-Key` 唯一保存语义请求指纹及成功结果。记录与业务过账处于同一事务：

- 同操作、同键、同语义：返回原成功结果，不重复库存、AR/AP、凭证或现金移动。
- 同键、不同语义：409 冲突。
- 提交前失败：事务回滚，不留下成功记录，可用同键修正后重试。
- 不同键对已确认单据：仍由状态/来源唯一性防止重复经济效果。

SQLite 依赖单数据库写事务和唯一约束；真实 MySQL 并发验证留待 Phase 7。

覆盖操作包括采购入库、销售出库、生产领料、生产入库、收款、付款、退款、财务冲销、退货冲销和核销确认。

## 10. 删除与来源图

仅无经济效果且无依赖的 DRAFT/CANCELLED 草稿可清理。已确认收付款、退款、退货、核销、应用及其冲销均不得硬删除。

```text
Delivery/Receipt ──> AR/AP open item ──> allocation ──> Collection/Payment ──> Voucher
        │                    ▲                 │                    └── Settlement account movement
        └── Return ──> Credit balance ──apply─┘
                           ├──refund──> Refund ──> Voucher/movement
                           └──reverse dependency chain
AR/AP ──> Write-off ──> Admin confirmation ──> Voucher ──> Write-off reversal
```
