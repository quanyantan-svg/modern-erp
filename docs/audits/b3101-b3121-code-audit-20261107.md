## 0. 使用说明与状态规则

### 0.1 本文件的定位

本文件是 B3101 采购管理、B3121 委外管理及其 VMI 关联能力的**持续审计台账和问题追踪基线**。

后续开发不得只依赖聊天记录。每次开始开发前，必须先读取：

1. `AGENTS.md`
2. `docs/status/PROJECT_STATUS.md`
3. 本文件
4. 对应 Requirement / Design
5. 对应测试套件及最新证据

本文件记录问题、代码证据、业务预期、修复要求、测试要求、状态和变更历史。项目状态文件只维护摘要和链接，不复制整份问题清单。

### 0.2 审计状态与实施状态不得混用

| 状态 | 含义 |
|---|---|
| `IDENTIFIED` | 已发现线索，尚未完成证据核验 |
| `DOCUMENTED` | 已记录到本审计台账，证据和边界已说明 |
| `NEEDS_REVALIDATION` | 需要在当前 HEAD 或真实测试环境重新核验 |
| `AUTHORIZED` | 业务所有者/项目治理已明确批准实施 |
| `IMPLEMENTING` | 已获授权，正在修改代码 |
| `CODE_COMPLETE` | 代码修改完成，但不代表测试通过 |
| `TESTED` | 指定测试已运行并通过，附测试命令、SHA、Run ID 和结果 |
| `VERIFIED` | 代码、业务不变量、回归及必要证据均已核验 |
| `ACCEPTED` | 有权责任人已正式签发 Acceptance |
| `BLOCKED` | 受依赖、证据、权限或业务规则阻塞 |
| `DEFERRED_NOT_AUTHORIZED` | 明确延期或尚未授权；不得实施 |
| `REJECTED` | 经裁定不纳入产品范围 |

**不得**将 `DOCUMENTED`、`CODE_COMPLETE` 或单元测试通过写成 `ACCEPTED`。

### 0.3 每项问题的状态更新要求

任何问题状态变化，都必须至少更新本文件对应 Issue 的：

- `Status`
- `Last Updated`
- `Evidence`
- `Resolution / Next Action`
- `Verification`（若进入 TESTED / VERIFIED）
- `Change History`

当问题状态变化影响项目整体状态时，再同步：
- `docs/status/PROJECT_STATUS.md`
- `log/YYYY-MM-DD.md`
- 必要时 `docs/status/CAPABILITY_MATRIX.md`

这些文件不会自动同步；每次开发任务结束时必须显式执行状态同步。

### 0.5 产品目标：满足必要业务，不复刻金蝶

> **项目范围原则（2026-11-07，用户补充）**：modern-erp 是独立的现代 ERP，不追求完整复现或 1:1 模仿金蝶云星空。B3101 / B3121 手册仅用于业务概念、流程和关键边界的参考。**手册出现某功能 ≠ 我们必须开发；现有 Requirement 曾列入某能力 ≠ 可以未经变更程序直接删除或改变已批准合同。**

- **先保留最小可用业务闭环**：实际需要的采购单、入库、退货、必要的委外发退补料、收货，以及对应的权限、追溯和统计。
- **复杂能力按业务价值裁剪**：采购组复杂数据隔离、自动配额优化、复合折扣、多环节审批、VMI 高级结算、跨期 WIP 财务处理等，除非有明确实际需求，不列为近期必做。
- **实现方式可以不同于手册**：页面、菜单、数据模型、操作流程可以更简单；优先复用已有模块、统一流程和单一事实来源。
- **不能简化掉核心正确性**：身份与权限边界、库存数量与物权、估值和金额、状态机、来源可追溯、事务/幂等、拒绝时的业务零副作用及审计，仍为硬约束。
- **已批准范围不能擅自缩减或扩大**：M1-Core Acceptance 及既有批准的 Requirement/Design 继续有效；计划不再建设的已批准能力，必须经相应 Scope Change / Owner Decision 正式裁定后，方可在未来 Requirement、Design 和 Capability Matrix 中体现，历史不改写。
- **禁用也可构成正确处置**：对未获授权、低价值或无足够证据的写入接口，可以经过正式裁定后服务端 fail closed / 停用或只读，不应为了“覆盖手册”强行开发完整业务链。

### 0.6 审计结果与产品范围是两条不同的轴

| 字段 | 用途 | 允许值/约束 |
|---|---|---|
| `Evidence Status` | 代码问题证据状态 | 参照 §0.2；静态证据与实测证据必须区分 |
| `Product Scope` | 该能力是不是本 ERP 未来要做的 | `SCOPE_REVIEW_PENDING`（默认） / `CORE_REQUIRED` / `SIMPLIFIED` / `OPTIONAL` / `DEFERRED` / `OUT_OF_SCOPE`；后五项须有可追溯 Owner/Scope Decision，不能仅由开发者或 AI 宣告 |
| `Authorization` | 本次是否授权动手开发 | `NOT_AUTHORIZED`（默认） / `AUTHORIZED` / `DEFERRED_NOT_AUTHORIZED`；不因 Product Scope=CORE_REQUIRED 自动授权 |
| `Delivery Status` | 当前实施与验收到了哪一步 | 代码、测试、验证、验收分开记录；不要用一个“完成”覆盖全部过程 |

**开发决策顺序**：发现问题 → 证据核验 → 业务价值判断 → 对照已批准 Requirement/Design → 必要时 Scope Change / Owner Decision → 授权 → 实施 → 回归 → 逐项验收。

**默认策略**：本文件列出的全部新增业务功能和 UI 缺口，其 `Product Scope` 暂为 `SCOPE_REVIEW_PENDING`；只有当前已批准合同明确要求的部分按原批准范围执行。发现代码正确性问题时，先评估该入口是否仍会被使用；活跃入口必须修复或安全封锁，不得仅因“暂时不需要功能”就允许错误写入。

### 0.7 价值裁剪建议（建议，非批准决定）

| 模块 | 建议近期路径 | 裁剪思路 |
|---|---|---|
| 标准采购 PO→Receipt→Return | 优先保留核心闭环 | 复用现有单据/库存/财务 backbone；不要复制第二套单据或账簿 |
| 委外订单→发/退/补→完工收货 | 优先保留 M1-Core 已批准闭环 | 保持 M1-Core 的有界支持范围，不自行新增复杂分支 |
| 采购员、采购组 | 先做简单归属 | 复杂组织级隔离是否需要，先由产品 Owner 决定；服务端现有权限不得被削弱 |
| 配额、寻源 | 优先保留简单可解释策略 | 真实需求不足时不做自动优化和复杂审批；正式写 API 仍要保证权限与来源正确 |
| 价格和折扣 | 基础取价/金额正确性优先 | 多级折扣、复杂公式和历史重算不作为默认目标 |
| VMI 结算/物权转移 | 保持延期/拒绝边界 | 无业务决策前不为了“手册完整”开放危险写入 |
| 跨单/跨期 WIP、复杂差异分摊 | 保持延期/受限 | 不为满足列表数量而引入高风险成本引擎 |
| 期初单据、扫码/PDA、复杂报表 | 价值评审后选择 | 先用现有输入方式和少量关键报表；不强制复制原版界面 |

以下所有 `Required Correction` 仅表示**如果该能力被保留并获授权**时应满足的技术与业务正确性要求；不等于对该能力已作实施承诺。每个开发包必须单独提交最小范围、验收标准和不做项。

## 11. 文档维护规则

7. 只有正式责任人签发后，才能进入 `ACCEPTED`。
8. 发现新问题时新增 Issue ID，不覆盖历史 Issue。
9. 修复代码后，保留原始发现、修复 commit、测试证据和验收证据。
10. 不得把本文件中的任何 `DOCUMENTED` 项目描述成已修复或已验收。
11. 手册中的可选、高级、低价值能力，经 Owner 正式决定可标为 `DEFERRED` 或 `OUT_OF_SCOPE`；不构成技术缺陷。
12. 已经对外开放且可能错误改变库存、金额、权限或财务事实的路径必须修复或安全封锁；产品裁剪不能成为容忍不安全写入的理由。
