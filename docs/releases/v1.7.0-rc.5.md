# Modern ERP v1.7.0-rc.5 Release Notes

V1.7.0-rc.5 是**第五次用户测试候选版本**。它在 `v1.7.0-rc.4`（commit `d570c4d`）之上闭合
**VMI 结算机制**这条自 `D-P01` / `D-P02` 悬置以来一直开放的业务链，并修掉它带来的一个
真实缺陷：结算凭证借记 `6401 主营业务成本`，而权威结账的 `COGS_TO_GL` 期望侧只认销售出库
成本 —— 于是**只要跑通 VMI 结算，权威结账就必然 BLOCKING**（客户环境实测
`COGS_TO_GL difference=5000`）。

业务所有者 2026-11-18 的两项裁定：

- **`D-P01` = D-2a** —— VMI 消耗直接扣 SUPPLIER 位单腿物理 OUT，商业释放 = 实际消耗量；
  `M1-F-07` 的双扣路径**结构性消失**；调整容差**严格 0**；首期**不开放**部分结算 / 多账单；
- **`D-P02` = 协议单价 + canonical 账单** —— 价格取 VMI **协议单价**；客户端**一律不得**传
  金额 / 账单 ID；账单走 **canonical Supplier Bill**（来源三元组 `VMI_SETTLEMENT_LINE`）；
  税按 `NO_TAX` 或协议约定；账单日期取消耗日期。

**本版本不是生产发布。** 手册级关闭（Manual Capability Closure）与九域 Release Readiness 仍未签发。
最终身份以 Git release tag 为准。

## 相对 v1.7.0-rc.4 的变更

### VMI 结算机制（Requirement §31.24 / Design §26.45，`VMI-SET-01..18`）

协议 → 收货 → 消耗 → **结算期** → **结算账单** → 过账的完整链路首次可用。

| 环节 | 合同 | 实现要点 |
|---|---|---|
| 协议单价 | `VMI-SET-03` | `vmi_agreements.unit_price_cents`；缺失或非法 → **409** `VMI_AGREEMENT_PRICE_MISSING`，**不得**回落池单价 / 标准成本 / 0 |
| 收货与消耗金额 | `VMI-SET-04` | 一律 = **协议单价 × 数量**（修正 §31.23 的收货价值来源）；否则账单金额与应付开项对不上 |
| 物权转移接口退役 | `VMI-SET-02` | `POST /api/procurement/vmi/ownership-transfers` → **410** `VMI_OWNERSHIP_TRANSFER_RETIRED` + 业务文案（不再出现「政策尚未批准」类内部治理措辞）；`vmi_ownership_transfers` 表**零写入** |
| 结算期 | `VMI-SET-06` | `CALENDAR_MONTH` / `CUSTOM`；同一协议的全部期间闭区间**不得重叠**（`UNIQUE(agreement_id, period_key)` 不替代重叠检查） |
| 首期期初证据 | `VMI-SET-07` | 必须来自 canonical inventory position 的**可审计快照**（`opening_source='CANONICAL_INVENTORY_POSITION'` + 快照时间 + 证据摘要 + 审计引用）；**不可证明即 409** `VMI_OPENING_BALANCE_UNPROVEN`，**不得**默认为 0 |
| 可结算量口径 | `VMI-SET-08` | `billable_qty = commercial_released_qty`（**不得**用 `received − consumed − transferred` 冒充） |
| 恒等式与容差 | `VMI-SET-09` | 关闭前必须通过 VMI-P / VMI-S / VMI-E / VMI-C / VMI-R 五组恒等式；调整容差**严格 0**（`M1-P-04`） |
| 首期不开部分结算 | `VMI-SET-10` | 一个结算期间只产生**一张**账单；分配事实写 `vmi_settlement_bill_allocations`（权威关系只在分配表） |
| canonical 账单与总账 | `VMI-SET-11` / `VMI-SET-12` | 走 `createSupplierBill` / `postSupplierBill`；结算凭证 `Dr 6401 主营业务成本 / Cr 2202 应付账款`，**不**照搬委外的 `Dr GRNI / Cr AP`（VMI 没有在途物资） |
| 期间守卫 | `VMI-SET-13` | 结算期开 / 闭与账单过账受 `FINANCE_AP_BILL` 轴（应付 + 存货 + 法定三轴）约束 |
| 权限与审计 | `VMI-SET-16` | 三个**独立**权限码（`VMI_SETTLEMENT_PERIOD_VIEW` / `VMI_SETTLEMENT_PERIOD_MANAGE` / `VMI_SETTLEMENT_BILL_MANAGE`），**不复用** `VMI_MANAGE` |

### `COGS_TO_GL` 期望侧覆盖 VMI 结算成本（Requirement §35.14 / Design §31.19，`AA-COG-01..06`）

- `6401 主营业务成本` 的**全部**来源是「销售出库成本 + VMI 结算成本」，期望侧**必须**覆盖
  **全部**来源；
- 期望侧**只计**「已出账结算账单所覆盖的结算成本」，以**分配事实**
  `vmi_settlement_bill_allocations` → 结算行 `settled_qty` × `unit_price_cents` 为连接脊柱；
- 期望侧**不**取「VMI 消耗的价值流水」—— 消耗腿在消耗时即减存货价值，而 `Dr 6401` 的成本
  凭证在结算出账时才记；计入消耗会造成「消耗已发生、结算未出账」窗口的**新瞬时失配**；
- **差额容忍未放宽**：仍是严格相等判定（差额 ≠ 0 即 FAIL / BLOCKING），无阈值、无白名单；
- 唯一实现点仍是 `server/modules/financial-inventory.js::systemHealth`。

### 权威结账归零

客户环境跑通结算链后，`/api/system-health` 的 **BLOCKING 24 项全部 PASS、FAILING = 0**，
`INVENTORY_VALUE_TO_GL` 差额 **0**。

### 迁移与 schema

- 新增 `server/migrations/v28-vmi-settlement.js`：三张结算表
  （`vmi_settlement_periods` / `vmi_settlement_lines` / `vmi_settlement_bill_allocations`）
  与 `vmi_agreements.unit_price_cents`；
- **纯加性、幂等、SQLite 与 MySQL 双端**；历史 VMI 数据**不回填** 0 或虚构值；
- `server/database/mysql-schema.js` 新增列类型 pin（被索引的文本列固定 `VARCHAR(128)`，
  否则通用启发式会给出 LONGTEXT，而 InnoDB 拒绝无前缀长度索引 LONGTEXT）。

## 已知残余（不得被描述为已消除）

1. **`6401` 的第三个来源仍未被期望侧覆盖**：`server/modules/consignment.js:488` 的
   `CONSIGNMENT_SETTLEMENT_COGS` 借记 `6401`，其估值流水类型 `CONSIGNMENT_SETTLEMENT`
   **不在**期望侧取值集合内 → `AA-COG-01`（「覆盖全部来源」）在委托代销这一支上**仍有口径
   缺口**。扩大期望侧**需独立裁定**（且委托代销的成本确认口径本身待裁定），本版本**未**
   擅自扩大。
2. **结算账单作废不冲销结算凭证**：`voidPostedInvoice` 只对 `SUPPLIER_BILL` 来源调
   `reverseSystemVoucher`，而 VMI 结算账单在 DIRECT 模式**不**产生该来源凭证（其成本凭证
   来源是 `VMI_SETTLEMENT_LINE`）→ 作废后 `6401` 成本与应付开项**留存**。属**会计语义待裁定**。
   （期望侧按「已出账」口径保留该金额，与总账侧一致，因此**不会**因此产生对账失配。）
3. **VMI 供应商资格规则** `OWNER_DECISION_PENDING`（`SCP-11`）。
4. **VMI 结算无 operator 工作面**：协议维护、结算期开闭、账单与分配**尚无前端页面**；
   本版本只交付读模型字段（`VMI-SET-15`）。
5. **VMI 收货不登记 LOT / SERIAL 身份**：跟踪口径货品的入库价值仍无法归属到具体身份
   （Requirement §32.18 开放项 1）。
6. **结算之后的消耗仍冲减收货开项**，结算开项不被结算后的消耗核销 —— 应付口径**待裁定**。
7. **步进调拨「退回来源仓」入库腿无 HTTP 路由**（zero-caller），其自持计值修复是预防性的。
8. **既有违规手工凭证不得再被冲销或改分录**（能力收缩；客户环境实测该类凭证为 0）。
9. **Manual Closure（22 本手册）与九域 Release Readiness 未签发**。
10. **客户环境无 TLS / 无异机副本**：`:443` 已配置并监听（证书当前为**自签**，浏览器提示不受
    信任），但**仍需业务所有者在腾讯云安全组放行 443** 才能签发受信任证书并打开 `:80 → :443`
    跳转；MySQL 自动备份 timer 已就绪（每天 02:17、Persistent、保留 14 份）且**恢复演练通过**
    （424 表 + 1 视图 + 5 触发器，行数与线上一致），但**异机副本**仍缺对象存储凭据
    （`PL-RI-01` RPO 24h / RTO 4h / 季度演练未达成，当前仅本机副本）。
11. **逐列 schema parity 未取证**；结算链的并发等价未在真实 MySQL 上单独取证。
