# V1.3 Phase 2：来源追溯与物流完整性

## 目标与来源真相

V1.3 新建的正常商业物流单据必须来自已授权的上游单据。头级来源、行级来源、往来单位、产品和商业计价基础在创建后不可通过普通草稿编辑接口改变。仓库只编辑执行数量、仓库、业务日期和备注。

历史 V1.2 无来源记录继续可读，界面关系区显示为 `Legacy / Source unavailable`（旧数据的 `relationships.direct` 标记）；它们不会被补造来源，也不能在 V1.3 中重新确认。独立库存变动使用库存调整、调拨、报废或盘点单，不再通过虚构的直入、直出或直退产生 AR/AP/收入/采购会计影响。

## 实际来源图

```text
PurchaseInstruction
  └─ purchase_instruction_id / purchase_instruction_item_id
     → PurchaseRequisition (RELEASED instruction)
       └─ purchase_requisition_id / purchase_requisition_item_id
          → PurchaseOrder (APPROVED requisition)
            └─ purchase_order_id / purchase_order_item_id
               → PurchaseReceipt (APPROVED order)
                 └─ receipt_id / receipt_item_id
                    → PurchaseReturn (CONFIRMED receipt)

SalesOrder
  └─ sales_order_id / sales_order_item_id
     → SalesDelivery (APPROVED order)
       └─ delivery_id / delivery_item_id
          → SalesReturn (CONFIRMED delivery)
```

## 每条来源边的合同

| 来源 → 下游 | 头来源 / 行来源 | 来源状态 | 往来单位 | 产品 | 价格 | 数量上限 | 确认后的库存 / 财务影响 |
|---|---|---|---|---|---|---|---|
| 采购指令 → 请购 | `source_instruction_id` / `purchase_instruction_item_id` | `RELEASED` | 请购可保留建议供应商；不是最终商业供应商 | 必须相同 | 指令可用估价作为参考；请购草稿允许销售角色修改估价 | 不超过指令建议数量；同一指令行只转换一次 | 无库存、无财务影响 |
| 请购 → 采购订单 | `purchase_requisition_id` / `purchase_requisition_item_id` | `APPROVED` | PO 草稿选择最终供应商 | 必须相同 | 请购估价预填；PO 草稿可谈价，提交后必须为正整数分 | 当前架构一次生成全部剩余量且禁止再次生成，因此不会超请购 | 无库存、无财务影响 |
| 采购订单 → 收货 | `purchase_order_id` / `purchase_order_item_id` | `APPROVED` | 供应商必须等于 PO | 必须相同 | 服务端使用已审批 PO 行单价；客户端冲突价格拒绝 | 所有已确认收货累计加本次不得超过 PO 行数量 | 库存增加一次；AP 与采购凭证按实收数量 × PO 单价生成一次 |
| 采购收货 → 采购退货 | `receipt_id` / `receipt_item_id` | `CONFIRMED` | 供应商必须等于收货单 | 必须相同 | 服务端继承收货/PO 单价 | 所有已确认退货累计加本次不得超过该收货行实收数量 | 库存减少一次；AP 冲减与反向凭证生成一次 |
| 销售订单 → 出货 | `sales_order_id` / `sales_order_item_id` | `APPROVED` | 客户必须等于 SO | 必须相同 | 服务端使用已审批 SO 行单价；客户端冲突价格拒绝 | 所有已确认出货累计加本次不得超过 SO 行数量 | 库存减少一次；AR 与收入凭证按实发数量 × SO 单价生成一次 |
| 销售出货 → 销售退货 | `delivery_id` / `delivery_item_id` | `CONFIRMED` | 客户必须等于出货单 | 必须相同 | 服务端继承出货/SO 单价 | 所有已确认退货累计加本次不得超过该出货行实发数量 | 库存增加一次；AR 冲减与收入反向凭证生成一次 |

## 事务和不可变性

确认接口在同一 SQLite 事务中重新读取来源头与来源行，验证来源状态、往来单位、产品、价格、累计剩余量和当前单据状态，然后才执行库存、库存流水、AR/AP、凭证和审计日志。任一验证失败会回滚全部副作用。重复确认由草稿状态守卫拒绝，不会重复过账。

来源头 ID、来源行 ID、往来单位、产品和价格不可通过草稿更新改变。选错来源时应取消或删除草稿后重建。草稿仍允许修改正整数执行数量，并在最终确认时再次按最新已确认累计量校验。

## 分批履行

履行真相来自“带行级来源且状态为 `CONFIRMED` 的下游行”之和；`DRAFT`、`CANCELLED` 和旧版无来源行不计入。

- 销售：`NOT_DELIVERED`、`PARTIALLY_DELIVERED`、`FULLY_DELIVERED`
- 采购：`NOT_RECEIVED`、`PARTIALLY_RECEIVED`、`FULLY_RECEIVED`

来源查询返回原数量、已执行数量和剩余数量；物流详情逐行返回相同数据与确定性履行状态。状态为派生数据，不复制到订单头，避免并发写入不同步。

## 数据库迁移与兼容

`server/migrations/v13-phase2-source-integrity.js` 是幂等加法迁移，新增：

- `purchase_orders.purchase_requisition_id`
- `purchase_order_items.purchase_requisition_item_id`
- `purchase_receipt_items.purchase_order_item_id`
- `sales_delivery_items.sales_order_item_id`
- `return_order_items.delivery_item_id`
- `purchase_return_items.receipt_item_id`

同时为所有头/行来源查询和累计数量查询建立索引。原有收货、出货和退货头来源继续使用既有 FK。SQLite 对存量表不能安全地通过 `ALTER TABLE` 追加行级 FK，因此新增行来源列保持可空以读取旧数据，所有 V1.3 新写入由应用事务强制验证。不会为旧记录填充虚假 ID。

## 人员职责

- `test_sales`：创建/提交请购和采购订单，不能确认出货或收货。
- `test_reviewer`：维持五类审批流程。
- `test_warehouse`：从有效来源创建并确认收货、出货和退货，不能修改商业价格。
- `admin`：保留管理能力，但正常物流执行不依赖管理员。
